## 개요

PR(pull request) 리뷰나 셀프 리뷰에 들어가기 전에 변경을 얼마나 이해했는지 문항으로 점검합니다.
대상의 diff에서 비즈니스·테크 문항을 만들어 대화형으로 풀거나 PR 댓글로 게시합니다.

- **경계**: 이 스킬은 이해도를 묻습니다. 결함 지적과 위험도 산출은 git-review가 담당하며 여기서는 하지 않습니다.
- **두 가지 방식**: 대화형 진행(기본)과 `--comment` 게시.
- **산출 파일**: 대화형은 `.ai/99_workspace/temp_review_quiz.md`, `--comment`는 `.ai/99_workspace/temp_review_quiz_comment.md`.
- **형식 SSoT**: 이 skill 디렉토리의 `templates/quiz-template.md`가 산출 파일 형식의 원본이고, `scripts/check-quiz.sh`가 그 형식을 판정합니다.

## 관련 skill

- git-review (독립): 서로 호출하지 않습니다. 테크 문항의 소재 축인 7 카테고리 체계의 원본이 git-review에 있으므로, 한쪽을 고치면 양쪽을 동기화합니다.
- git-review-context (참고): `.ai/99_workspace/temp_review_context.md`가 있으면 변경 요약으로 참고합니다. 자동 호출하지 않습니다.
- git-pr-feedback (참고): 대상 PR 식별과 댓글 게시 규칙의 원본입니다. 이 스킬은 핵심만 옮겨 담은 사본이므로, 한쪽을 고치면 양쪽을 동기화합니다.
- ai-workspace (권장): `.ai/99_workspace/` 경로에 산출 파일을 씁니다. 구조가 없으면 필요한 디렉토리를 직접 생성합니다.

## 실행 절차

아래 순서로 진행합니다. 각 단계의 세부 규칙은 같은 이름의 섹션을 참조합니다.

### 1단계: 대상 식별

> 이 단계의 저장소 확정·`--repo`·`--hostname` 규칙은 `git-pr-feedback/SKILL.md` "대상 PR 식별"에서 핵심만 옮긴 사본입니다. 한쪽을 고치면 양쪽을 동기화합니다.

- 최초 조회 전에 대상 저장소를 확정합니다. 현재 브랜치의 upstream 원격(없으면 `origin`)의 URL을 정규화해 호스트/소유자/저장소를 얻고, 원격이 없거나 후보가 복수면 사용자에게 질의합니다.
- 인자로 PR 번호를 받으면 그 PR을 대상으로 합니다. 인자가 없으면 현재 브랜치의 열린 PR을 자동 감지하고, 감지에 실패하면 **브랜치 모드**로 진행합니다.
- 최초 `gh pr view`부터 `--repo '<호스트>/<소유자>/<저장소>'`를 명시합니다. 무보호로 조회하면 `GH_REPO`·`GH_HOST` 환경 변수나 실행 디렉토리가 다른 저장소의 동명 PR을 선택하고, 그 응답을 불변값으로 보관하면 잘못된 대상이 그대로 고정됩니다.
- 조회 응답의 PR URL이 확정한 저장소와 일치하는지 확인한 뒤, 호스트/소유자/저장소·PR 번호·URL·`headRefOid`·`baseRefName`·`baseRefOid`를 불변값으로 보관합니다. `headRefOid`와 `baseRefOid`는 permalink의 커밋 SHA 기준값입니다.
- 이후 `gh pr` 계열 명령에는 `--repo`를, `gh api` 계열 명령에는 `--hostname '<호스트>'`를 명시합니다. `gh api`의 기본 호스트는 github.com이라, GitHub Enterprise를 다룰 때 호스트를 생략하면 같은 소유자/저장소·번호의 무관한 github.com PR을 읽게 됩니다.

```bash
# 대상 저장소 확정. upstream 원격(없으면 origin)의 URL을 정규화해 호스트/소유자/저장소를 얻는다
git rev-parse --abbrev-ref '@{upstream}'      # '<원격 이름>/<브랜치>'
git remote get-url '<원격 이름>'

# 현재 브랜치의 열린 PR 자동 감지. --repo를 쓰면 선택자 인자가 필수라 브랜치 이름을 지정한다
gh pr view '<현재 브랜치>' --repo '<호스트>/<소유자>/<저장소>' \
  --json number,title,url,headRefName,headRefOid,baseRefName,baseRefOid
```

- **브랜치 모드**: 대상 PR이 없는 상태입니다. `--comment`를 쓸 수 없고 위치 행에 permalink도 붙이지 않습니다. `--comment`가 지정된 채 브랜치 모드가 되면 그 사실을 알리고 중단합니다.

### 2단계: diff 수집

- PR 모드는 `gh pr diff`로, 브랜치 모드는 merge-base 기준 `git diff`로 변경을 수집합니다. 브랜치 모드의 `git diff`는 커밋하지 않은 작업 트리 변경까지 포함합니다.
- 변경 파일 목록과 파일별 변경 규모를 함께 파악합니다. 4단계의 문항 수 조정에 씁니다.

```bash
# PR 모드. --repo는 1단계에서 보관한 불변값
gh pr diff '<PR 번호>' --repo '<호스트>/<소유자>/<저장소>'

# 브랜치 모드. base는 origin/HEAD가 가리키는 브랜치, 없으면 main
base="$(git symbolic-ref --quiet --short refs/remotes/origin/HEAD 2>/dev/null || echo 'main')"
git diff "$(git merge-base "$base" HEAD)"
```

### 3단계: 근거 문서 확보

- `.ai/30_contract/index.md`와 `.ai/40_domain/index.md`를 읽고, 변경과 관련 있는 파일만 선택적으로 읽습니다. 사용자가 특정 `.md` 파일을 지정하면 그 파일도 읽습니다.
- **"없음" 판정 기준**: index의 목차가 비어 있거나 자리표시자 행뿐이고 하위 파일이 `.gitkeep` 또는 빈 표 템플릿이면 근거 문서 0건으로 봅니다. 파일이 존재한다는 사실만으로 근거가 있다고 보지 않습니다.
- 근거 문서가 0건이면 "비즈니스 문항 없음, 테크 문항만 출제"를 사용자에게 알리고 그대로 진행합니다.
- 문서가 없을 때 도메인·계약을 추정해 문서를 새로 쓰지 않습니다. 추정 문서 작성은 git-review "문서 부재 시 처리"의 영역이며 이 스킬은 하지 않습니다.

### 4단계: 옵션 확정

- **형식**: `--mcq`·`--open` 중 어느 것도 없으면 객관식·주관식·혼합 가운데 무엇으로 낼지 1회 질의합니다.
- **관점**: `--business`·`--tech` 중 어느 것도 없으면 두 관점을 모두 냅니다. 근거 문서가 0건이면 테크 문항만 냅니다.
- **문항 수**: 기본 5개이고 허용 범위는 3~10개입니다. 변경 파일이 1~2개면 3개까지 줄입니다. 사용자가 자연어로 수를 지정하면 그 값을 범위 안에서 따릅니다.

### 5단계: 문항 생성·파일 작성

- "문항 생성 규칙"을 따라 문항을 만들고, `templates/quiz-template.md`의 형식으로 산출 파일을 씁니다.
- 대화형은 `.ai/99_workspace/temp_review_quiz.md`에 `## 대상`·`## 문항`·`## 응답 기록` 순으로 씁니다. `## 응답 기록`의 표는 머리행만 두고 시작합니다.
- `--comment`는 `.ai/99_workspace/temp_review_quiz_comment.md`에 따로 씁니다. 위치 행에 permalink를 병기하고 `## 응답 기록`은 두지 않습니다.
- `.ai/99_workspace/`가 없으면 만들고 씁니다.

### 6단계: 헬퍼 검사

- 산출 파일을 쓴 직후 형식 검사 헬퍼를 돌립니다. 통과하기 전에는 7단계로 넘어가지 않습니다.
- 위반이 나오면 해당 문항을 보정하고 다시 검사합니다. 보정으로 해결되지 않는 위반은 사용자에게 알립니다.

```bash
# <skill 디렉토리>는 이 SKILL.md가 있는 디렉토리. 실행 시 실제 경로로 바꿔 쓴다.
quiz_check='<skill 디렉토리>/scripts/check-quiz.sh'

# 대화형 산출 파일
"$quiz_check" '.ai/99_workspace/temp_review_quiz.md'

# --comment 게시 본문 (permalink 전수 검사 + 1단계에서 보관한 기준 SHA 대조)
"$quiz_check" --comment --head '<headRefOid>' --base '<baseRefOid>' \
  '.ai/99_workspace/temp_review_quiz_comment.md'
```

통과는 무출력·종료 코드 0입니다. 위반은 `위반 R<n> Q<m>: <사유>`를 1행씩 출력하고 종료 코드 1, 사용오류는 종료 코드 2입니다.

**댓글 본문은 반드시 `--comment`로 검사합니다.** 일반 모드는 permalink 병기를 선택으로 보므로, 문항 일부에 permalink가 빠지거나 브랜치명을 가리켜도 통과합니다. `--head`·`--base`를 함께 넘겨야 SHA가 기준 커밋과 대조됩니다.

### 7단계: 대화형 진행 또는 게시

- 기본은 대화형 진행입니다 ("대화형 진행" 참조).
- `--comment`가 지정되면 승인 게이트를 거쳐 PR 댓글로 게시합니다 ("옵션"의 `--comment` 참조).

## 문항 생성 규칙

### 근거 규칙

- 문항마다 `위치: ` 행을 1개 이상 두고, 헤더 다음 첫 비어 있지 않은 행에 둡니다. 경로와 줄 범위는 수집한 diff에 실제로 있는 값이어야 합니다.
- **변경 자체를 묻습니다.** 변경을 보지 않고도 답할 수 있는 일반 지식 문항은 내지 않습니다.
- **정답과 해설은 실제 동작으로 확인합니다.** 소스 주석이나 커밋 메시지의 설명을 근거로 삼을 때도 코드가 실제로 무엇을 하는지 대조하고, 갈리면 실제 동작을 따릅니다. 주석이 일반적인 성질을 설명하는데 코드는 그 성질을 피해 가는 인자를 쓰는 경우가 있어, 주석만 믿으면 정답이 성립하지 않는 문항이 나옵니다. 판단이 서지 않으면 해당 명령을 최소 재현으로 돌려 확인합니다.
- 비즈니스 문항은 `.ai/30_contract/`·`.ai/40_domain/` 문서의 조항을 근거로 삼습니다. 근거 문서가 0건이면 비즈니스 문항을 내지 않습니다.
- 소재는 기능 구현부와 정책 반영부를 우선합니다. 오타 수정·서식 변경·자동 생성 파일은 소재로 쓰지 않습니다.
- 삭제된 코드를 묻는 문항은 위치 행에 ` (base)`를 병기합니다. 이 위치는 `baseRefOid` 기준입니다.

### 문항 본문에 코드 블록을 두지 않습니다

`check-quiz.sh`는 마크다운 코드 펜스를 상태로 다루지 않고 행 접두어를 그대로 봅니다. 문항 본문에 코드 블록을 두면 그 안의 `### `·`<details>` 행까지 문서 구조로 세어 형식 검사가 어긋납니다.
코드를 보여줘야 하면 위치 행으로 가리키고 문장으로 설명합니다.

### 테크 소재 축

git-review 테크 리뷰의 7 카테고리에서 소재를 고릅니다. 카테고리 체계의 원본은 `git-review/SKILL.md`이므로 한쪽을 고치면 양쪽을 동기화합니다.

| 카테고리 | 문항 소재 |
|----------|-----------|
| 기능 | 변경이 무엇을 하는지, 입력·출력·분기 조건 |
| 아키텍처 | 배치·계층·의존 방향, 관련 ADR과의 정합성 |
| 버그 | 경계 조건·예외 처리·동시성에서 달라진 동작 |
| 보안 | 입력 검증·권한 확인·비밀값 취급의 변경 |
| 코드품질 | 기존 패턴을 따른 지점과 그 이유 |
| 성능 | 반복 조회·자원 해제 등 비용 구조의 변경 |
| 테스트 | 어떤 회귀를 막는지, 반례가 무엇을 고정하는지 |

### 힌트 규칙

- 볼 위치와 판단 조건만 알려줍니다. 정답을 직접 말하거나 선택지를 지목하지 않습니다.
- 힌트 블록은 문항마다 정확히 1개이고 정답 블록보다 앞에 옵니다.
- **힌트와 정답은 각각 독립된 `<details>` 블록입니다.** 한 접기에 두 `<summary>`를 넣으면 힌트를 열 때 정답까지 함께 펼쳐져 문항이 성립하지 않습니다. 접기는 문항 안에서 열린 만큼 닫습니다.

### 형식 규칙

- 문항 헤더는 `### Q<n> [<관점> · <형식>]`이고 `<n>`은 1부터 연속 증가합니다. `<관점>`은 `테크`·`비즈니스`, `<형식>`은 `객관식`·`주관식`입니다.
- **`## 문항` 아래의 `### ` 헤더는 모두 문항으로 봅니다.** 문항이 아닌 소절 헤더를 그 아래에 두지 않습니다. 형식 검사가 `### ` 행을 전부 문항 후보로 열어 R1 형식과 대조하므로, 참고용 소절을 두면 문항 헤더 형식 위반으로 걸립니다.
- 객관식 선택지는 `- (a) ` 형식으로 `(a)`·`(b)`·`(c)` 순으로 늘리며 2개 이상 둡니다. 라벨은 `(a)`부터 건너뜀·중복 없이 연속해야 하며, 객관식 판정이 선택지 문자를 비교하므로 중복 라벨은 답안을 모호하게 만듭니다. 선택지는 첫 접기 앞에 둡니다. 주관식에는 선택지를 두지 않습니다.
- 정답 블록은 `<summary>정답·해설</summary>`을 둔 접기 1개입니다. 객관식은 `(<문자>). <해설>`로 시작하고, 주관식은 모범 답안을 먼저 씁니다. 그 다음 줄에 `근거: ` 행으로 코드 위치를, 비즈니스 문항이면 `정책 근거: ` 행으로 문서 경로와 조항을 함께 둡니다. **객관식 정답 문자는 그 문항의 선택지 라벨 중 하나여야 합니다.** 형식 검사가 이 네 가지(첫 행 형식, 정답 문자와 선택지의 결속, `근거: ` 행, 비즈니스 문항의 `정책 근거: ` 행)를 판정하므로, 정답 블록을 비워 두거나 근거 행을 빠뜨리면 6단계에서 걸립니다. 정답 문자 뒤를 공백으로 두거나 모범 답안 자리에 `<!-- TODO -->` 같은 주석만 남기는 것도 내용이 없는 것으로 판정합니다. 읽는 사람 화면에 해설이 보이지 않기 때문입니다.
- **`근거:`·`정책 근거:` 행은 반드시 접기 안에 둡니다.** 접기 밖 행이 `정답`으로 시작하면 형식 검사 R6 위반이며, 정답이 문항과 함께 노출됩니다.
- 문서 골격은 `## 대상` 1개, `## 문항` 1개이고 문항 블록은 `## 문항` 아래에만 둡니다. `## 응답 기록`은 선택이며 마지막 문항 뒤에 옵니다.

## 대화형 진행

한 문항씩 제시하고 응답을 받아 판정한 뒤 다음 문항으로 넘어갑니다.

### 문항 제시

- 문항 번호·관점·형식, 위치, 문제를 제시합니다. 객관식이면 선택지도 함께 제시합니다.
- 힌트와 정답·해설은 이 시점에 제시하지 않습니다.

### 사용자 응답 처리

- **"힌트"**: 그 문항의 힌트만 제시하고 같은 문항의 응답을 다시 기다립니다. 힌트 요청은 판정에 반영하지 않습니다.
- **"건너뛰기"**: 판정 없이 다음 문항으로 갑니다. 응답 기록 표에는 행을 추가하지 않고, 결과 요약의 건너뛴 문항 목록에 남깁니다.
- **"그만"**: 남은 문항을 중단하고 결과 요약으로 갑니다.
- 그 밖의 입력은 답안으로 봅니다.

### 판정

- **객관식**: 응답의 선택지 문자를 정답 문자와 비교합니다.
- **주관식**: 정답 블록의 모범 답안·해설과 대조해 `정답`·`부분`·`오답` 중 하나로 매기고 근거를 한 줄 붙입니다.

### 기록·공개

- 판정 직후 정답·해설을 공개합니다.
- `## 응답 기록` 표에 `| Q<n> | <응답> | <판정> |` 1행을 덧붙입니다. `정답`이 아니면 판정 뒤 괄호로 사유를 한 줄 적습니다.
- 응답이 길면 표에는 요지만 줄여 적습니다.

### 결과 요약

진행을 마치면 아래를 제시합니다.

- 정답 수와 문항 수 (`부분`은 정답으로 세지 않고 따로 셉니다)
- 틀린 문항의 번호와 위치 목록
- 건너뛴 문항이 있으면 그 번호 목록
- 산출 파일 경로

## 옵션

### `--comment`

문항을 PR 댓글로 게시합니다.

- **PR 대상에서만 씁니다.** 브랜치 모드에서 지정되면 그 사실을 알리고 중단합니다.
- 게시 본문은 `.ai/99_workspace/temp_review_quiz_comment.md`에 따로 씁니다. 위치 행에 permalink를 병기하고 `## 응답 기록`은 두지 않습니다. 대화형 진행은 하지 않습니다.
- **permalink 형식**: `https://<호스트>/<소유자>/<저장소>/blob/<커밋 SHA>/<경로>#L<시작>-L<끝>` (한 줄이면 `#L<n>`). 추가·수정 코드는 `headRefOid`, 삭제 코드는 `baseRefOid`를 씁니다.
- 게시 전에 6단계 헬퍼 검사를 본문 파일에도 돌립니다. 이때 `--comment --head <headRefOid> --base <baseRefOid>`를 넘겨 모든 위치 행의 permalink와 기준 SHA를 전수 검사합니다.

#### 승인 게이트 (생략 불가)

댓글 게시는 외부 공개 행위이므로 실행 직전에 승인을 받습니다.

- 대화에 제시하는 것은 **본문 파일 경로, 문항 수, 관점별 건수, 위치 목록**뿐입니다. 본문 전문은 대화에 다시 출력하지 않습니다.
- 승인받은 본문은 명령 문자열에 보간하지 않고 파일로 전달합니다. 본문에 `$(...)`나 백틱이 있으면 셸이 명령 치환을 실행해, 승인 화면에서 본 값과 실제 게시되는 값이 달라집니다.
- 승인 후 본문을 고치면 다시 승인 대상입니다. 거절하면 게시하지 않고 본문 파일만 남깁니다.

```bash
# 승인받은 본문 파일을 그대로 게시. --repo의 호스트/소유자/저장소는 1단계에서 보관한 불변값
gh pr comment '<PR 번호>' --repo '<호스트>/<소유자>/<저장소>' --body-file '.ai/99_workspace/temp_review_quiz_comment.md'
```

### `--mcq` / `--open`

문항 형식을 지정합니다.

- `--mcq`: 모든 문항을 객관식으로 냅니다.
- `--open`: 모든 문항을 주관식으로 냅니다.
- 둘 다 없으면 4단계에서 1회 질의합니다. 둘을 함께 지정하면 혼합으로 봅니다.
- 혼합은 문항별로 소재에 맞는 형식을 고릅니다. 값을 고르는 문제는 객관식, 이유·의도를 묻는 문제는 주관식이 맞습니다.

### `--business` / `--tech`

문항 관점을 지정합니다.

- `--business`: 비즈니스 문항만 냅니다.
- `--tech`: 테크 문항만 냅니다.
- 둘 다 없거나 둘을 함께 지정하면 두 관점을 모두 냅니다. 근거 문서가 0건이면 테크 문항만 내고 그 사실을 알립니다.
- 근거 문서가 0건인데 `--business`만 지정되면 낼 수 있는 문항이 없으므로 그 사실을 알리고 중단합니다.

## 산출물 접기 기준

산출물의 상세 내용은 `<details>` 접기로 분량을 줄이되, 아래 기준을 따릅니다.

- **접기 가능**: 근거·대안 비교·상세 절차·코드 예시·참고자료
- **접기 금지**: 결정사항·리스크·액션 아이템

`.ai/10_rules/writing-principles.md`가 있으면 그 원칙을 따르고, repo 고유 확장 `writing-principles-local.md`와 충돌하면 local이 우선합니다. 이 블록은 파일이 없을 때의 기본값입니다.

이 스킬에서는 힌트와 정답·해설이 접기 대상이고, 문항 본문과 위치 행은 접지 않습니다.
정답이 접기 밖으로 나오면 문항을 풀기 전에 답이 보이므로 문항이 성립하지 않습니다 (`check-quiz.sh` R6).
