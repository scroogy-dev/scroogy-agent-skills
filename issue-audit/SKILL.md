## 개요

이슈 스펙(요구사항) 대비 구현을 **독립 감사인** 관점에서 검증합니다.
구현을 수행한 AI가 아닌 다른 모델이 실행하는 것을 전제로, 두 단계로 감사를 수행합니다.

- **1단계 — 적합성 검증**: 스펙 대비 구현 완료 여부를 항목별로 대조
- **2단계 — 비판적 검증**: 구현이 잘못되었을 수 있는 근거를 적극적으로 탐색

## 관련 skill

- issue-work (권장): `.ai/90_issues/` 의 스펙·계획·요약 파일을 감사 입력으로 활용합니다.
  `issue-work` 계획의 마지막 고정 **Task N(교차모델 검증)**에서 이 스킬을 호출합니다.
  구현 모델과 **다른 벤더 모델**(Non-Anthropic 포함)로 **사용자가 직접 수동 수행**하며,
  감사 결과는 `issue-<번호>-summary.md`의 모델 기록·Task별 결과에 반영합니다.
- ai-workspace (권장): `.ai/30_contract/`, `.ai/40_domain/` 문서를 비즈니스 검증에 참조합니다.

> `git-review`와의 차이: git-review는 PR 단위 코드 품질 리뷰이고,
> issue-audit는 이슈 단위 스펙 충족 + 비판적 검증입니다.

## 참조 문서

- **공통 규칙**: `.ai/10_rules/context-loading.md` — 있으면 따르며, 이미 적재되어 있으면 재로딩하지 않습니다.
- **스킬 고유 추가 참조**:
  - `.ai/90_issues/active/` 하위 전체 또는 `.ai/90_issues/archive/issue-<번호>/` 전체
  - `.ai/30_contract/index.md`, `.ai/40_domain/index.md` — 도메인·계약 정합성 (index 먼저 → 관련 파일만 선택적으로)
  - `.ai/50_adr/index.md` — 1단계 경계 검증 시 ADR과의 정합성 대조 (index 먼저 → 관련 ADR만 선택적으로)
  - `.ai/60_codebase/index.md` — 관련 기능의 호출 흐름
  - `.ai/70_ledger/index.md` — 이미 수용된 known issue·기술부채 대조 (index 먼저 → 관련 항목만 선택적으로)
  - `.ai/10_rules/writing-principles.md`·`.ai/10_rules/writing-principles-local.md` — 있으면 산출물 작성 원칙으로 참조 (충돌 시 local 우선; 없으면 본문의 "산출물 접기 기준"이 기본값)

## 역할 원칙

이 스킬을 실행하는 AI는 **독립 감사인**입니다.

- 구현자의 의도를 선의로 해석하지 않는다.
- "동작하니까 괜찮다"가 아니라 "스펙에 명시된 대로인가"를 기준으로 판단한다.
- 스펙 자체의 모호함이나 누락도 발견 사항으로 보고한다.

## 절차

### 0단계: 컨텍스트 수집

1. `.ai/90_issues/active/issue-<번호>/` 또는 `.ai/90_issues/archive/issue-<번호>/` 에서 스펙·계획·요약 파일을 읽는다.
   - 파일이 없으면 GitHub Issue 본문을 직접 읽어 스펙으로 사용한다.
2. `.ai/60_codebase/index.md`에 내용이 있으면 참고하여 관련 기능의 호출 흐름을 빠르게 파악한다.
   - 단, SSoT는 소스코드이므로 색인을 신뢰하지 않고 반드시 실제 코드를 확인한다.
   - 감사 과정에서 색인과 실제 코드가 다른 부분을 발견하면, 감사 리포트에 "코드베이스 색인 갱신이 필요해 보입니다 (`/code-map`)" 의견을 남긴다.
3. `.ai/30_contract/index.md`, `.ai/40_domain/index.md`, `.ai/50_adr/index.md`를 먼저 읽고 관련 문서만 선택적으로 확보한다 (있는 경우).
4. `.ai/70_ledger/index.md`가 있으면 읽고 이번 감사 범위와 관련된 항목만 선택 적재한다. 이미 수용된 known issue·기술부채를 신규 발견으로 재보고하지 않기 위한 대조 기준이다.
   2단계 대조에 필요한 항목의 `수용 사유`·`재검토 조건`은 `.ai/70_ledger/active/K-<번호>-<slug>.md`에서 확인한다.
   index의 항목 목록에서 감사 범위와 관련된 `archive/` 항목(`승격`·`해소`)이 보이면 그 항목도 `.ai/70_ledger/archive/`에서 함께 적재한다.
   `active/`만 읽으면 청산한 결함의 재등장을 계보(`K-<번호> 재발`) 없이 그냥 신규로 적게 되고, `승격` 항목의 연결 이슈 번호도 확인할 수 없다.
   원장이 없으면 기등재 0건으로 보고 진행한다. 대조 기준이 없을 뿐 감사 자체는 성립한다.
5. 구현 브랜치의 변경 파일 목록과 diff를 확보한다.
6. 같은 이슈의 이전 감사 리포트가 있으면 모두 읽는다. 최신 리포트는 `.ai/99_workspace/issue-<번호>-audit-report.md`,
   이전 회차는 `issue-<번호>-audit-report-<회차>.md`로 보존된다 ("3단계: 결과 기록" 참조).
   이슈 정리(issue-work `--clear`) 뒤에는 보존된 리포트가 `.ai/90_issues/archive/issue-<번호>/`로 이관되므로,
   archive 이슈를 재감사할 때는 그 디렉토리의 리포트도 함께 탐색한다.
   재감사에서는 이전 발견의 닫힘/잔여 판정과 발견 번호 계승의 기준이 된다.

### 1단계: 적합성 검증 (Compliance Check)

> 목적: 이슈 스펙에서 요구한 사항이 빠짐없이 구현되었는지 대조한다.

#### 검증 항목

1. **요구사항 대조** — 스펙 `요구사항 (Requirements)` 포함 목록의 각 항목(R<n>)에 대해 구현 충족 여부를 판정한다.
2. **완료의 정의(DoD) 대조** — 스펙에 정의된 DoD 체크리스트 항목별 충족 여부를 판정한다.
3. **경계 검증** — 스펙 요구사항의 제외 목록을 침범하지 않았는지, 또는 스펙에 없는 기능이 추가되지 않았는지 확인한다.
4. **도메인/계약/ADR 정합성** — `.ai/30_contract/`, `.ai/40_domain/`, `.ai/50_adr/` 의 관련 문서가 있으면 구현이 이와 충돌하지 않는지 검증한다.

#### 판정 기준

각 항목에 대해 아래 중 하나로 판정한다.

| 판정 | 의미 |
|------|------|
| 충족(PASS) | 스펙 요구사항을 충족함 |
| 미충족(FAIL) | 스펙 요구사항을 충족하지 않음 |
| 부분 충족(PARTIAL) | 부분적으로 충족하나 불완전함 |
| 판정 불가(N/A) | 현재 변경 범위에서 판정 불가 |

2단계 발견을 1단계 미충족(FAIL)·부분 충족(PARTIAL)의 근거로 삼는 것은 그 발견이 스펙에 명시된
요구사항·DoD 항목에 결속될 때만으로 한정한다. 스펙에 결속되지 않은 발견은 1단계 판정을 낮추지 않는다.
종료 기준 없이 판정을 낮추면 감사가 끝나지 않는다. 이 한정은 **1단계 판정에만** 적용되며,
2단계 위험도는 스펙 결속 여부와 무관하게 2단계의 위험도 분류 정의로 독립 판정한다.
예를 들어 스펙이 요구하지 않은 보안·데이터 손실 결함은 1단계 충족(PASS)과 2단계 높음(HIGH)이 병존할 수 있다.

---

### 2단계: 비판적 검증 (Critical Review)

> 목적: "이 구현이 왜 잘못되었을 수 있는가?"를 전제로 적극적으로 문제를 탐색한다.

#### 검증 관점

1. **엣지케이스** — 경계값, 빈 입력, 대용량, 동시성 등 비정상 상황에서의 동작
2. **암묵적 가정** — 구현이 전제하고 있지만 스펙에 명시되지 않은 가정
3. **부작용** — 변경이 기존 기능에 미칠 수 있는 영향 (회귀 가능성)
4. **스펙 모호성** — 스펙 자체가 여러 해석을 허용하는 부분
5. **누락된 검증** — 테스트가 부재하거나 불충분한 영역

#### 카테고리

각 발견 사항에 아래 7개 카테고리 중 하나를 부여한다. 두 축은 역할이 다르다.
**카테고리**는 발견이 속한 영역의 집계 축이고, 위 **검증 관점**은 발견을 어떻게 찾았는지의 탐색 축이다.

| 카테고리 | 검증 내용 |
|----------|-----------|
| 기능 | 도메인·비즈니스 내용에 해당하는 주요 기능이 올바르게 구현되었는지 |
| 아키텍처 | 프로젝트 아키텍처 방향(`.ai/10_rules/architecture.md` 참고)에 부합하는지, 관련 ADR(`.ai/50_adr/index.md` 참고)과 설계 정합성이 맞는지 |
| 버그 | 논리 오류·경계 조건·예외 처리·동시성 등 결함 가능성이 없는지 |
| 보안 | 입력 검증 누락·비밀값 노출·권한 확인 누락 등 취약점이 없는지 |
| 코드품질 | 가독성·중복·기존 패턴 준수 등 유지보수성이 유지되는지 |
| 성능 | 불필요한 연산·반복 조회·자원 누수 등 성능 저하 요인이 없는지 |
| 테스트 | 변경 기능에 대한 테스트 케이스가 충분한지, 회귀를 막는지 |

이 카테고리 체계는 `git-review`가 원본이다 (스킬 단독 실행을 위해 복사해 두었으므로 한쪽 변경 시 양쪽 동기화).

#### 위험도 분류

각 발견 사항에 **영향 축**과 **발생확률 축**을 먼저 판정하고, 두 값의 조합으로 위험도를 산출한다.
감사인이 등급을 직접 고르지 않는다. 교차모델 감사에서 모델마다 등급이 갈리면 아래 처리 기준이 일관성을 잃는다.

**영향 축** — 발견이 실현됐을 때 무엇이 무너지는가

| 값 | 의미 |
|----|------|
| 스펙·기능 달성 차단 | 스펙이 요구한 기능·보장이 성립하지 않음. 데이터 손실·보안 침해처럼 결과가 기능 달성을 무효화하는 결함을 포함한다 |
| 기능 저하 | 동작하나 품질·사용성이 떨어짐 |
| 기술 품질 의견 | 동작·보장에 영향 없는 구조·가독성 지적 |

**발생확률 축** — 어떤 조건에서 실현되는가

| 값 | 의미 |
|----|------|
| 통상 사용 | 정상 사용 경로에서 발생 |
| 특수 조건·엣지 | 경계값·비정상 입력·드문 조합에서만 발생 |

**영향 × 발생확률 매트릭스**

| 영향 \ 확률 | 통상 사용 | 특수 조건·엣지 |
|-------------|-----------|----------------|
| 스펙·기능 달성 차단 | 높음(HIGH) | 중간(MEDIUM) |
| 기능 저하 | 중간(MEDIUM) | 낮음(LOW) |
| 기술 품질 의견 | 낮음(LOW) | 정보(INFO) |

**등급 산출** — 두 축을 판정한 뒤 아래 헬퍼로 매트릭스를 조회한다. 표를 눈으로 읽어 등급을 고르지 않는다.

```bash
# <skill 디렉토리>는 이 SKILL.md가 있는 디렉토리. 실행 시 실제 경로로 바꿔 쓴다.
classify='<skill 디렉토리>/scripts/classify-risk.sh'

"$classify" --impact '기능 저하' --likelihood '통상 사용'   # → 🟡 중간(MEDIUM)
```

허용되지 않은 축 값은 종료 코드 2로 걸러진다. 위 표와 "판정 산출"의 이모지 대응표가 SSoT이며, 어느 표든 고치면 헬퍼와 `tests/`의 기대값을 함께 갱신한다.

1단계 미충족(FAIL)·부분 충족(PARTIAL)은 이 매트릭스 대상이 아니다. 스펙 미충족은 등급과 무관하게 우선 처리한다 (`issue-work` `--response`의 순서 게이트).

#### 등급별 기본 처리 기준

| 등급 | 기본 처리 |
|------|-----------|
| 높음(HIGH) | 보정 필수 → 재검증 대상 |
| 중간(MEDIUM) | `--response` 승인 게이트에서 사용자 판단 |
| 낮음(LOW) | 원장(`.ai/70_ledger/`) 이관 — 수용 사유·재검토 조건 기재. 사용자가 명시 승격하지 않는 한 보정 루프에 넣지 않는다 |
| 정보(INFO) | 기록만 — 리포트에 남기고 원장 등재는 선택 |

같은 헬퍼의 `--treatment` 모드가 이 표를 조회한다.

```bash
"$classify" --treatment '🟢 낮음(LOW)'   # → 원장(`.ai/70_ledger/`) 이관 — 수용 사유·재검토 조건 기재…
```

이 모드는 이모지 접두가 붙은 등급도 받는다. 매트릭스 헬퍼 출력을 그대로 되넘길 수 있으며, 출력은 위 표의 처리 문구 그대로라 이모지가 붙지 않는다.

등급은 `issue-work` `--response` 승인 게이트의 **기본 제시값**을 정할 뿐이며, 실행은 여전히 항목별 승인 후다. 리포트를 받자마자 자동 보정하지 않는다.

재감사의 신규 발견에도 같은 등급별 기본 처리 기준을 적용한다. 낮음(LOW)·정보(INFO)급이 보정 루프를 되살리지 않아 재검증이 수렴한다.

#### 발견 기록 규칙

- **기등재 대조 (번호 부여 전)** — 대조 대상은 원장 `active/`(`.ai/70_ledger/active/`)의 `수용` 상태 항목뿐이다.
  발견이 그 항목과 같은 결함을 가리키면 신규 발견으로 보고하지 않는다.
  `F-` 번호를 부여하지 않고 리포트의 `### 기등재 참조 항목` 섹션에 `기등재 K-<번호> 참조`로 적으며, 2단계 위험도 집계에서 제외한다.
  발견 사항 표가 곧 집계 대상이라 표 안에 두면 집계가 오염되고 번호까지 소비된다.
  - **재제기 조건** — 그 항목의 `재검토 조건`이 충족된 경우에만 신규 발견으로 다시 올리고, 계보에 `기등재 K-<번호> 재제기`와 충족 근거를 함께 적는다.
    조건이 충족되지 않았다는 판단은 감사인의 위험도 재평가로 뒤집지 않는다. 뒤집을 수 있으면 원장이 반복 보고를 막지 못한다.
    위험도가 등재 시점보다 높아 보이면 재제기 대신 기등재 참조 섹션에 위험도 재평가 의견을 적어 원장 갱신을 권고한다.
  - `active/` 항목의 원인이 이미 사라졌거나 조건 서술이 낡아 실제 구현과 어긋나면(= 원장이 낡음), 발견으로 재보고하지 않고 같은 섹션에 그 사실을 적어 원장 갱신을 권고한다.
  - **`archive/해소` 항목의 재발은 신규 발견이다**. 원인이 사라졌던 결함이 다시 나타난 회귀이므로 억제하지 않고,
    신규 발견으로 `F-` 번호를 부여하고 위험도 집계에 넣으며 계보에 `K-<번호> 재발`을 적는다.
    한 번 청산한 항목까지 억제하면 회귀가 집계에서 사라져 후속 `--response` 게이트의 처리 대상에서 누락된다.
  - **`archive/승격` 항목은 기본이 참조다**. 승격은 원인이 사라진 상태가 아니라 추적처를 이슈로 옮긴 상태다.
    같은 결함을 발견하면 기본값으로 `### 기등재 참조 항목` 섹션에 `기등재 K-<번호> 승격(이슈 #N) 참조`로 적고 위험도 집계에서 제외한다.
    이슈가 살아 있는 동안 매 감사가 신규 발견으로 다시 올리면 추적처를 옮겼을 뿐인데 반복 보고가 되살아난다.
    연결된 이슈가 **닫힌 것이 확인될 때만** `해소` 재발과 같게 신규 발견(`K-<번호> 재발`)으로 올린다. 닫힌 이슈는 추적처가 사라졌다는 뜻이다.
    이슈 상태를 확인할 수단이 없으면 참조 처리를 유지한다. 감사는 GitHub 조회 없이도 성립해야 하므로 확인 실패를 재발 판정으로 바꾸지 않는다.
- **발견 번호 계승** — 발견 번호(`F-n`)는 이슈 단위로 이어 붙인다. 재감사에서 `F-1`부터 다시 시작하지 않고,
  다음 번호는 "보존된 모든 리포트의 발견 번호와 리포트 머리말에 명시된 번호 기준선 중 최대값 + 1"로 정한다.
  번호를 매번 새로 매기면 잔여분이 새 문제처럼 보인다.
  기준선 값의 의미는 **마지막 사용·예약 번호**다. 계산식이 기준선에 다시 + 1을 하므로,
  기준선에 다음 번호를 적으면 첫 신규 발견이 한 번호를 건너뛴다.
  - 직전 회차가 발견 0건이어도 그 이전 회차까지의 최대 번호를 유지해 이어 붙인다.
    예: 최대 번호가 F-12인 상태에서 한 회차가 발견 0건이면, 다음 회차의 첫 신규 발견은 건너뜀 없이 F-13이다.
  - 이전 회차들이 회차마다 번호를 재사용했으면(구버전 이력) 재사용 번호를 전부 포함하는 마지막 사용·예약 번호를
    리포트 머리말의 번호 기준선 줄에 근거와 함께 1회 기록한다. 이후 회차는 그 기준선을 계승한다.
    예: 구버전 회차들이 F-1~F-12를 재사용했으면 기준선을 F-12로 기록하고, 첫 신규 발견은 F-13이 된다.
  - **산출은 헬퍼로 한다** — 보존된 리포트를 전부 인자로 넘기면 다음 번호가 나온다. 손으로 세면 번호를 건너뛰거나 재사용하기 쉽다.

    ```bash
    # <skill 디렉토리>는 이 SKILL.md가 있는 디렉토리. 실행 시 실제 경로로 바꿔 쓴다.
    next='<skill 디렉토리>/scripts/next-finding-number.sh'

    # 보존된 리포트를 전부 넘긴다. 리포트가 아직 없으면 인자 없이 호출해 1 을 받는다.
    "$next" .ai/99_workspace/issue-<번호>-audit-report*.md
    ```

    읽을 수 없는 경로는 종료 코드 2로 걸러진다. 경로 오타를 초회 감사(1)로 오인하면 이미 쌓인 번호를 통째로 재사용하게 되기 때문이다.
- **계보 표기** — 발견마다 계보를 표기한다: 신규 / `F-n` 잔여(이전 발견의 미해소 부분) / `F-n` 재발(닫혔던 발견의 재등장) /
  `기등재 K-n 재제기`(원장 `active/` 항목의 재검토 조건 충족) / `K-n 재발`(원장 `archive/해소` 항목, 또는 연결 이슈가 닫힌 `archive/승격` 항목과 같은 결함이 재등장).
- **발견별 완료 기준** — 권장 조치는 검증 가능한 완료 기준 항목으로 쪼개 적는다.
  다음 감사는 이 항목 단위로 닫힘/잔여를 판정한다. 한 발견을 큰 덩어리로 두면 일부만 고쳐도 완료처럼 보인다.
- **이전 발견 추적** — 재감사에서는 이전 리포트의 모든 발견을 완료 기준 항목 단위로 닫힘/잔여 판정해 표로 남긴다.

### 3단계: 결과 기록

1. 이 skill 디렉토리의 `templates/issue-audit-report-template.md`를 참조하여 감사 리포트를 작성한다.
   결론이 먼저 보이는 역피라미드 구조이며, **판정 한 줄과 요약은 1·2단계를 모두 마친 뒤 맨 위에 작성한다**.
   기록 순서는 판정 한 줄 → 종합 의견 접기 → 요약 → 1단계 → 2단계다. 상태·판정 값은 아래 "상태 산출"·"판정 산출"로 얻는다.
   - **판정 한 줄**: `## 종합 의견` 헤더 바로 아래 첫 줄에 `--verdict` 출력을 그대로 적는다.
   - **종합 의견**: 판정을 뺀 종합 판단·후속 액션은 `종합 의견 펼치기` 접기로 내린다.
   - **상태·등급 표기 위치**: 아래 네 곳에 헬퍼 출력을 그대로 쓴다. 감사인이 값을 고르거나 이모지를 손으로 붙이지 않는다.
     - 요약 `1단계 적합성` 줄: 항목 판정 전부를 넘긴 `--compliance` 출력 + ` · ` + 텍스트 건수
     - 요약 `2단계 위험도` 줄: 발견 등급 전부를 넘긴 `--status` 출력 + ` · ` + 텍스트 건수
     - 1단계 요구사항 대조·DoD 대조 표의 판정 열: 값 하나를 넘긴 `--compliance` 출력
     - 2단계 발견 사항 표의 위험도 열과 상세 분석의 `- **위험도**:` 필드: 매트릭스 헬퍼(`--impact`·`--likelihood`) 출력
   - **건수 표기**: 요약 줄의 건수와 카테고리 표 건수는 이모지 없이 텍스트 등급만 쓴다. 색이 반복되면 상태·판정의 신호가 묻힌다.
   - **발견 헤더**: `#### F-<번호>: <제목>` 형식은 바꾸지 않는다. 등급 신호는 위험도 필드가 맡는다.
2. 리포트를 `.ai/99_workspace/issue-<번호>-audit-report.md`에 저장한다. 같은 경로에 이전 회차 리포트가 있으면
   덮어쓰기 전에 `issue-<번호>-audit-report-<직전 회차>.md`로 이름을 바꿔 보존한다. 최신 리포트는 항상 기본 경로에 있고,
   이전 회차의 상세 근거는 유실되지 않는다.
   archive 이슈를 재감사할 때는 `.ai/90_issues/archive/issue-<번호>/`에 이관된 최신 리포트(`issue-<번호>-audit-report.md`)도
   새 리포트 작성 전에 같은 규칙으로 회전한다. workspace 경로만 확인하면 archive의 최신 리포트가 기본 이름 그대로 남아,
   다음 이슈 정리(issue-work `--clear`)의 이관이 그 동명 파일과 충돌하거나 덮어써 이전 회차가 유실된다.
3. 사용자에게 주요 발견 사항을 요약 보고한다. 대화창 보고도 리포트와 같은 판정 한 줄로 시작한다. 그 밖의 대화창 출력 형식은 정하지 않는다.
4. 감사에 사용한 모델은 **"벤더, 모델명" 형식**으로 기록한다 (예: `OpenAI, GPT-5.x` / `Google, Gemini 3.x`). 이는 `issue-work`의 summary 모델 기록과 **동일한 형식**이며, 리포트 머리말의 '감사 모델' 줄도 이 형식을 따른다.

#### 상태 산출

요약의 1단계 상태와 2단계 상태는 감사인이 직접 고르지 않고 **항목 판정·위험도의 최고값으로 산출**한다.
등급 산출과 같은 철학으로, 같은 감사 결과에 회차마다 다른 상태가 붙지 않게 한다.

**1단계 상태** — 요구사항 대조·DoD 대조 항목의 판정 값을 그대로 상태 값으로 쓴다. 서열은 미충족(FAIL) > 부분 충족(PARTIAL) > 충족(PASS)이며,
판정 불가(N/A)는 상태를 올리지 않아 항목 전부가 판정 불가일 때만 판정 불가(N/A)가 나온다.

같은 헬퍼의 `--compliance` 모드로 산출한다. 값 하나를 넘기면 그 항목의 판정 라벨이 나오고, 항목 판정 전부를 넘기면 1단계 상태가 나온다.

```bash
"$classify" --compliance '부분 충족(PARTIAL)'   # → 🟡 부분 충족(PARTIAL) (항목 라벨)
"$classify" --compliance '충족(PASS)' '부분 충족(PARTIAL)' '충족(PASS)'   # → 🟡 부분 충족(PARTIAL) (1단계 상태)
```

인자 0개는 사용오류다. 요구사항·DoD 대조는 항상 수행하므로 1단계 항목이 0개인 감사는 성립하지 않는다.

**2단계 상태** — 발견 사항 위험도의 최고값으로 산출한다.

| 최고 위험도 | 상태 |
|-------------|------|
| 높음(HIGH) | 보완 필요(FAIL) |
| 중간(MEDIUM) | 주의(WARN) |
| 낮음(LOW) 이하 또는 발견 없음 | 통과(PASS) |

같은 헬퍼의 `--status` 모드로 산출한다. 위험도 목록을 넘기면 최고값 기준 상태가 나오고, 인자가 없으면 발견 없음으로 보고 통과(PASS)를 낸다.

```bash
"$classify" --status '🟡 중간(MEDIUM)' '낮음(LOW)'   # → 🟡 주의(WARN)
"$classify" --status                                  # 발견 없음 → 🟢 통과(PASS)
```

낮음(LOW)·정보(INFO)는 등급별 기본 처리가 이관·기록이라 상태를 낮추지 않는다. 건수는 요약 줄에 그대로 드러난다.

#### 판정 산출

리포트 `## 종합 의견` 첫 줄의 판정은 감사인이 고르지 않고 **1단계 상태와 2단계 상태 2개의 최고값**으로 산출한다.
등급·상태 산출과 같은 철학으로, 같은 감사 결과에 회차마다 다른 판정이 붙지 않게 한다.

| 최고 상태 | 판정 |
|-----------|------|
| 미충족(FAIL) · 보완 필요(FAIL) | 부적합(FAIL) |
| 부분 충족(PARTIAL) · 주의(WARN) | 조건부 적합(CONDITIONAL) |
| 충족(PASS) · 판정 불가(N/A) · 통과(PASS) | 적합(PASS) |

판정 불가(N/A)는 판정에 영향을 주지 않는다. 최하위 서열이라 다른 값이 있으면 묻히고, 1단계가 전부 판정 불가여도 2단계 상태가 판정을 정한다.

같은 헬퍼의 `--verdict` 모드로 산출한다. 1단계 상태와 2단계 상태를 위치 인자 2개로 넘기며 순서는 무관하다.

```bash
"$classify" --verdict '🟡 부분 충족(PARTIAL)' '🟡 주의(WARN)'   # → 🟡 조건부 적합(CONDITIONAL)
```

판정 3종의 의미는 아래와 같다.

- **🔴 부적합(FAIL)**: 스펙 요구사항·DoD를 충족하지 못한 항목이 있거나, 보정이 필수인 높음(HIGH) 발견이 있다.
- **🟡 조건부 적합(CONDITIONAL)**: `issue-work` `--response` 승인 게이트에서 사용자 판단이 필요한 항목이 있다.
- **🟢 적합(PASS)**: 보정 대상이 없어 Task N(교차모델 검증)을 닫을 수 있다. 낮음(LOW)·정보(INFO) 발견은 등급별 기본 처리대로 원장 이관·기록으로 처리한다.

판정은 우선순위 신호이며, 실제 처리는 현행대로 `issue-work` `--response`의 항목별 승인이 정한다. 판정이 보정을 자동으로 실행시키지 않는다.

**이모지 대응표**

| 구분 | 값 | 이모지 |
|------|----|--------|
| 적합성 | 충족(PASS) | 🟢 |
| 적합성 | 미충족(FAIL) | 🔴 |
| 적합성 | 부분 충족(PARTIAL) | 🟡 |
| 적합성 | 판정 불가(N/A) | ⚪ |
| 등급 | 높음(HIGH) | 🔴 |
| 등급 | 중간(MEDIUM) | 🟡 |
| 등급 | 낮음(LOW) | 🟢 |
| 등급 | 정보(INFO) | ⚪ |
| 상태 | 보완 필요(FAIL) | 🔴 |
| 상태 | 주의(WARN) | 🟡 |
| 상태 | 통과(PASS) | 🟢 |
| 판정 | 부적합(FAIL) | 🔴 |
| 판정 | 조건부 적합(CONDITIONAL) | 🟡 |
| 판정 | 적합(PASS) | 🟢 |

이모지는 헬퍼가 등급·상태·판정 출력 앞에 붙이며 감사인이 손으로 붙이지 않는다.
항목의 색은 그 항목이 만드는 상태의 색과 같다. 부분 충족(PARTIAL)이 🟡인 것도 그것이 만드는 상태가 조건부 적합(CONDITIONAL)이기 때문이며,
`--response` 순서 게이트가 미충족(FAIL)과 부분 충족(PARTIAL)을 함께 선처리하는 것은 처리 순서 규칙이라 색과 무관하다.
정보(INFO)·판정 불가(N/A)는 상태를 올리지 않으므로 무색(⚪)이다.
요약 줄의 건수와 카테고리 표 건수는 이모지 없이 텍스트 등급만 쓴다.
값 모드 4종(`--treatment`·`--compliance`·`--status`·`--verdict`)은 대응표 접두 4종이 붙은 값과 붙지 않은 값을 모두 받으므로 헬퍼 출력을 그대로 되넘길 수 있다. 그 밖의 접두는 종료 코드 2다.
위험도 매트릭스·등급별 기본 처리 기준·2단계 상태 표·판정 표의 셀 값은 텍스트로 유지한다. 논리 표와 표시 규칙을 분리해 이모지의 SSoT를 이 대응표 한 곳에 둔다.

## 산출물 접기 기준

산출물의 상세 내용은 `<details>` 접기로 분량을 줄이되, 아래 기준을 따릅니다.

- **접기 가능**: 근거·대안 비교·상세 절차·코드 예시·참고자료
- **접기 금지**: 결정사항·리스크·액션 아이템
- **종합 의견 접기**: 판정 한 줄을 뺀 종합 판단·후속 액션은 접는다. 판정 한 줄이 접기 밖에 있고 발견 제목·권장 조치가 본문에 그대로 남으므로 "액션 아이템 접기 금지"와 충돌하지 않는다.

`.ai/10_rules/writing-principles.md`가 있으면 그 원칙을 따르고, repo 고유 확장 `writing-principles-local.md`와 충돌하면 local이 우선합니다. 이 블록은 파일이 없을 때의 기본값입니다.
