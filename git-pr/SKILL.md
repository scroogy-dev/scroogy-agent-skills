## 개요

동료의 코드 리뷰 시간을 단축하고, 변경 사항에 대한 완벽한 추적성을 제공하는 PR 메시지를 작성합니다.
이슈·브랜치·PR이 각각 1개인 단일 배포이든, 여러 브랜치를 하나의 PR로 통합하는 통합 배포이든,
PR에 포함된 **각 이슈별로** 반드시 '비즈니스 관점'과 '테크 관점' 두 섹션으로 나누어 작성합니다.

메시지 작성에서 끝나지 않고, PR 유형(정식/드래프트(draft)) 확인과 메시지 승인 게이트를 거쳐 해당 유형의 PR을 생성합니다 ("PR 제출").
제출은 외부 공개 행위이므로 **승인 게이트는 유형·옵션과 무관하게 생략하지 않습니다** — 승인을 거절하면 제출 없이 최종 제목·본문만 남습니다.
유형이 이미 정해졌으면 `--draft`로 유형 확인만 건너뛸 수 있습니다 ("옵션").

## 관련 skill

- git-commit (권장): PR 제목은 커밋 메시지와 동일한 Conventional Commits 형식을 따릅니다.
- ai-workspace (권장): `.ai/50_adr/`, `.ai/30_contract/`, `.ai/40_domain/` 경로의 문서를 참조합니다.

- **스킬 고유 추가 참조**:
  - `.ai/30_contract/index.md`, `.ai/40_domain/index.md`, `.ai/50_adr/index.md` — 비즈니스·테크 관점 참고사항 작성 및 인용할 파일 식별용 (index 먼저 → 관련 파일만 선택적으로)

## 작성 시점 및 주체

PR을 올리기 전, 작성자 본인이 작성합니다.
AI 도구를 활용해 초안을 생성한 뒤 작성자가 검토·수정하여 반영하는 방식을 권장합니다.

## 실행 절차

아래 순서로 작성합니다. 각 단계의 세부 규칙은 같은 이름의 섹션을 참조합니다.

1. 공통 규칙·`index.md`를 선택 적재한다 ("참조 문서").
2. PR 유형(정식/드래프트)을 확인한다 ("PR 제출").
3. PR 제목을 작성한다 ("PR 제목").
4. 이슈 목록을 작성한다 ("PR 메시지 구조").
5. 이슈별로 비즈니스 관점·테크 관점을 작성한다.
6. PR 초안을 마친 뒤 마지막 패스로 문서 동기화 점검을 1회 수행한다 ("문서 동기화 점검").
7. 최종 제목·본문·대상을 제시하고 승인받은 뒤 해당 유형으로 PR을 생성한다 ("PR 제출").

## PR 제출

메시지 작성에서 끝내지 않고, 유형 확인과 승인 게이트를 거쳐 PR을 실제로 생성합니다.

### 1. PR 유형 확인 (메시지 작성 전)

- 메시지를 쓰기 전에 **정식 PR / 드래프트 PR** 중 어느 유형으로 올릴지 작성자에게 질의합니다. **기본값은 정식 PR**이며, 기본값을 그대로 쓸 때에도 작성자의 확인 응답을 받습니다.
- `--draft` 옵션으로 실행했으면 이 질의만 생략하고 드래프트로 확정합니다 ("옵션").
- 베이스 브랜치는 원격 기본 브랜치(`main` 등)를 자동 감지해 채웁니다. 감지에 실패한 경우에만 작성자에게 질의합니다.
- 소스 브랜치가 베이스와 **같은 저장소**에 있는지 이 단계에서 확인합니다. 대조는 `gh` 없이도 동작하도록 git 원격 URL로 합니다 — 베이스 저장소는 기본 브랜치를 감지한 원격의 URL, 소스 저장소는 `git config branch.<브랜치>.remote`로 조회한 원격의 URL을 `호스트/소유자/저장소` 형태로 정규화해 비교합니다.
  - upstream이 없는 브랜치(첫 push 전 새 브랜치)는 다른 저장소로 간주하지 않습니다 — 3단계에서 push 대상 원격이 확정되면 그 원격의 URL로 이 대조를 수행합니다.
  - 어느 쪽도 판정할 수 없으면 같은 저장소가 맞는지 작성자에게 질의해 분기합니다.
  - 저장소가 다르면(포크에서 올리는 경우) **포크 기반 제출은 지원하지 않습니다** — 그 사실을 먼저 알리고, 메시지 작성만 이어갈지 질의해 승인하면 제출 없이 최종 제목·본문만 남기고 종료합니다.

### 2. 메시지 작성

- **기준 리비전을 먼저 고정합니다.** 메시지를 쓰기 전에 작업트리 상태(`git status --porcelain`)를 확인하고 소스 브랜치의 현재 커밋 SHA를 기준으로 잡습니다. 제목·이슈 목록·본문·문서 동기화 점검은 모두 이 기준(`<베이스>...<소스 SHA>`) 안의 커밋·diff만 읽습니다.
- 미커밋 변경(staged·unstaged·untracked)이 있으면 그 사실을 알리고 **커밋한 뒤 진행 / 미커밋 변경을 제외하고 진행** 중 어느 쪽인지 작성자에게 확인받습니다 — 미커밋 변경까지 읽고 쓰면 PR 본문이 실제로 게시되는 변경보다 앞서고, 반대로 작성자가 포함하려던 변경이 조용히 누락됩니다.
- 기준 SHA가 바뀌면(추가 커밋·amend·리베이스) 이 단계부터 다시 수행합니다. 3단계에서 승인받는 커밋 SHA는 여기서 고정한 값과 같아야 합니다.
- 위를 지킨 뒤 "PR 제목" → "PR 메시지 구조" → "문서 동기화 점검" 순으로 기존 절차를 수행합니다.

### 3. 최종 제시 및 승인 (생략 불가)

- 제출 직전에 아래를 그대로 제시하고 작성자의 승인을 받습니다.
  - 최종 PR 제목
  - 최종 PR 본문
  - 제출 대상 — 대상 저장소(`[호스트/]소유자/저장소`), 베이스 브랜치, 소스 브랜치와 그 커밋 SHA·원격 동기화 상태(미게시 / 일치 / 로컬 앞섬 / 분기), PR 유형(정식/드래프트)
- 대상 저장소는 1단계에서 정규화한 값을 그대로 제시합니다 (판정을 미룬 새 브랜치는 아래에서 push 대상 원격이 확정된 뒤 정규화합니다). 제시하지 않으면 로컬 `gh` 컨텍스트나 `GH_REPO` 환경변수가 실행 시점에 저장소를 고르게 되어, 작성자가 승인한 대상과 실제 PR이 올라가는 저장소가 어긋날 수 있습니다.
- 원격 head가 소스 브랜치의 로컬 커밋과 다르면(미게시·로컬 앞섬) **push 여부와 대상 원격**도 승인 대상에 포함해 이 단계에서 확정합니다 — 원격 ref가 있어도 로컬이 앞서 있으면 push 없이는 낡은 커밋으로 PR이 만들어지기 때문입니다. 실제 push는 4단계에서 수행합니다. 1단계에서 판정을 미룬 새 브랜치는 이때 확정된 push 대상 원격으로 같은 저장소 대조를 마칩니다. `gh`가 push 위치·fork 생성을 대화형으로 되물으면 비대화형 실행이 멈춥니다.
- 승인받은 **대상 저장소와 커밋 SHA는 불변 값으로 보관**해 4단계 검증에 그대로 씁니다 — 실행 시점에 다시 조회한 값으로 대체하면, 승인 후 브랜치가 이동해도 새 커밋끼리 비교되어 검증이 그대로 통과합니다.
- **승인 게이트는 유형·옵션과 무관하게 생략할 수 없습니다.** PR 생성은 외부 공개 행위이므로 `--draft`로 실행했더라도 승인 없이 제출하지 않습니다.
- 작성자가 베이스 브랜치·유형 변경을 요청하면 반영한 뒤 다시 제시합니다. 통합 배포처럼 대상이 기본 브랜치와 다른 경우도 이 단계에서 교정합니다.
  베이스·소스 브랜치가 바뀌면 포함 커밋이 달라지므로, 새 diff 기준으로 이슈 목록·메시지·문서 동기화 점검을 다시 수행한 뒤 제시합니다.
- 작성자가 거절하면 제출하지 않고 종료합니다 — 제시한 제목·본문은 그대로 남으므로, 텍스트만 필요할 때는 이 경로를 씁니다.

### 4. PR 생성

- 승인받은 유형으로 PR을 생성합니다.
- **승인한 대상 저장소 재확인이 먼저입니다.** 외부에 쓰기(push·PR 생성) 전에 승인한 원격 이름의 현재 URL을 1단계와 같은 방식으로 정규화해 승인받은 대상 저장소와 같은지 확인합니다 — 원격 이름은 URL을 가리키는 가변 별칭이라, 승인 후 `remote.<이름>.url`이 바뀌면 승인한 소스가 다른 저장소로 게시됩니다. 뒤늦게 PR 생성을 막아도 이미 게시된 코드는 되돌릴 수 없습니다.
  검증도 push도 원격 이름으로 수행하고 URL을 push 대상으로 직접 쓰지는 않습니다 — `git push -u <URL>`은 `branch.<브랜치>.remote`에 URL을 기록하면서 remote-tracking ref를 만들지 않아, 이후 `@{u}` 해석이 깨집니다.
- **승인한 SHA 재확인이 그다음입니다.** 소스 브랜치의 현재 SHA가 3단계에서 승인받은 SHA와 같은지 확인합니다 — 승인과 생성 사이에 작성자나 다른 에이전트가 브랜치를 갱신하면, 제목·본문은 승인됐어도 검토하지 않은 커밋 집합으로 PR이 만들어집니다.
- **소스 브랜치 게시가 그다음입니다.** 3단계에서 push를 승인받았으면 PR 생성 전에 승인한 원격으로 push하고, 원격 head가 승인한 SHA와 **같은 SHA**인지 확인한 뒤에 생성으로 넘어갑니다 — ref 존재만 확인하면 로컬이 앞선 낡은 원격 브랜치로 PR이 만들어질 수 있습니다. `--head`를 쓰면 `gh`는 push와 포크 생성을 건너뛰므로, 원격에 브랜치가 없으면 생성이 실패합니다.

  ```bash
  git remote get-url '<승인한 원격>'                                       # 정규화값이 승인한 대상 저장소와 같을 때만 진행
  git rev-parse 'refs/heads/<승인한 소스 브랜치>'                          # 승인한 SHA와 같을 때만 push 진행
  git push -u '<승인한 원격>' '<승인한 소스 브랜치>'
  git ls-remote --heads '<승인한 원격>' 'refs/heads/<승인한 소스 브랜치>'  # 승인한 SHA와 같을 때만 생성 진행
  ```

- push를 승인받지 않은 경우(3단계 상태가 "일치")에도 원격 SHA 확인은 그대로 수행합니다 — 위 예시에서 `git push` 한 줄만 건너뜁니다.
- 로컬·원격 조회는 모두 **완전한 ref 이름**(`refs/heads/<브랜치>`)으로 하고, `ls-remote` 출력이 정확히 1행인지 확인합니다 — `ls-remote`의 ref 인자는 tail 패턴이라 `main`으로 조회하면 `refs/heads/feature/main`까지 함께 반환되고, 첫 행을 택하면 낡은 `main`이 다른 ref의 SHA로 검증을 통과합니다.
- 두 값 중 하나라도 승인한 SHA와 다르거나, 원격이 분기해 강제 push가 필요한 상태면 자동으로 처리하지 않습니다 — 생성을 중단하고 상태를 알린 뒤 별도 승인을 받습니다.
- **`ls-remote` 확인과 생성 명령 사이에는 다른 동작을 끼우지 않습니다.** 생성 명령은 SHA가 아니라 `--head <브랜치>`가 가리키는 그 시점의 원격 ref를 쓰므로, 확인과 생성이 벌어지면 그 사이의 원격 갱신이 앞선 SHA 검증을 그대로 우회합니다.

- 생성 수단은 `gh` CLI를 기본으로 하고, `gh`가 없거나 인증되지 않았으면 GitHub MCP `create_pull_request`로 폴백합니다. 둘 다 쓸 수 없으면 그 사실을 알리고 최종 제목·본문을 남긴 채 종료합니다.

  ```bash
  # 정식 PR — 제목·본문은 파일로, 나머지 값은 작은따옴표로 전달
  gh pr create --repo '<승인한 대상 저장소>' --base '<베이스 브랜치>' --head '<승인한 소스 브랜치>' \
    --title "$(cat '<제목 파일>')" --body-file '<본문 파일>'

  # 드래프트 PR
  gh pr create --draft --repo '<승인한 대상 저장소>' --base '<베이스 브랜치>' --head '<승인한 소스 브랜치>' \
    --title "$(cat '<제목 파일>')" --body-file '<본문 파일>'
  ```

- **승인받은 값을 명령 문자열에 그대로 보간하지 않습니다.** 제목이나 브랜치명에 `$(...)`·백틱이 있으면 큰따옴표 안에서 셸 명령 치환이 실행되어, 승인 화면에 보인 값과 실제 전달되는 인자가 달라집니다.
  - 제목은 본문과 함께 파일로 저장하고 `--title "$(cat '<제목 파일>')"`로 전달합니다 — 명령 치환의 **결과**는 셸이 다시 해석하지 않으므로 승인받은 값이 그대로 보존됩니다.
  - 대상 저장소, 베이스·소스 브랜치, 원격 이름, 파일 경로는 작은따옴표로 감쌉니다. 작은따옴표 안에서는 `$`·백틱이 해석되지 않습니다.
  - 값 자체에 작은따옴표가 들어 있으면 그 자리만 `'\''`로 바꿔 감쌉니다 (예: 브랜치 `feat'quoted` → `'feat'\''quoted'`). 이 인코딩은 POSIX 셸에서 동일하게 동작하므로 값의 종류와 무관하게 결정적이며, 이 경우에도 MCP로 전환하지 않고 위 명령을 그대로 씁니다.
- `--repo`·`--head`는 생략하지 않습니다 — `--repo`를 생략하면 로컬 `gh` 컨텍스트나 `GH_REPO` 환경변수가 저장소를 고르고, `--head`를 생략하면 실행 시점의 현재 브랜치가 쓰여 각각 승인받은 대상과 어긋날 수 있습니다. `--repo`에는 승인받은 `[호스트/]소유자/저장소`를 넣고, 생성 직전에 그 값이 같은 저장소 판정에 쓴 원격 URL과 여전히 일치하는지 재검증합니다.
- GitHub MCP로 폴백할 때는 `create_pull_request`에 `owner`·`repo`(승인받은 대상 저장소), `base`·`head`(승인받은 베이스·소스 브랜치), `title`·`body`(승인받은 제목·본문), `draft`(승인받은 유형)를 **모두 승인값으로 명시**합니다. MCP는 구조화된 인자로 값을 넘기므로 셸 보간 문제가 없습니다.
- MCP 폴백은 대상 저장소가 `github.com`일 때로 **한정**합니다. `create_pull_request`는 `owner`·`repo`만 받고 host 인자가 없어, MCP 연결이 어느 host를 가리키는지 호출 쪽에서 지정·확인할 수 없습니다. 승인받은 대상이 다른 host로 한정된 값(`<호스트>/<소유자>/<저장소>`)이면 폴백하지 않고 그 사실을 알린 뒤 최종 제목·본문을 남기고 종료합니다 — 같은 `소유자/저장소`가 여러 host에 존재하면 승인하지 않은 host에 PR과 그 제목·본문이 공개될 수 있습니다.
- MCP 폴백은 **PR 생성 단계만 대체**합니다 — 선행 `git push`·`git ls-remote`는 대체하지 못하므로, 원격 게시와 ref·SHA 검증을 셸에서 끝낸 뒤에 폴백으로 넘어갑니다.
- **생성 후 head SHA를 대조합니다.** 생성된 PR의 head SHA가 승인한 SHA와 같은지 확인합니다 — 검증과 생성 사이에 다른 작성자·에이전트가 같은 원격 브랜치를 갱신했다면 승인하지 않은 커밋으로 PR이 만들어져 있습니다.

  ```bash
  gh pr view '<PR 번호>' --repo '<승인한 대상 저장소>' --json headRefOid --jq .headRefOid
  ```

  다르면 자동으로 되돌리지 않습니다 — PR 번호·URL과 불일치 사실을 알리고 후속 처리(드래프트 전환·닫기 등)는 별도 승인을 받습니다.
- 생성 후 PR 번호와 URL을 작성자에게 보고합니다.

## PR 제목

PR 제목은 [Conventional Commits 1.0.0](https://www.conventionalcommits.org/ko/v1.0.0/) 형식을 따릅니다.
Squash Merge 시 PR 제목이 커밋 메시지로 사용되므로 형식을 일치시켜 이력의 일관성을 유지합니다.

```
<type>(<scope>): <제목> (#이슈번호)
```

### 단일 배포 (이슈 1 : 브랜치 1 : PR 1)

이슈 번호와 scope를 그대로 사용합니다.

```
feat(order): 주문 생성 API 성능 개선 (#123)
fix(payment): 결제 실패 시 사용자 알림 누락 수정 (#124)
```

### 통합 배포 ((이슈 1 : 브랜치 1) × N : PR 1)

포함된 모든 이슈 번호를 나열합니다. scope가 단일 도메인으로 수렴하면 scope를 명시하고, 여러 도메인에 걸쳐 있으면 scope를 생략합니다.

```
# scope가 하나의 도메인으로 수렴하는 경우
feat(order): 주문 성능 개선 및 결제 알림 추가 (#123, #124)

# scope가 여러 도메인에 걸쳐 있는 경우
feat: 3월 1차 배포 - 주문 성능 개선, 결제 알림 (#123, #124)
```

### [PR 헤더] 이슈 목록

PR에 포함된 이슈를 한눈에 파악할 수 있도록 상단에 목록으로 정리합니다.

### Issue: #[이슈번호] - [이슈 제목 또는 핵심 요구사항]

이슈가 여러 개인 경우 아래 섹션을 이슈마다 반복합니다.
이슈별 비즈니스·테크 관점 상세는 `<details>`로 감싸 접습니다 ("산출물 접기 기준" 참조) — PR 헤더(이슈 목록)와 이슈 헤더는 본문에 유지합니다. 접기 구조는 아래 "작성 예시"를 따릅니다.

#### 1. 비즈니스 관점

리뷰어가 "이 코드가 왜 필요한가?"를 이해할 수 있도록 비즈니스 목적과 영향을 요약합니다.

* **목적 및 요약:** 이 이슈가 해결하고자 하는 비즈니스 요구사항, 버그, 또는 사용자 가치를 명확히 기재합니다. (무엇을, 왜 변경했는가?)
* **주요 변경 사항:** 사용자 경험이나 정책 등 비즈니스 관점에서 어떤 변화가 발생했는지 2~3개의 불릿 포인트로 작성합니다.
* **참고사항:** 관련된 기획 문서, 비즈니스 룰, 또는 인증 심사(컴플라이언스)와 관련된 필수 요구사항이 있다면 명시합니다.

#### 2. 테크 관점

리뷰어가 "이 코드가 어떻게 구현되었는가?"를 파악하고 소스 코드를 쉽게 추적할 수 있도록 작성합니다.

* **구현 요약:** 비즈니스 요구사항을 코드로 어떻게 풀어냈는지, 추가/변경/삭제된 핵심 로직 위주로 요약합니다.
* **호출 흐름:**
  - `.ai/60_codebase/index.md`에 내용이 있으면 참고하되, SSoT는 소스코드이므로 반드시 실제 코드를 확인하여 작성합니다.
  - 기능(엔트리 포인트)별로 나누어, 주요 컴포넌트 간의 실행 흐름을 디렉토리 트리 형태의 ASCII 다이어그램으로 도식화합니다.
    - 각 노드에 `ClassName#methodName` 명시, 트리 기호(`├──`, `└──`)로 호출 계층 표현, 핵심 로직은 노드 옆 `# 설명` 주석.
  - 하나의 이슈에 여러 기능이 있으면 기능별로 각각 작성합니다.

  *(예)*
  ```
  - 주문 생성:
    OrderController#create
    ├── OrderValidator#validate        # 필수 필드 및 재고 가용성 검증
    └── OrderService#process           # 주문 생성 트랜잭션 관리
        ├── InventoryService#decrease  # 재고 차감 및 락 획득
        │   └── InventoryRepository#update (DB)
        ├── PaymentService#charge      # 결제 요청 및 실패 시 재고 롤백
        │   └── PgClient#requestPayment (외부 API)
        └── OrderRepository#save (DB)
  ```

* **참고사항:** 구현 시 참고한 아키텍처 결정 기록(ADR), DB 스키마 변경 사항, 사내 가이드, 또는 보안/성능 측면의 특이사항을 명시합니다.
  관련 ADR·계약·도메인 문서가 있으면 해당 파일 경로를 함께 적습니다 (경로 안내는 위 "참조 문서" 참고).

## 문서 동기화 점검 (PR 초안 작성 후)

PR 초안을 마친 뒤 **마지막 패스로 1회** 수행합니다. 브랜치 diff로 README·AI-CONTEXT·코드베이스 색인이 낡았는지 감지해 **갱신 권고만** PR 끝에 덧붙입니다 — 문서 자동 재생성은 하지 않습니다(SSoT는 소스코드). 각 행은 **해당 diff 신호가 있을 때만** 켜지므로, 신호가 없으면 해당 행은 생략하고 감지 항목이 하나도 없으면 이 섹션 자체를 생략합니다.

| diff 신호 | 낡았을 가능성 있는 문서 | 권고 스킬 |
|-----------|--------------------------|-----------|
| 스킬·모듈 디렉토리 추가/삭제/이름변경, 진입 문서(`SKILL.md` 등) description 변경 | README, AI-CONTEXT 목록 | `/readme-sync`, `/ai-workspace` |
| 디렉토리 구조 변경 | AI-CONTEXT 구조 트리 | `/ai-workspace` |
| 호출 흐름·엔트리포인트 변경 | `.ai/60_codebase/` 색인 | `/code-map` |
| `domain`/`keywords` 변경 | AI-CONTEXT + 상위 안내도 `Repos` 행(멀티 워크스페이스) | `/ai-workspace` |

> 위 매핑은 이 저장소(스킬 모음) 기준입니다. 다른 프로젝트에선 README/AI-CONTEXT가 기술하는 대상(모듈·패키지·엔트리포인트)에 맞춰 신호를 대응시킵니다.

권고는 PR 끝에 `## 문서 동기화 점검` 블록으로 남기고 적용 여부는 작성자가 판단합니다 (예: `- AI-CONTEXT 스킬 목록이 낡았을 수 있음 → /ai-workspace`). 권고에 그치지 않고 같은 PR에 갱신까지 포함하려면(승인형), 이 단계에서 해당 스킬(`/readme-sync`·`/ai-workspace`·`/code-map`) 실행 여부를 질의해 승인한 것만 같은 브랜치에 반영합니다.

## 옵션

### `--draft`

PR 유형 확인 질의를 생략하고 드래프트 PR로 확정합니다.

- **용도**: 작업 중간 공유나 조기 리뷰 요청처럼 드래프트로 올릴 것이 이미 정해진 경우에 유형 질의를 줄입니다.
- **동작**: "PR 제출" 1단계의 유형 확인 질의만 생략하고 유형을 드래프트로 고정합니다.
  이후 절차(메시지 작성 → 최종 제시·승인 → 생성)는 기본 동작과 동일합니다.
  **승인 게이트는 이 옵션으로도 생략되지 않습니다** — 최종 제목·본문·제출 대상을 제시하고 승인받은 뒤에 생성합니다.
  최종 제시 단계에서 작성자가 정식 PR로 바꾸도록 요청하면 그에 따릅니다.
