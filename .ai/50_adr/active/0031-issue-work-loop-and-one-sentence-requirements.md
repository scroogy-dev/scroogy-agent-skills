# ADR: 요구사항과 완료의 정의를 한 문장으로 두고 이슈 진행을 계획·검증·구현 루프로 바꾸는 결정

- **상태**: 유효

## 결정

### 이슈 본문과 spec

- 이슈 본문의 포함과 완료의 정의를 같은 묶음 제목으로 나누고 포함 항목을 하위 목록 없는 한 문장으로 쓴다. 등록 때 정한 세부는 `정한 것` 섹션에 둔다 (#145).
- spec 요구사항과 완료의 정의는 이슈 본문의 묶음 제목·문장·AC 번호를 그대로 쓴다. 완료의 정의는 `- [ ] AC<n>: <문장> (R<n>)` 행만 두고 레벨 태그·검증 명령·케이스 목록을 담지 않는다.
  - 모든 AC 행에 R 표기가 있고 포함 R마다 AC가 1개 이상 연결되며 같은 번호의 행은 하나다.
  - 이슈 본문의 AC가 대응하지 않는 R에는 spec이 AC를 다음 번호로 직접 쓰고 6단계가 이슈 본문에 올릴지 묻는다. 거절하면 spec의 AC가 기준이다.
- spec `전제` 섹션을 없앤다. 제품·도메인 결정은 spec `결정 사항`에, 소프트웨어 설계는 plan `설계 결정`에 적는다. 계획 종료 게이트와 Task 0은 남기고 찾은 것을 두 자리에 나눠 적는다.
- spec `변경 이력`에는 승인 뒤에 문장이 바뀐 요구사항·AC·결정의 번호, 분류, 계기를 적는다. 적을 것이 없는 `결정 사항`과 `변경 이력`은 두지 않는다.

### plan과 검증

- plan에 선택 섹션 `설계 결정`을 둔다. 시스템 구성, 다른 시스템과의 연결, 애플리케이션 구조 안의 자리, 영향 모듈·순서의 근거·관례를 적는다. 바꾸는 모듈이 하나이고 구조나 순서에서 고를 것이 없으면 두지 않는다.
- plan에 `테스트 계획`을 두어 AC마다 어느 층의 어느 테스트가 보는지 한 줄 이상 적는다. 단위 테스트를 먼저 고르고 위 층을 쓰면 단위로 못 보는 이유를 적는다.
  - 검증 레벨은 이 표에 둔다. 테스트 표의 줄은 `[D]`, `테스트로 못 보는 항목` 표의 줄은 `[QD]`나 `[ND]`이고 강등 사유는 `이유` 칸이 맡는다.
  - `확인` 칸에 `[D]`·`[QD]` 줄은 AC를 충족으로 판정한 교차 감사의 회차를, `[ND]` 줄은 사용자가 확인한 날짜를 적는다.
- 기능을 바꾸는 Task는 테스트 작성 → 실패 확인 → 테스트 커밋 → 구현 → 통과 확인 → 구현 커밋 순서로 진행한다. 실패 확인은 커밋 순서와 summary `테스트` 필드로 남긴다.
  - 동작을 바꾸지 않는 Task(문서만, 자동 테스트가 보지 못하는 화면 배치, 스파이크, 리팩터링)는 구현 → 통과 확인 두 단계다.
  - 실패 확인이 계획 감사의 가짜 `[D]` 사전 판별과 통과 건수 하한 검사를 대신한다.
- 커밋한 테스트의 기대값 변경·단언 축소·테스트 삭제는 변경 통제의 완화다. 기대값이 처음부터 틀렸던 경우도 같다. 결과는 그대로이고 이름·위치·준비 코드·호출 방식만 바뀌는 수정은 질의 없이 반영한다.

### 루프

- 이슈 진행을 계획 수립 → 계획 검증 → 구현 → 구현 검증 → 완료 확인의 다섯 단계로 두고, 완료 확인에서 사용자가 `다음 회차`로 정하면 계획 수립으로 돌아간다.
- 계획 검증: 계획 감사 수행 여부는 이슈에 한 번 묻는다. 수행으로 정한 이슈는 지난 검증 뒤에 AC·요구사항, `설계 결정`, `테스트 계획` 가운데 하나가 바뀌면 다시 받는다. 6단계(이슈 본문 갱신 질의)나 Task 0에서 바뀐 것도 같으며 일반 Task를 시작하기 전에 받는다. 기존 AC 안에서 발견을 고치는 Task를 더한 것만으로는 받지 않는다.
- 구현 검증: 교차 감사를 Task N에서 이 단계로 옮긴다. 지난 검증 뒤에 구현이 바뀌었으면 전체로 다시 받고, 고친 발견의 위험도에 따른 예외를 두지 않는다.
  - 바뀌었는지는 summary `루프 기록`에 적은 검증 커밋 뒤의 diff로 가린다. 검증 커밋은 감사 리포트 머리말의 `감사 대상 커밋`에서 옮긴다.
  - 감사 전에 감사 대상에 미커밋 변경이 있으면 커밋할지 묻는다. 미커밋 상태로 감사받은 회차는 비교 기준이 없어, 커밋한 대상으로 다시 받을 때까지 바뀐 것으로 본다.
  - spec의 AC나 결정이 더해졌거나 문장이 바뀌면 구현이 그대로여도 다시 받는다. 지난 감사가 그 문장을 판정하지 않았기 때문이다.
- `--response`는 최종 감사 리포트에서 결정만 받고 소스를 고치지 않는다. 반영으로 정한 발견은 다음 회차의 계획 수립에서 plan에 Task로 더하고 재현 테스트를 먼저 쓴 뒤 고친다.
- 완료 확인: 에이전트는 마지막 교차 감사의 1단계 상태 충족, 2단계 상태 통과나 주의, `테스트 계획`의 모든 줄 확인, 반영으로 정한 발견 종결이 모두 맞으면 `마무리`를, 그 밖은 `다음 회차`를 권장한다. 루프를 나갈지는 사용자가 정한다.
  - 기준에 못 미친 채 `마무리`로 정하면 남은 AC와 발견마다 완화·원장 등재·새 이슈 가운데 결정을 받는다.
- Task N은 마무리(전체 회귀, 색인, 충족 AC 체크, repo 고유 마무리, `--clear`, PR)만 맡고 사용자가 `마무리`로 정한 뒤에만 들어간다.
  - `--clear` 1단계는 Task N의 미체크를 미완료로 세지 않고, 루프 기록 마지막 행의 `결정`이 `마무리`인지 본다. Task N의 체크와 `PR 대기` 기록은 4단계가 archive 이관 직전에 한다.
- 같은 종류의 발견이 두 회차 이어지면 다음 회차의 계획 수립이 `설계 결정`부터 고친다. 종류는 `--response`에서 붙여 summary `종류별 발견`에 적는다.
- 더한 Task는 회차 묶음 없이 plan에 이어 붙이고 summary `루프 기록`에 회차마다 한 줄을 적는다.
- PR 뒤의 리뷰 피드백은 git-pr-feedback으로 처리한다. 피드백으로 구현을 고쳤을 때 교차 감사를 다시 받을지는 사용자가 고른다.
- issue-workflow 템플릿에만 다섯 단계를 보이는 아스키 그림을 둔다. 선은 ASCII 문자만 쓴다.

### 연동

- issue-audit 최종 감사의 1단계는 완료의 정의(DoD) 대조와 결정 사항 대조 두 표다. DoD 대조는 `테스트 계획`이 AC마다 가리키는 테스트와 `[D]` 명령을 구현 뒤 트리에서 실행해 판정한다. 2단계 발견이 `결정 사항`의 결정을 어기면 1단계 판정을 낮추는 근거로 본다.
- issue-audit `--plan`의 1단계는 요구사항 대조와 DoD 대조 두 표이고, 관점 2는 테스트 계획의 층 선택과 못 보는 항목의 이유를 본다.
- 추적성 헬퍼 `check-plan.sh`는 새 구조만 읽는다. `--trace`는 R·AC·Task·테스트 계획의 대응을, `--ac`는 이슈 본문과 spec의 AC가 번호·문장·묶음까지 같은지를 센다.
- git-pr의 완료의 정의 대조는 spec의 AC 행을 목록으로 쓰고, 리포트 표의 AC 번호로 이어 판정을 그대로 옮긴다. PR 본문의 항목 이름·표 머리·상태 이름은 바꾸지 않는다.
- 옛 구조와 새 구조를 함께 읽는 규칙을 두지 않는다. 진행 중인 옛 구조 이슈는 마친 뒤에 재설치한다.
- 이슈 산출물의 구조를 읽는 스킬은 도메인 명세 `issue-workflow.md`의 표에 한 행씩 기록한다.

### 기존 ADR과의 관계

- ADR 0003·0004·0005·0015·0016·0019·0023·0026을 일부 변경했다. 각 ADR의 결정 본문을 새 흐름으로 고치고 근거에 경위를 적었다.

## 근거

<details>
<summary>상세 펼치기</summary>

- 요구사항과 완료의 정의가 사람이 읽기 어려웠다. 이 스킬로 진행한 이슈 하나의 spec이 161KB였고(요구사항 28KB, 완료의 정의 72KB, 전제 58KB) 이슈 본문의 AC 19줄은 한 문장씩이었다 (#145 배경).
  - 하위 목록도 요구사항으로 보아 경계 규칙과 감사 회차 표기가 쌓였다.
  - 완료의 정의는 검증 명령과 케이스 목록이었고 같은 케이스가 테스트 코드의 이름에 이미 있었다.
  - 설계를 적을 자리가 없어 요구사항 하위 목록, 전제, plan Task에 흩어졌다.
- 진행이 한 줄이라 구현 검증의 피드백으로 계획을 고칠 때 돌아가는 절차와 적을 자리가 없었다. 같은 이슈에서 첫 구현은 하루였고 최종 감사는 사흘 동안 17차를 돌았다(발견 43건, 범위 확장 3번).
  - 17차의 보정이 Task 하나의 블록에 쌓였다.
  - 문서와 색인을 감사 전에 마쳐 보정에 맞춰 다시 고치는 커밋이 11번 나왔다. 그래서 구현을 따라 적는 문서만 마무리로 미룬다.
  - 발견 43건 가운데 28건이 두 종류였고 두 종류 모두 2차 감사에서 두 번째로 나왔다. 원리를 고친 것은 4차와 12차 뒤였다. 그래서 같은 종류가 두 회차 이어지면 `설계 결정`부터 고친다.
- 단위 테스트를 먼저 두는 이유: 결정적이고 빠르며 고치기 쉬워 한 회차의 검증에 맞고, 테스트를 먼저 쓰면 설계가 달라진다.
- 완료 확인의 결정을 사용자에게 둔 이유(2026-11-23 대화): 새 판정 값을 만들지 않고 리포트의 상태를 그대로 쓴다. 기준을 "조건부 적합 이상"으로 적으면 1단계 부분 충족인 회차도 `마무리`를 권장하게 된다.
- 구현 검증에 예외를 두지 않은 이유(2026-11-23 대화): 작은 수정도 다른 곳을 깨뜨릴 수 있고 다시 받지 않으면 검증 없이 남는다. 고치지 않을 발견은 `--response`에서 이관이나 보류로 정해 회차를 줄인다.
- 구현 검증의 diff에서 이슈 작업 기록을 빼되 plan 일반 Task가 고친다고 적은 파일은 보는 이유: 감사 결과를 적기만 한 변경이 다시 감사를 부르지 않게 하면서, 원장 항목처럼 제외 경로의 파일이 AC의 산출물인 이슈를 놓치지 않는다 (계획 감사 F-4·F-15).
- `테스트 계획` 줄의 추가·변경을 구현 변경으로 보고 그 줄의 `확인`을 비우는 이유: 지난 감사가 평가하지 않은 줄이 그 감사의 판정을 물려받지 않게 한다 (계획 감사 F-13).
- Task N의 완료 기록을 `--clear`가 맡는 이유: `--clear`가 Task N의 한 단계라 Task N의 체크를 선행 조건으로 두면 정리를 시작할 수 없다 (계획 감사 F-1). 결정 전이나 `다음 회차`에서 실행한 정리가 완료로 기록되지 않도록 루프 기록의 `결정`을 함께 본다 (계획 감사 F-14).
- 첫 계획 감사가 6단계보다 먼저라 이슈 본문에 없는 AC가 정상으로 남는다. 그래서 계획 감사는 summary `이슈 본문 갱신` 줄의 값으로 보강 대기와 위반을 가른다 (계획 감사 F-11·F-12).
- 계획 감사의 1단계에 요구사항 대조를 남긴 이유(2026-11-24 Task 0 사용자 결정): 이슈 본문의 포함·제외 항목이 빠짐없이 옮겨졌는지 보는 헬퍼가 없다. 템플릿 파일은 하나로 두고 표 구성을 감사 종류로 가른다.
- `check-plan.sh`가 `LC_ALL=C`로 견주는 이유: macOS awk의 `==`가 `en_US.UTF-8`에서 길이가 같은 한글 문자열을 같다고 보아 문장이 다른 AC를 통과시켰다. 다른 헬퍼의 같은 문제는 이슈 #147로 나눴다.
- 그림의 가운뎃점을 쉼표로 바꾼 이유(2026-11-25 사용자 결정): 가운뎃점(U+00B7)은 "ASCII 문자와 한글"에 들지 않는다. 선을 한글보다 왼쪽에만 두어 글꼴에 따라 어긋나지 않게 했다.
- 단계 번호("새 이슈 시작 시" 1~6, `--response` 1~5, `--clear` 1~6)를 바꾸지 않은 이유: 번호를 가리키는 다른 스킬과 문서를 고치지 않기 위해서다.
- 사람 확인만 있는 이슈는 1단계 상태가 판정 불가라 전부 확인해도 `다음 회차`를 권장한다. 권장 기준이 AC의 문장이라 고치지 않고 [K-0045](../../70_ledger/active/K-0045-nd-only-issue-recommends-next-round.md)로 등재했다.
- 가짜 `[D]` 사전 판별을 뺀 결과로 [K-0009](../../70_ledger/active/K-0009-plan-audit-fake-d-check-manual.md)가 함께 해소 대상이 됐다.

## 대안

<details>
<summary>상세 펼치기</summary>

- 등록 때 정한 세부를 포함 항목의 하위 목록에 두는 안: 포함이 다시 길어져 `정한 것` 섹션을 택했다.
- `결정 사항`이 커지면 파일로 빼는 안: 기준을 만들지 않고 spec 안 섹션으로만 둔다. 오래 갈 결정은 ADR·계약·도메인 문서로 올린다.
- 섹션 이름 "디자인 결정": 화면 디자인으로도 읽혀 `설계 결정`으로 바꿨다.
- 실행 로그 파일로 실패 확인을 남기는 안: 커밋 순서와 summary 기록으로 충분해 두지 않았다.
- 낮음·정보 발견의 보정이나 바뀐 구현만 보는 부분 감사: 위 근거로 배제했다.
- plan·summary의 Task를 사이클 블록으로 묶는 안: Task는 이어 붙이고 회차는 루프 기록 표가 맡는다.
- PR을 Task N 밖으로 빼는 안: AC12·AC16이 바뀌어 이슈 본문 갱신과 재승인이 필요하다.
- 원장 경로를 구현 검증의 제외 경로에서 빼는 안: 원장 이관만 한 회차도 다시 감사를 받게 된다.
- 감사 리포트 템플릿을 감사 종류별로 나누는 안: 1단계 표 밖의 내용이 두 파일에 중복된다.
- 옛 구조와 새 구조를 함께 읽는 안: 스킬에 옛 규칙이 남는다.
- 교차 감사의 자동 실행, 스킬이 테스트 러너나 층을 정하는 안, archive 문서를 새 구조로 다시 쓰는 안: 불필요로 제외했다.

</details>
