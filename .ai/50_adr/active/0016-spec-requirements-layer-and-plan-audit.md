# ADR: 스펙 요구사항 층 신설과 계획 단계 승인·감사

## 결정

- spec에 `## 요구사항 (Requirements)` 섹션을 둔다. 포함 목록은 R1, R2… 번호와 "무엇이 가능해져야 하는지" 한 문장, 제외 목록은 검토했지만 요구하지 않는 항목과 이유 한 줄(번호 없음). `## 범위 (Scope)`는 삭제하고 경계 선언을 제외 목록으로 일원화한다.
- 완료의 정의는 요구사항 단위 그룹(`### R<n>: <짧은 이름>` + `### 공통`)이다. 상위 그룹 제목에는 레벨 태그가 없고 판정은 하위 항목이 맡는다. `[D]`가 못 덮는 나머지는 `[QD]`/`[ND]`로 그룹 안에 남긴다.
- plan 일반 Task에 `대상 요구사항` 필드를 둔다. 고정 Task(Task 0·N)는 제외한다. 결과 층위는 목표 → 요구사항 → DoD → Task다.
- issue-audit 3단계 명칭은 "경계 검증"이며 대조 원천은 요구사항의 제외 목록이다.
- 새 이슈 시작 절차를 승인 전(목표·요구사항·연관 문서 후보)과 승인 후(완료의 정의·plan·summary)로 나눈다. 승인 요청은 spec 경로와 목표 한 줄·포함·제외 목록만 제시하고, 이슈 본문에 근거 없는 요구사항은 따로 표시해 확정·제외를 질의한다. 요구사항 승인 게이트는 모든 이슈에 적용한다.
- issue-audit `--plan` 모드로 구현 전 spec·plan을 GitHub 이슈 본문과 `.ai` 문서(30/40/50/70) 대비 감사한다. 2단계 관점은 추적성(헬퍼 `check-plan.sh --trace`), 가짜 `[D]` 사전 판별(감사인 수동), 범위, 모호성, 과잉 설계(`[QD]`)다.
- 계획 감사와 계획 보정(`--response`)은 세트이며 사용자가 이슈마다 기본값 없이 선택한다. 건너뛰면 summary에 `생략`을 적고 Task 0으로 간다. 수행 주체·교차모델 원칙은 구현 감사와 같고 기준 모델만 계획 작성 모델이다.
- 단계 어휘는 계획 → 구현 → 최종 감사다. summary `모델 기록`은 계획 모델·계획 audit 모델·구현 모델·최종 audit 모델 4행이며, 계획 감사 건수는 Task 지표·보정률에 넣지 않는다.

## 근거

<details>
<summary>상세 펼치기</summary>

- 스펙에 목표를 무엇으로 달성하는지 적는 자리가 없어 DoD 항목과 Task가 어떤 요구사항을 위한 것인지 역추적되지 않았다. DoD는 잘게 쪼개는 원칙 때문에 파편화되어 사람이 목적을 읽기 어려웠다 (#94).
- 요구사항 층이 비어 있어 포함(In)이 그 자리를 떠안고 파일 경로·산출물 중심 구현 서술로 비대해졌다(#92 사례). `--response` 절차는 이미 "요구사항·DoD·범위 대조"라고 서술해 요구사항 층을 전제하고 있었다.
- spec·plan이 초반에 잘못 잡히면 구현이 정확해도 결과가 의도와 다르다. 기존 게이트 2개는 전제 전달 여부만 묻고 사용자 의도와 맞는지는 묻지 않는다 (#100).
- 사람 검토를 막는 원인은 분량이다. #98 spec 428행 중 328행이 접기 안 검증 명령이었다. 검증 명령은 audit 근거라 뺄 수 없어 사람이 승인할 부분을 분리해 먼저 보인다.
- AI 계획 감사는 정합성·검증 가능성·범위 이탈을 잡고 의도 불일치는 사용자만 잡는다. 그래서 승인 게이트가 감사 모드보다 먼저다.
- 계획 감사 비용이 이슈 규모를 넘는 경우가 있어 수행 여부는 사용자가 정하고 자동 판정 기준을 두지 않는다.
- 가짜 `[D]` 사전 판별의 헬퍼 결정화는 회귀 방지 예외 표기가 템플릿 변경을 요구해 보류하고 원장 K-0009로 등재했다. `check-plan.sh`의 행 단위 파서 경계는 K-0010이다.
- PR #95 리뷰가 템플릿 구조 회귀 검사의 구멍(섹션 소속 접두 매칭, 목록 항목 미검사, 고정 Task 오분류, R 번호 중복·dangling 참조, 섹션 순서)을 닫았다.

</details>

## 대안

<details>
<summary>상세 펼치기</summary>

- 범위 섹션 유지: 포함·비포함이 요구사항의 긍정·부정 열거와 같은 층이라 별도 섹션 이유가 없다.
- 계획 감사 전용 스킬 신설: issue-audit 모드로 둔다. 역할 분담(issue-work 작성·관리, issue-audit 독립 검증, `--response` 보정 게이트) 유지.
- 계획 감사 자동 실행, 수행 여부 자동 판정, `[D]` 검증 명령 접기 제거·분량 상한: 비포함.
- 계획 감사 기록 위치: plan 게이트 블록 대신 summary `모델 기록` 표 + `계획 감사` 한 줄.

</details>
