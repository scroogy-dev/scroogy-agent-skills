# Git PR 정책

## 목적

이 지침의 목적은 동료의 코드 리뷰 시간을 단축하고, 변경 사항에 대한 완벽한 추적성을 제공하는 PR 메시지를 작성하는 것이다.
이슈·브랜치·PR이 각각 1개인 단일 배포(이슈 1 : 브랜치 1 : PR 1)이든,
이슈별로 브랜치를 분리하되 여러 브랜치를 하나의 PR로 통합하는 통합 배포((이슈 1 : 브랜치 1) × N : PR 1)이든,
PR에 포함된 **각 이슈별로** 반드시 '비즈니스 관점'과 '기술 관점' 두 섹션으로 나누어 작성해야 한다.

## 작성 시점 및 주체

PR을 올리기 전, 작성자 본인이 작성한다.
AI 도구를 활용해 초안을 생성한 뒤 작성자가 검토·수정하여 반영하는 방식을 권장한다.

---

## PR 제목

PR 제목은 커밋 메시지와 동일하게 [Conventional Commits 1.0.0](https://www.conventionalcommits.org/ko/v1.0.0/) 형식을 따른다.
Squash Merge 시 PR 제목이 커밋 메시지로 사용되므로 형식을 일치시켜 이력의 일관성을 유지한다.

```
<type>(<scope>): <제목> (#이슈번호)
```

### 단일 배포 (이슈 1 : 브랜치 1 : PR 1)

이슈 번호와 scope를 그대로 사용한다.

```
feat(order): 주문 생성 API 성능 개선 (#123)
fix(payment): 결제 실패 시 사용자 알림 누락 수정 (#124)
```

### 통합 배포 ((이슈 1 : 브랜치 1) × N : PR 1)

포함된 모든 이슈 번호를 나열한다. scope가 단일 도메인으로 수렴하면 scope를 명시하고, 여러 도메인에 걸쳐 있으면 scope를 생략한다.

```
# scope가 하나의 도메인으로 수렴하는 경우
feat(order): 주문 성능 개선 및 결제 알림 추가 (#123, #124)

# scope가 여러 도메인에 걸쳐 있는 경우
feat: 3월 1차 배포 - 주문 성능 개선, 결제 알림 (#123, #124)
```

## PR 메시지 구조

### [PR 헤더] 이슈 목록

PR에 포함된 이슈를 한눈에 파악할 수 있도록 상단에 목록으로 정리한다.

```
## 이슈 목록
- #[이슈번호] - [이슈 제목 또는 핵심 요구사항]
- #[이슈번호] - [이슈 제목 또는 핵심 요구사항]
```

단일 이슈인 경우에도 동일하게 작성한다.

---

### 📝 Issue: #[이슈번호] - [이슈 제목 또는 핵심 요구사항]

이슈가 여러 개인 경우 아래 섹션을 이슈마다 반복한다.

#### 1. 비즈니스 관점

리뷰어가 "이 코드가 왜 필요한가?"를 이해할 수 있도록 비즈니스 목적과 영향을 요약한다.

* **목적 및 요약 (Objective):** 이 이슈가 해결하고자 하는 비즈니스 요구사항, 버그, 또는 사용자 가치를 명확히 기재한다. (무엇을, 왜 변경했는가?)
* **주요 변경 사항 (Impact):** 사용자 경험이나 정책 등 비즈니스 관점에서 어떤 변화가 발생했는지 2~3개의 불릿 포인트로 작성한다.
* **참고사항 (References):** 관련된 기획 문서, 비즈니스 룰, 또는 인증 심사(컴플라이언스)와 관련된 필수 요구사항이 있다면 명시한다.

#### 2. 기술 관점

리뷰어가 "이 코드가 어떻게 구현되었는가?"를 파악하고 소스 코드를 쉽게 추적할 수 있도록 작성한다.

* **구현 요약 (Implementation):** 비즈니스 요구사항을 코드로 어떻게 풀어냈는지, 추가/변경/삭제된 핵심 로직 위주로 요약한다.
* **호출 흐름 (Call Flow):** 기능(엔트리 포인트)별로 나누어, 주요 컴포넌트 간의 실행 흐름을 텍스트 화살표(`->`)로 간략히 도식화한다. 하나의 이슈에 여러 기능이 있는 경우 기능별로 각각 작성한다.

  ```
  - [기능명]: [EntryPoint] -> [핵심 로직] -> [외부 의존성(DB, 외부 API 등)]
  ```

  *(예)*
  ```
  - 주문 생성: OrderController.create() -> OrderValidator.validate() -> OrderService.process() -> OrderRepository.save()
  - 재고 차감: OrderService.process() -> InventoryService.decrease() -> InventoryRepository.update()
  ```

* **참고사항 (References):** 구현 시 참고한 아키텍처 결정 기록(ADR), DB 스키마 변경 사항, 사내 가이드, 또는 보안/성능 측면의 특이사항을 명시한다.
  ADR이 있는 경우 `.ai/50_adr/` 하위의 관련 결정 기록 파일을 명시한다.
  도메인/계약 정보가 있는 경우 `.ai/30_contract/`, `.ai/40_domain/` 하위의 관련 파일도 함께 명시한다.

### 📝 Issue: #123 - 주문 생성 API 성능 개선

#### 1. 비즈니스 관점
* **Objective:** 주문 생성 응답 시간이 평균 2초를 초과하여 사용자 이탈이 발생하고 있어, 핵심 경로를 최적화한다.
* **Impact:**
  - 주문 생성 응답 시간 2초 → 0.5초 미만으로 단축
  - 재고 조회 로직을 캐시 기반으로 전환하여 DB 부하 감소
* **References:** 기획 문서 `docs/order-performance-spec.md`

#### 2. 기술 관점
* **Implementation:** 재고 조회 쿼리를 Redis 캐시로 대체하고, 주문 유효성 검증 로직을 병렬 처리로 변경.
* **Call Flow:**
  - 주문 생성: OrderController.create() -> OrderValidator.validate() -> OrderService.process() -> OrderRepository.save()
  - 재고 조회: OrderService.process() -> InventoryCache.get() -> (miss 시) InventoryRepository.findById()
* **References:** `.ai/50_adr/adr-cache-strategy.md`, DB 스키마 변경 없음
