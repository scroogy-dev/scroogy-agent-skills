### 상세 분석

#### F-1: 승인 SHA에 무관한 기존 변경이 섞여도 탐지할 수 없음

- **위험도**: 높음(HIGH)
- **분류**: 부작용
- **권장 조치**:
  - 코드 수정 전에 `git status --porcelain`로 기존 staged·unstaged·untracked 변경을 고정하고, 발견 시 이번 커밋에 포함할지 제외할지 사용자에게 확인받는다.
  - 리뷰 대응 파일만 명시적으로 stage·commit하고, 승인 직전에 보관한 `headRefOid...승인 SHA`의 커밋 목록·diffstat·최종 diff를 제시한다.
  - 검증은 최종 커밋 트리를 대상으로 다시 확인하고, 남은 미커밋 변경이 있으면 포함 여부와 무관함을 결과에 명시한다.

<details>
<summary>근거·상세 설명 펼치기</summary>

- **설명**: 수정 전 게이트는 현재 브랜치·기준 커밋만 대조한다. 기존 작업트리 상태를 확인하거나 이번 조치의 파일과 분리하는 규칙이 없고, push 승인 정보도 원격·브랜치·SHA·검증 결과뿐이라 SHA가 가리키는 실제 변경을 사용자가 확인할 수 없다.
- **영향**: 이미 staged된 다른 작업, 생성형 AI가 만든 범위 밖 파일, 로컬 설정·비밀값이 같은 커밋에 포함돼도 승인 화면에서 드러나지 않은 채 공개 원격으로 push될 수 있다. 이는 “push의 최종 내용 제시 후 승인”이라는 DoD #6도 실질적으로 충족하지 못한다.

</details>

#### F-2: push 원격이 대상 PR head 저장소라는 사전 보장이 없음

- **위험도**: 중간(MEDIUM)
- **분류**: 암묵적 가정
- **권장 조치**:
  - 보관한 head 호스트·소유자·저장소를 정규화하고, 승인 후보 원격 URL이 이 값과 정확히 일치할 때만 push 승인 단계로 진행한다.
  - 대상 ref가 `refs/heads/<headRefName>`인지, 승인 SHA가 보관한 `headRefOid`를 기반으로 하는지 함께 확인한다.
  - push 직전 원격 ref가 보관한 `headRefOid`와 다르면 중단한다. 가능하면 예상 이전 SHA를 lease로 지정해 원격 변경·삭제와 push를 원자적으로 결속한다.

<details>
<summary>근거·상세 설명 펼치기</summary>

- **설명**: 3차 보정은 head 저장소를 수집하지만, push 직전에는 원격 URL을 “승인 시 보관값”과만 비교한다. 그 승인 후보 원격이 수집한 head 저장소와 같아야 한다는 대조가 없으며, push 후 `headRefOid` 검사는 이미 다른 원격을 변경한 뒤의 사후 탐지다.
- **영향**: 사용자가 표시된 원격을 잘못 승인하면 무관한 저장소의 동명 브랜치가 갱신되고 대상 PR은 그대로일 수 있다. 사후 PR SHA 불일치 보고는 잘못된 외부 변경을 되돌리지 못한다.

</details>
