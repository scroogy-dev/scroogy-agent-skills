### 상세 분석

#### F-33: 수집한 patch와 주변 코드가 서로 다른 커밋을 가리킬 수 있다

- **위험도**: 🟡 중간(MEDIUM)
- **관점**: 모호성. Task 2는 ‘2단계에서 구한 값’을 쓰라고 하지만 헬퍼 출력에는 그 값이 없고, 3단계의 명령은 현재 참조로 merge-base를 다시 계산한다.
- **권장 조치**: 수집 시점의 merge-base 객체 ID를 주변 줄 조회와 인용 재확인까지 전달하거나, 기준이 달라졌을 때 같은 시점의 자료를 다시 수집하도록 정한다.
- **완료 기준 1**: 변경 목록에 없는 주변 파일을 읽기 직전 base가 전진해도, 수집한 patch와 같은 기준 커밋에서 그 파일을 읽는다. 재수집을 선택하면 목록과 patch도 함께 교체한다.
- **완료 기준 2**: 두 기준 커밋의 주변 값이 반대인 사례에서 한쪽 patch와 다른 쪽 값을 조합하면 검증이 실패한다.

<details>
<summary>실행에서 읽은 두 값</summary>

임시 저장소의 기준 커밋에는 `enabled=false`, 작업 브랜치 HEAD에는 `enabled=true`를 뒀다. 작업 트리에서 해당 파일만 기준 값으로 돌리고 다른 파일을 수정하자 계획의 변경 목록에는 `M change.txt`만 나왔다. 브랜치와 작업 트리를 그대로 두고 base 참조만 HEAD로 전진시켰다. 수집 때의 merge-base에서 읽으면 `false`, plan 315행의 명령을 다시 실행해 읽으면 `true`였다. F-27은 내용 변환 필터를 다뤘다. 이 사례는 필터가 없는 일반 파일에서 성립한다.

</details>

#### F-34: 임시 스테이징이 원본 저장소의 인덱스 변경 훅을 실행한다

- **위험도**: 🟡 중간(MEDIUM)
- **관점**: 모호성. Task 1은 원본 저장소 보존을 약속하지만 임시 인덱스와 객체 디렉토리만 분리한다.
- **권장 조치**: 스냅샷용 Git 호출에만 훅 실행을 끄고, 사용자 저장소의 훅 설정과 일반적인 스테이징 동작을 보존한다.
- **완료 기준 1**: 인덱스 변경을 기록하는 훅이 설정된 임시 저장소에서 `--base`는 예상 목록과 patch를 내고, 훅 기록과 원본 파일은 그대로다.
- **완료 기준 2**: 수집 뒤 같은 저장소에서 사용자가 직접 스테이징하면 기존 훅이 실행된다.

<details>
<summary>원본과 사본을 구분한 시험</summary>

Git 2.50.1의 임시 저장소에 인덱스 갱신을 기록하는 `post-index-change` 훅을 설정했다. 계획의 인덱스 사본과 임시 객체 디렉토리를 사용해 두 `git add`를 실행하자 목록은 `M sample`이었고 원본 `.git/index-events`에는 두 줄이 생겼다. Git은 인덱스를 쓸 때 이 훅을 호출한다. [Git 훅 문서](https://git-scm.com/docs/githooks#_post_index_change)

</details>

#### F-35: 커밋 메시지 안의 지시문을 어떻게 읽을지 빠져 있다

- **위험도**: 🟡 중간(MEDIUM)
- **관점**: 범위·모호성. R1에 따라 PR 모드와 브랜치 모드 모두 작성자가 쓴 커밋 메시지를 읽는다. Task 2의 조항과 R4 검사는 입력 네 종류만 열거한다.
- **영향**: 리뷰어가 커밋 메시지 속 요청을 작업 지시로 받아들이면 R5의 변경 줄 검토를 건너뛰거나 판정을 바꿀 수 있다. 이는 문서상 누락에서 도출한 위험이다. AC5가 명시한 네 입력은 모두 반영됐다.
- **권장 조치**: 수집한 자유 형식 텍스트에 같은 원칙을 적용하고 커밋 메시지를 예에 포함한다.
- **완료 기준**: 동일한 diff와 리뷰 기준에서 커밋 메시지에만 리뷰 절차를 바꾸라는 문장이 추가되어도 검토 대상과 판정 근거가 유지된다. 기존 Task 6 사례를 활용할 수 있다.

#### F-36: 커밋 수 조회 실패를 처리해도 실제 실행 점검의 합격 조건이 모호하다

- **위험도**: 🟢 낮음(LOW)
- **관점**: 모호성. Task 2는 전체 커밋 수를 얻지 못하면 사유와 확보한 수를 기록하고 계속하도록 한다. R1의 실제 실행 DoD는 두 수의 일치를 요구하고 Task 7의 기록에도 두 수가 있어야 한다.
- **영향**: 수집기와 결과 파일이 승인된 실패 처리를 따르더라도, 같은 기록이 최종 감사에서 R1 미충족으로 읽힐 수 있다. 정상 조회가 가능한 점검에서는 충돌이 없다.
- **권장 조치**: 성공 경로의 통과 조건은 유지하고, 조회 실패 관찰은 별도로 채점하거나 정상 경로 검증을 판정 불가로 두고 재실행한다고 명시한다.
- **완료 기준**: ‘5개 중 5개 확보’, ‘전체 수 조회 실패·확보 5개 기록’, ‘일부 확보·사유 누락’ 세 기록을 spec과 plan이 같은 기준으로 분류한다.

### 기등재 참조 항목

[K-0031](../../../70_ledger/active/K-0031-review-branch-mode-index-exception-paths.md)의 수용 범위는 Git의 스테이징 규칙에 따라 작업 트리와 수집 내용이 달라지는 경우다. F-33은 수집 뒤 기준 커밋을 바꿔 읽는 문제이고 F-34는 원본 저장소 보존에 관한 문제다. 원장의 재검토 조건에 해당하는 변경이나 사례는 확인하지 않았다.
