## Tasks

> AI가 순서대로 실행할 작업 단위를 정의합니다.
> **작성 원칙**: 구현자에게 이 문서 외 컨텍스트가 없다고 가정하고, Task별 완료 기준을 결정적으로 씁니다.
> 각 작업은 독립적으로 검증 가능해야 하며, 완료 기준은 **항목별 리스트로 쪼개 레벨 태그 + 검증 수단**을 적습니다.
> 명령으로 환원이 어려운 항목만 판정 주체(다른 AI / 사람)를 적고 강등 사유를 남깁니다.
> Task 완료 기준은 진행만 판정하고 spec에 없는 결과를 더하지 않는다는 원칙을 따릅니다. 결과 판정은 spec 완료의 정의가 맡습니다.
>
> **대상 요구사항 필드** — 일반 Task에는 `- **대상 요구사항**: R<n>` 필드를 `목표` 다음 행에 두어
> 이 Task가 spec의 어느 요구사항을 구현하는지 밝힙니다. 여러 개면 `R<n>, R<m>`로 나열합니다.
> 고정 Task(Task 0·Task N)는 특정 요구사항에 속하지 않으므로 이 필드를 두지 않습니다.
>
> **완료 기준 형식** — 본문(접기 금지)에는 레벨 태그 + 무엇이 보장되는지 한 문장(+ 강등 사유)만 두고,
> 검증 명령·테스트케이스·기대 출력·명령 설계 주의점은 접기로 내립니다. 접기 제목에 기대 출력을 함께 적습니다
> (기본형: "검증 명령 — 출력 0건이면 통과"). 접을 상세가 없는 항목은 접기 없이 본문 한 줄로 둡니다.
> 다른 게이트의 선행 조건이 되는 항목은 의존 관계와 **선행 조건이 무너졌을 때의 결과**를 본문 문장에 남기고, 메커니즘만 접기에 둡니다.
> 첫 고정 Task(Task 0 구현 시작 게이트)와 마지막 고정 Task(교차모델 issue-audit)는 삭제하지 말고 그대로 둡니다.
>
> **테스트 배치** — 구현 테스트(단위·회귀)는 그 기능을 만드는 Task 안에 둡니다. 테스트 작성(fixture·기대 출력)을
> `작업 내용`의 단계로 넣고 테스트 파일을 그 Task의 산출물로 삼으며, `완료 기준`에는 "이 Task의 테스트 0 실패" `[D]`를 둡니다.
> 별도 테스트 Task는 fixture 일괄 갱신처럼 테스트 자체가 작업 대상일 때만 둡니다.
> 전체 테스트 통과는 spec `### 공통`의 회귀 방지 항목으로 유지합니다.
> `.ai/10_rules/testing-principles-local.md`가 있으면 테스트 `[D]`의 러너 호출·출력 판독·실행 셸은 그 파일의 테스트 층 표를 따릅니다.
>
> **검증 레벨** — 낮을수록 좋다(자동 검증에 가까움). 기본은 L1, 한 레벨 내릴 때마다 강등 사유를 함께 적는다.
>
> - `[D]`  L1 결정적   — 명령이 합/불을 판정, 사람 판단 없음
> - `[QD]` L2 준결정적 — 다른 AI·기준 체크리스트가 채점
> - `[ND]` L3 비결정적 — 사람이 직접 읽고 판단
>
> **문서를 대상으로 검증할 때는 문구가 아니라 행 구조를 셉니다**. 같은 문구가 주석·안내문에도 등장하므로
> `grep -c '<문구>'`는 실제 구조가 없어도 통과합니다. 헤더는 `^## `, Task는 `^### Task `,
> 필드는 `^- \*\*…\*\*:`로 앵커를 고정하고, 명령은 작업 디렉토리에 의존하지 않게 repo 루트 기준 경로로 적습니다.
> **검증 명령 보정은 반례 격추가 아니라 불변식 전수 명세로 합니다**. 지적된 변형 하나만 막으면 이웃 변형이
> 다음 감사에서 재발하므로, 기대 구조를 열거하고 "그 외 0건"까지 판정에 넣습니다.

**이 계획의 공통 사항**

- 모든 명령은 repo 루트에서 실행한다.
- 러너는 `git-review/tests/run-tests.sh` 하나다. 새 케이스의 설명은 `<라벨>: <내용> 통과` 또는 `<라벨>: <내용> 격추` 형식으로 쓰고, 한 설명에 두 낱말을 함께 쓰지 않는다. Task 완료 기준이 러너 출력의 `ok` 행을 라벨과 낱말로 센다.
- 조항 구조 케이스는 `git-qa/tests/run-tests.sh`의 방식을 따른다. 실제 파일은 통과하고, 앵커를 지우거나 절 밖으로 옮긴 사본은 격추돼야 한다.
- 러너의 기존 케이스(분기점 61건)는 지우거나 고치지 않는다. spec R10의 회귀 방지 항목이 분기점 러너로 다시 확인한다.
- SKILL.md 본문은 합니다체이고 설명 본문에 이모지를 쓰지 않는다. 산출물 형식은 템플릿에 두고 SKILL.md는 참조한다(ADR 0010).

       - 내용 변환 필터는 끄지 않는다. 필터 프로그램이 스스로 남기는 파일은 `.git` 보장에 들지 않는다고 헬퍼 머리 주석에 적는다(spec 전제 최종 감사 1차 "필터의 부작용").

       - 이 환경의 `git` 명령은 모두 `-c core.fsmonitor=false`도 붙여 실행한다. 파일 시스템 감시(file system monitor, `core.fsmonitor`)를 켠 저장소에서는 인덱스를 읽는 명령이 변경 조회(조회 훅이나 내장 데몬)를 부른다(spec 전제 12차 "스냅샷 중 파일 시스템 감시").

     - 산출: 같은 환경에서 `git -c core.quotePath=false diff-index --cached --no-renames --no-ext-diff --no-textconv --no-color --ignore-submodules=dirty --name-status -z '<merge-base>'`의 목록(NUL 구분)과, `-z`를 뺀 같은 명령의 목록(줄 단위, Git의 인용 표기), `--name-status -z`를 `-p`로 바꾼 같은 명령의 patch를 임시 파일에 받는다. 셋 다 성공한 뒤에만 목록, 빈 줄 1행, patch 순서로 표준 출력에 쓴다. 목록이 비면 아무것도 쓰지 않는다.
       - 목록은 NUL 구분 목록의 레코드(변경 종류, 경로)마다 `<변경 종류><탭><경로>` 한 행으로 쓴다. 경로는 저장소 루트 기준의 실제 경로다(spec 전제 10차 "경로 표기"). 줄 단위 목록을 그대로 쓰지 않는다. Git은 경로를 줄 단위로 낼 때 큰따옴표·역슬래시·제어 문자가 든 경로를 `core.quotePath` 설정과 관계없이 큰따옴표로 감싸 이스케이프하고, 그 표기는 `git show`에 넘길 수 없다.
       - 이름에 줄바꿈이 들었거나 이름이 큰따옴표로 시작하는 경로는 그 레코드만 줄 단위 목록에서 같은 순번의 행(Git의 인용 표기)을 그대로 쓴다(spec 전제 11차 "경로 표기의 계약"). 줄바꿈이 든 경로는 한 행에 담을 수 없고, 큰따옴표로 시작하는 실제 경로는 인용 표기 행과 가를 수 없다. 두 목록은 같은 스냅샷에서 같은 옵션으로 내 레코드 순서가 같다.
       - `git diff`를 쓰지 않고 `git diff-index`를 쓴다. `git diff`는 사용자 diff 설정(`diff.noprefix`, `diff.context`, `diff.ignoreSubmodules`, textconv 등)을 읽어 저장소마다 출력이 달라진다(spec 전제 8차 "목록의 완전성").
       - `--ignore-submodules=dirty`를 빼지 않는다. 하위 모듈의 무시 설정(`.gitmodules`의 `ignore = all` 등)은 `git diff-index`에도 적용돼, 이 옵션이 없으면 스냅샷에 들어간 하위 모듈의 커밋 이동이 목록과 patch에서 빠진다.
     - `--marked`: 변경을 보지 않도록 표시한 경로를 낸다(spec 전제 11차 "표시한 경로 조회"). `git ls-files -v -z --full-name -- ':/'`의 레코드(`<표지><공백><경로>`, NUL 구분)와 `git -c core.quotePath=false ls-files -v --full-name -- ':/'`의 줄 단위 행을 임시 파일에 받는다. 둘 다 성공하고 레코드 수가 같을 때만 표준 출력에 쓴다.
       - 표지가 소문자이거나 `S`인 레코드만 `<표지><공백><경로>` 한 행으로 쓴다. 경로 표기는 변경 파일 목록과 같다. 이름에 줄바꿈이 들었거나 이름이 큰따옴표로 시작하는 경로는 줄 단위 목록에서 같은 순번의 행을 그대로 쓴다.
       - 표지는 NUL 구분 레코드마다 판정한다. NUL을 줄바꿈으로 바꾼 뒤 거르면 이름에 줄바꿈이 든 파일의 뒷부분이 다른 레코드로 읽힌다.
       - 실제 인덱스를 읽기만 한다. 스냅샷 환경을 만들지 않는다. 두 `git ls-files` 명령에는 `-c core.fsmonitor=false`를 붙인다(스냅샷 환경과 같은 이유).
     - 실패: 어느 단계든 실패하면 표준 출력에 아무것도 쓰지 않고 사유를 표준 오류에 1행으로 쓴 뒤 종료 코드 1로 끝낸다. 인자 오류는 종료 코드 2다.
     - 임시 디렉토리는 끝날 때 지운다(`trap`의 `EXIT`). 자기가 만든 디렉토리만 지운다.
     - 실제 인덱스, 작업 트리, 저장소 객체를 바꾸지 않는다. 분할 인덱스를 켠 저장소에서도 `.git` 아래 파일의 목록과 내용이 그대로다. 저장소의 훅과 파일 시스템 감시의 조회를 실행하지 않는다. `gh`를 부르지 않는다.

     - 격추 6건 이상: 없는 base, git 작업 트리 밖에서 `--base`로 실행, git 작업 트리 밖에서 `--marked`로 실행(셋 다 종료 코드 1·빈 표준 출력), `--base`와 `--marked`가 둘 다 없음, 둘을 함께 줌, 알 수 없는 인자(셋 다 종료 코드 2·빈 표준 출력).

     - 호스트가 `github.com`이 아니거나 MCP도 쓸 수 없으면 리뷰를 시작하지 않고 그 사실을 알린 뒤 끝낸다.
  4. `### 2단계: 변경 수집`을 쓴다.
     - `PR 모드`: `gh pr diff`로 diff를, 1단계 응답에서 PR 본문과 커밋 메시지를 모은다.
     - 커밋 메시지의 완전성(`PR 모드`, spec 전제 11차 "커밋 메시지 수집의 완전성"): 모은 커밋 메시지의 수를 PR의 커밋 수와 견준다고 적는다. PR의 커밋 수는 `gh api --hostname '<호스트>' 'repos/<소유자>/<저장소>/pulls/<PR 번호>' --jq .commits`로 얻는다. `PR의 커밋 수`와 `견줍니다`를 같은 행에 쓴다.
       - 두 수가 같으면 다 모은 것이다. 같지 않으면 `gh api --hostname '<호스트>' --paginate 'repos/<소유자>/<저장소>/pulls/<PR 번호>/commits?per_page=100'`로 커밋 메시지(응답 항목의 `commit.message`)를 다시 모으고 수를 다시 견준다. `gh pr view`의 `commits`는 처음 100개까지만 나온다. 문구 `--paginate`를 쓴다.
       - 다시 모은 뒤에도 두 수가 같지 않거나(이 조회는 250개까지만 낸다) 두 조회(PR의 커밋 수 조회, 페이지 조회) 가운데 하나라도 실패하면, 그 사실과 모은 수·PR의 커밋 수(얻지 못했으면 얻지 못했다는 사실)를 결과의 최종 의견에 한 줄로 적고 계속한다. PR의 커밋 수를 얻지 못하면 견줄 수 없으므로 다 모았다고 보지 않는다. `커밋 메시지를 모두 모으지 못하면`과 `최종 의견`을 같은 행에 쓴다.
       - 두 조회는 아래 "수집 중 PR 변경"의 다시 조회보다 먼저 한다. 그 사이 PR이 바뀌면 다시 조회가 1단계부터 다시 모으게 한다.
     - 연결 이슈(`PR 모드`): PR 본문의 이슈 참조와 1단계 응답의 `closingIssuesReferences`(GitHub에서 PR에 연결한 이슈. 본문에 번호가 없어도 나온다)를 합쳐 찾는다. 저장소와 이슈 번호가 같으면 한 번만 세고, 연결 이슈 본문을 `gh issue view … --repo …`로 읽는다(다른 저장소의 이슈면 그 저장소). `closingIssuesReferences`를 조회할 수 없으면(MCP 폴백 등) 본문 참조만으로 찾고 그 사실을 결과의 최종 의견에 한 줄로 적는다.
     - `브랜치 모드`: base는 `origin/HEAD`가 가리키는 브랜치(없으면 `main`)다. 수집 전에 merge-base 커밋의 해시를 한 번 구해 불변값으로 보관한다(`mb="$(git merge-base "$base" HEAD)"`). 변경은 헬퍼에 그 해시를 넘겨 모은다(`'<skill 디렉토리>/scripts/collect-branch-changes.sh' --base "$mb"`). 헬퍼는 merge-base와 작업 트리의 차이를 변경 파일 목록(`<변경 종류><탭><경로>` 행), 빈 줄, patch 순서로 낸다. 커밋 메시지는 그 해시 이후의 `git log`로 모은다(`git log "${mb}..HEAD"`). 문구 `merge-base`, `git merge-base`, `collect-branch-changes.sh`, `--base "$mb"`를 쓴다.
       - merge-base 커밋의 해시는 이 단계에서 한 번만 구한다고 적는다(spec 전제 12차 "merge-base의 고정"). 3단계의 읽기와 `발견 처리`의 인용 위치 재확인은 보관한 해시를 쓴다. `merge-base`와 `다시 구하지 않습니다`를 같은 행에 쓴다. base 브랜치는 리뷰 도중에도 움직일 수 있어(fetch, 다른 브랜치의 병합), 다시 구하면 patch와 다른 커밋의 파일을 읽을 수 있다.
       - merge-base를 구하지 못하면 diff를 얻지 못한 것이다(아래 수집 실패).
       - 대상을 SKILL.md에 적는다(spec R1). 대상은 지금 작업 트리를 전부 스테이징해 커밋하면 들어갈 변경이고, 무엇이 스테이징되는지는 Git이 정한다. 커밋한 변경, 작업 트리에 남아 있는 미커밋 변경, 미추적 새 파일이 들어간다. 문구 `미추적 새 파일`을 쓴다.
       - 일반 파일의 기준을 적는다. 일반 파일(무시 규칙에 걸리지 않고 `.ai/99_workspace/` 밖에 있으며 변경을 보지 않도록 표시하지 않은 파일)은 작업 트리의 내용이 기준이라 스테이징 여부가 결과를 바꾸지 않는다. 스테이징한 뒤 작업 트리에서 되돌려 인덱스에만 남은 변경은 대상이 아니다.
       - Git이 스테이징 내용을 정하는 경로를 적는다. 아래 넷을 빠짐없이 옮긴다.
         - 사용자가 변경을 보지 않도록 표시한 경로(`assume-unchanged`, `skip-worktree`)는 인덱스의 내용을 쓴다.
         - 무시 규칙에 걸린 파일과 `.ai/99_workspace/` 아래 파일은 인덱스에 있을 때만 작업 트리의 내용으로 읽고, 인덱스에 없으면 없는 파일로 본다. 그래서 무시 규칙에 걸린 미추적 파일과 `.ai/99_workspace/` 아래 미추적 파일은 대상이 아니다.
         - 하위 모듈은 가리키는 커밋이 바뀐 것만 변경으로 나오고, patch에는 두 커밋의 해시 행만 나온다.
         - 그 밖의 Git 설정(내용 변환 필터, 희소 체크아웃 등)이 스테이징 내용을 정하는 경우도 Git의 결과를 따른다.
       - 헬퍼가 낸 목록을 변경 파일 목록으로 그대로 쓴다고 적는다. `git diff`·`git status`·`git ls-files`의 결과로 목록을 따로 만들거나 고치지 않는다. 이 명령들은 인덱스를 거쳐 작업 트리를 보므로 스테이징 상태에 따라 같은 작업 트리를 다르게 보고한다.
       - 출력 읽는 법을 적는다. 변경 종류는 추가(A)·수정(M)·삭제(D)·종류 변경(T)이다. 이름 변경은 삭제와 추가로 나온다. 미추적 새 파일은 patch에 내용 전체가 추가 줄로 나오고, 실행 권한만 바뀐 파일은 patch에 모드 행만 나온다.
       - 경로 표기를 적는다(spec 전제 11차 "경로 표기의 계약"). 목록의 경로는 두 형태 가운데 하나다. 큰따옴표로 시작하지 않으면 저장소 루트 기준의 실제 경로다. 큰따옴표로 시작하면 Git의 인용 표기(큰따옴표로 감싸고 역슬래시로 이스케이프한 표기)이며, 이름에 줄바꿈이 들었거나 이름이 큰따옴표로 시작하는 경로만 이 형태로 나온다. 서로 다른 경로는 서로 다른 행으로 나온다. patch의 파일 머리 행(`diff --git`·`---`·`+++`)의 경로는 Git의 표기 그대로이고, patch의 파일 구간은 목록의 행과 같은 순서로 나온다. 결과에 적는 경로도 목록의 경로다.
       - 종료 코드가 0이 아니면 diff를 얻지 못한 것이다(아래 수집 실패). 종료 코드 0에 출력이 없으면 변경 파일이 0개다.
     - 수집 중 PR 변경(`PR 모드`): diff를 받은 뒤 `headRefOid`·`baseRefOid`를 다시 조회해 1단계에서 보관한 값과 견준다. 다르면 수집 중에 PR이 바뀐 것이므로 1단계부터 한 번 다시 모으고, 다시 모은 뒤에도 다르면 리뷰를 시작하지 않고 그 사실을 알린다. `다시 조회`와 `headRefOid`를 같은 행에 쓴다.
     - 수집 실패: 두 모드 모두 diff를 얻지 못하면 빈 변경으로 진행하지 않고, 리뷰를 시작하지 않으며 실패한 명령과 사유를 알린다. 수집은 성공했는데 변경 파일이 0개인 경우와 구분한다. `diff를 얻지 못하면`과 `리뷰를 시작하지 않`을 같은 행에 쓴다.
     - 연결 이슈 본문만 얻지 못하면 그 사실과 사유를 결과의 최종 의견에 한 줄로 적고 계속한다.
     - 두 모드 모두 변경 파일 목록을 확정한다. 이 목록이 테크 리뷰 2단계와 요약의 검토 파일 수의 기준이다.
  5. `### 3단계: 읽기 기준 확정`을 쓴다.
     - `PR 모드`: 주변 코드는 `headRefOid` 커밋에서 읽는다. 커밋이 로컬에 없으면 `git fetch '<원격>' 'refs/pull/<PR 번호>/head'`로 객체만 받는다.
     - 커밋 존재 확인(`PR 모드`): fetch의 성공 여부와 별개로 `git cat-file -e "${sha}^{commit}"`로 고정한 커밋이 로컬에 있는지 확인한다. 있으면 파일을 `git show "${sha}:${file}"`로 읽는다. 없으면(fetch 실패, 또는 fetch는 성공했지만 그 사이 PR head가 바뀌어 고정한 커밋이 받은 이력에 없는 경우) `gh api --hostname '<호스트>'`의 contents 조회(`?ref=<SHA>`)로 읽고, 그것도 실패하면 그 파일을 읽지 않은 파일(사유: 읽기 실패)로 둔다. `FETCH_HEAD`나 작업 트리의 파일로 대신 읽지 않는다.
       - contents 조회는 경로가 영문자·숫자·`.`·`_`·`-`·`~`·`/`로만 되어 있을 때만 쓰고, 그 밖의 경로는 조회하지 않고 읽기 실패로 둔다. 코드 블록의 판정은 `case "$file" in` … `esac`로 적는다. 코드 블록의 경로 변수는 `file`이다(zsh에서 `path`는 `PATH`와 묶여 있다. spec 전제 최종 감사 1차 "contents 조회의 경로 문자"·"코드 블록의 변수 이름").
       - contents 조회 앞에 고정한 커밋의 트리 조회(`git/trees/<SHA>?recursive=1`)로 경로의 모드를 읽고, 모드가 일반 파일(`100644`·`100755`)일 때만 조회한다. 모드 `120000`(심볼릭 링크)인 경로에는 contents 조회를 쓰지 않고 링크가 가리키는 경로가 diff의 변경 줄에 나올 때만 그 줄로 읽으며, 그 밖의 모드와 모드를 얻지 못한 경로는 읽기 실패로 둔다(spec 전제 최종 감사 2차 "심볼릭 링크의 contents 조회", 3차 "contents 조회의 파일 종류". 2차에는 diff 머리 행의 모드로 링크를 가렸다).
     - "작업 트리와 현재 브랜치를 바꾸지 않습니다"를 적고, 쓰지 않는 명령(`gh pr checkout`, `git checkout`, `git switch`, `git stash`)을 산문으로 든다. 이 명령들을 코드 블록에 넣지 않는다.
     - `PR 모드`에서 이 스킬이 쓰는 파일은 결과 파일 `.ai/99_workspace/temp_review_result.md`뿐이라고 적는다. 문서 부재 시 처리도 수행하지 않는다(아래 7번).
     - `브랜치 모드`: 읽기 기준은 2단계에서 수집한 내용이다. 수집한 내용은 헬퍼의 patch와 merge-base 커밋 둘로 정해진다(spec 전제 9차 "브랜치 모드의 읽기 기준").
       - 변경 줄은 헬퍼가 낸 patch로 읽는다. `브랜치 모드`·`변경 줄`·`patch`를 같은 행에 쓴다.
       - patch에 나오지 않은 줄(변경 파일의 나머지 줄, 변경 파일 목록에 없는 파일)의 수집한 내용은 merge-base 커밋의 파일이라고 적는다. 변경 파일 목록에 없는 파일은 커밋될 내용이 merge-base 커밋과 같기 때문이다. 읽는 명령을 코드 블록으로 적는다. `mb`는 2단계에서 보관한 merge-base 커밋의 해시이며 3단계에서 다시 구하지 않는다. 3단계에는 문자열 `git merge-base`를 문장에도 코드 블록에도 쓰지 않는다. 다시 구하지 않는다는 문장은 2단계에 두고, spec R1의 3단계 조항 `[D]`는 이 소절에 그 문자열이 있으면 위반으로 본다.

         ```bash
         git show "${mb}:${file}"
         ```
       - 파일을 조회하는 경로(`git show`의 `path`, 작업 트리의 파일 경로)에는 변경 파일 목록의 경로를 그대로 넘긴다고 적는다. 문구 `목록의 경로를 그대로`를 쓴다. patch 머리 행의 Git 표기는 조회 경로로 쓰지 않는다. 변경 파일 목록에 없는 파일은 작업 트리에서 찾은 실제 경로를 넘긴다.
         - 목록에서 큰따옴표로 시작하는 경로는 Git의 인용 표기라 조회에 넘기지 않는다고 적는다(이름에 줄바꿈이 들었거나 이름이 큰따옴표로 시작하는 경로). 문구 `큰따옴표로 시작`을 쓴다. 그 파일은 patch의 변경 줄로 읽고, patch에 나오지 않은 줄을 읽지 못했으면 `발견 처리`의 인용 위치 재확인이 정한 대로 처리한다고 적는다.
       - 주변 코드를 찾아 읽을 때는 작업 트리의 파일로 읽어도 된다고 적는다. 일반 파일은 작업 트리의 내용이 수집한 내용과 같다. 변경을 보지 않도록 표시한 경로는 수집이 인덱스의 내용을 썼으므로 인덱스의 내용으로 읽는다(`git show ":0:${file}"`). 문구 `인덱스의 내용으로 읽습니다`를 쓴다.
         - 인덱스 조회에는 스테이지 번호 `0:`을 적는다. `git show ":${file}"`는 `2:x.txt`처럼 숫자와 `:`로 시작하는 이름의 앞부분을 스테이지 번호로 읽는다(spec 전제 11차 "표시한 경로 조회").
       - 표시한 경로는 이 단계에서 한 번 구한다. 헬퍼의 `--marked`로 구하고 문구 `--marked`를 쓴다. 출력 행은 `<표지><공백><경로>`이고(표지가 소문자면 `assume-unchanged`, `S`면 `skip-worktree`), 출력이 없으면 표시한 경로가 없다. 경로 표기는 변경 파일 목록과 같다. 명령을 코드 블록으로 적는다.

         ```bash
         '<skill 디렉토리>/scripts/collect-branch-changes.sh' --marked
         ```
         - `git ls-files -v`의 출력을 줄 단위로 걸러 표시한 경로를 따로 만들지 않는다고 적는다. 이름에 줄바꿈이 든 파일의 뒷부분이 다른 행으로 읽힌다.
       - 작업 트리나 인덱스에서 읽은 내용이 수집한 내용(patch, merge-base 커밋의 파일)과 다르면 수집한 내용을 따른다고 적는다(내용 변환 필터가 걸린 파일, 수집 뒤에 파일이 바뀐 경우 등). 문구 `수집한 내용을 따릅니다`를 쓴다. Git 기능을 하나씩 들어 예외로 적지 않는다.
       - merge-base 커밋에도 patch에도 없는 파일(무시 규칙에 걸린 미추적 파일, `.ai/99_workspace/` 아래 미추적 파일, 하위 모듈 안의 파일)은 수집한 내용에 없는 파일이라고 적는다.
       - 발견의 처리는 `발견 처리`의 인용 위치 재확인이 정한다(Task 4).
     - 셸 변수 뒤에 `:`가 오는 자리는 `${sha}`처럼 중괄호로 감싼다.
  6. `### 4단계: PR 본문 확인 항목 수집`을 쓴다.

     - 삭제 줄을 인용한 발견은 읽기 기준 커밋에 그 줄이 없는 것이 정상이다. diff의 삭제 줄을 다시 읽고, 지워진 동작이 읽기 기준 커밋의 다른 위치에 남아 있지 않은지 확인한다. 줄이 없다는 이유만으로 성립하지 않는다고 보지 않는다.
     - `브랜치 모드`에서 변경 줄을 인용한 발견은 헬퍼가 낸 patch의 그 줄을 다시 읽어 확인한다. `브랜치 모드`와 `patch`를 같은 행에 쓴다.
     - `브랜치 모드`에서 patch에 나오지 않은 줄(변경 파일의 나머지 줄, 변경 파일 목록에 없는 파일의 줄)을 인용한 발견은 merge-base 커밋의 파일(`git show "${mb}:${file}"`)에서 그 줄을 찾아 확인한다. `patch에 나오지 않은 줄`과 `merge-base`를 같은 행에 쓴다. 변경 파일은 변경 줄 수만큼 줄 번호가 어긋나므로 내용으로 찾는다고 적는다. 조회 경로는 대상 수집 3단계가 정한 대로 변경 파일 목록의 경로다. `mb`는 대상 수집 2단계에서 보관한 해시다. 이 소절에는 문자열 `git merge-base`를 문장에도 코드 블록에도 쓰지 않는다(spec R9의 `[D]`가 있으면 위반으로 본다).
     - `브랜치 모드`에서 읽은 파일의 내용이 수집한 내용(patch, merge-base 커밋의 파일)과 다르면 수집한 내용으로 성립을 판단한다(변경을 보지 않도록 표시한 경로를 작업 트리에서 읽은 경우, 내용 변환 필터가 걸린 파일, 수집 뒤에 파일이 바뀐 경우). "patch와 다르다는 이유만으로 성립하지 않는다고 보지 않습니다"를 적는다.
     - `브랜치 모드`에서 수집한 내용을 읽지 못했거나, 수집한 내용에 없는 파일(merge-base 커밋에도 patch에도 없는 파일)의 내용에 성립이 달려 있어 확인하지 못했으면 `(확인 필요)`를 붙이고 사유를 적는다.
  3. `### 실패 시나리오`를 쓴다.
     - 버그·보안·성능 리뷰 포인트는 근거 접기에 `실패 시나리오:` 줄을 한 줄 둔다. 어떤 입력·상태에서 어떤 잘못된 결과가 나오는지를 적는다.
     - 다른 카테고리와 doc 카테고리 세트에는 요구하지 않는다.
     - 실패 시나리오를 한 줄로 쓸 수 없으면 인용 위치 재확인으로 돌아가 발견이 성립하는지 다시 본다.
  4. `### 변경 전부터 있던 결함`을 쓴다.
     - 정의: 변경 전에도 같은 결함이 있었고, 이번 변경이 그 결함에 닿는 경로를 새로 만들거나 넓히지 않은 경우다. 결함이 있는 줄이 diff의 추가·수정 줄이 아니면 변경 전부터 있던 것으로 본다.
     - 옮기기만 한 줄: 추가 줄이어도 내용 변경 없이 옮기기만 한 줄은 추가 줄로 보지 않는다. 연속한 줄 묶음(블록)이 그대로 다른 위치로 옮겨졌고 diff의 삭제 쪽 블록에도 같은 결함이 있던 경우다. 문구 `옮기기만 한 줄`을 쓴다.
       - 추가 줄과 같은 문자열이 같은 diff의 삭제 줄에 있다는 사실은 옮긴 블록 후보를 찾는 단서로만 쓴다. 문자열만 같고 다른 함수·다른 문맥에 새로 쓴 줄은 추가 줄이며, 그 줄의 결함은 일반 리뷰 포인트로 올린다.
       - 확인은 테크 리뷰 2단계에서 읽은 삭제 줄로 한다. 이 확인 때문에 변경 전 파일을 따로 읽지 않는다.
     - 이번 변경이 결함을 드러내거나 악화시키면 일반 리뷰 포인트로 올린다. 어느 쪽인지 판단이 서지 않을 때도 일반 리뷰 포인트로 올린다.
     - 결과의 `## 변경 전부터 있던 결함` 섹션에 적고 "카테고리 건수·상태·판정 산출에 넣지 않습니다"를 적는다. `--status`·`--verdict`에 넘기는 위험도 목록에서 뺀다는 뜻이다.
     - 등급은 헬퍼로 산출하되 텍스트로만 적고 이모지를 붙이지 않는다. 요약에는 건수만 적는다.
  5. 결과 기록 단계 두 곳(비즈니스 리뷰 `### 3단계: 결과 기록`, 테크 리뷰 `### 4단계: 결과 기록`)에 기록 전에 `발견 처리`의 인용 위치 재확인을 거친다는 문장을 더한다.
  6. `## 상태 산출`과 `## 판정 산출`에 변경 전부터 있던 결함은 산출 입력에 넣지 않는다는 한 줄을 더한다. 표와 헬퍼 호출 예시는 고치지 않는다.
  7. `## 결과 기록 형식`을 고친다.
     - 기록 순서: 판정 한 줄 → 최종 의견 접기 → 요약 → PR 본문 대조 → 비즈니스 리뷰 → 테크 리뷰 → 변경 전부터 있던 결함.
     - 요약: `코드 레벨 검증` 줄(읽은 파일 수, 읽지 않은 파일 수, 읽지 않은 파일이 있으면 경로와 사유의 하위 행)과 `변경 전부터 있던 결함` 건수 줄.
     - PR 본문 대조: 리뷰어 확인 요청은 항목마다 답을 1~2문장으로 적는다. 완료의 정의 대조는 대조 표의 AC 행마다 PR 본문이 적은 상태와 리뷰에서 확인한 결과를 견줘 `일치(MATCH)`·`불일치(MISMATCH)`·`확인 불가(N/A)` 중 하나를 적는다. 항목이 없거나 브랜치 모드면 `해당 없음` 한 줄을 적는다.
       - 불일치의 처리: "불일치 자체는 리뷰 포인트로 올리지 않습니다"를 적는다. 불일치는 대조 표에만 적고 산출에 넣지 않는다는 뜻이다.
       - PR 본문이 충족으로 적었는데 성립하지 않는 항목은 그 원인을 비즈니스·테크 리뷰의 기존 기준으로 리뷰 포인트 하나로 올리고 근거 칸에 그 리뷰 포인트 제목을 적는다. 이미 올린 리뷰 포인트가 원인이면 새로 만들지 않는다.
       - PR 본문이 미충족·미검증으로 적었는데 리뷰에서 충족으로 확인한 항목은 표에만 적는다.
       - 대조 표 없이 요약 줄만 있으면 요약 줄을 한 행으로 적는다(AC 칸은 `요약`, PR 본문 상태 칸은 요약 줄 그대로). 연결 이슈 본문의 AC로 요약의 충족 수를 확인할 수 있으면 견준 결과를, AC를 확보하지 못했으면 `확인 불가(N/A)`와 사유를 적는다.
     - 비즈니스 리뷰: `PR 모드`에서 참조 문서가 없으면 섹션 첫 줄에 `참조 문서 없음:` 줄을 둔다고 적는다(규칙은 `문서 부재 시 처리`, Task 2의 7번).
     - 리뷰 포인트: 버그·보안·성능의 `실패 시나리오:` 줄과 `(확인 필요)` 표시는 `발견 처리`를 따른다고 적는다.
     - `## 산출물 접기 기준`의 항목별 접기 줄에 실패 시나리오(접기 안)와 `(확인 필요)`(접기 밖, 제목)를 반영한다.
  8. `git-review/templates/review-result-template.md`를 "고정 앵커"의 템플릿 표대로 고친다.
     - 맨 위 순서 주석을 새 기록 순서로 고친다.
     - `## 요약`: `- 검토 파일: N개` 다음에 `- 코드 레벨 검증: 읽은 파일 N개 · 읽지 않은 파일 M개`와 하위 행 `  - <경로>: <사유 — 잠금 파일 / 생성 파일 / 바이너리 / 읽기 실패>`를 두고, `- 변경 전부터 있던 결함: N건 (판정 산출 제외)`를 둔다. 하위 행은 읽지 않은 파일이 있을 때만 쓴다는 주석을 단다.
