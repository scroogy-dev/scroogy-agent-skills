#### F-4: PR 본문 불일치가 그 자체로 판정 입력이 된다

- **위험도**: 🟡 중간(MEDIUM)
- **영향 축**: 기능 저하
- **발생확률 축**: 통상 사용
- **카테고리**: 기능
- **관점**: 범위 · AC3 확장
- **계보**: 신규
- **권장 조치**: 자동 발견 등록의 범위를 승인받거나, 불일치는 대조 표에 기록하고 독립적으로 확인된 요구사항 위반·결함을 기존 기준으로 등급 산출에 반영한다.
- **완료 기준**:
  - PR 본문이 미충족이라고 적었으나 리뷰에서 충족으로 확인된 경우와, PR 본문이 충족이라고 적었으나 실제 결함이 있는 경우의 처리 결과를 각각 정한다.
  - 실제 결함을 기존 테크 리뷰에서 이미 찾은 경우 동일 결함을 대조 결과 때문에 두 번 집계하지 않는다. 갱신한 기준을 spec R2와 Task 4·6이 공유한다.

<details>
<summary>근거·상세 설명 펼치기</summary>

- AC3과 R2는 대조 결과를 리뷰에 표시하도록 한다. spec 162행과 plan 319행은 모든 `불일치(MISMATCH)` 항목을 리뷰 포인트로 올려 산출에 반영한다. 작성자가 보수적으로 미충족이라 표시한 AC가 구현에서 충족된 경우도 동일하게 발견으로 올라갈 수 있다.
- Task 6의 현행 사례는 이미 버그·보안·성능 리뷰 포인트로 올린 변경 줄의 결함이 AC 불일치의 근거다. 동일 근거를 다른 리뷰 포인트로 한 번 더 세는지에 대한 결정이 빠져 있다.

</details>

#### F-5: 라인 이동만으로 기존 결함이 이번 변경의 발견이 된다

- **위험도**: 🟡 중간(MEDIUM)
- **영향 축**: 스펙·기능 달성 차단
- **발생확률 축**: 특수 조건·엣지
- **카테고리**: 버그
- **관점**: 모호성 · AC13
- **계보**: 신규
- **권장 조치**: 기존 결함의 분류 기준을 base 대비 결함의 동작·도달 경로·영향으로 정한다. diff 줄 표시를 출처를 확인하는 근거로 사용한다.
- **완료 기준**:
  - 같은 결함이 이동·재배치됐고 동작·접근 범위·영향이 그대로인 경우 별도 섹션에만 나온다.
  - 이번 변경이 기존 결함의 경로를 열거나 영향 범위를 넓힌 경우 일반 발견으로 집계된다.
  - 기존 결함의 위험도가 나머지 발견보다 높은 케이스에서 그 결함을 산출 입력에 넣으면 상태 또는 판정 기대값이 달라지도록 하여 제외 규칙을 확인한다.

<details>
<summary>근거·상세 설명 펼치기</summary>

- plan 311행은 결함의 위치가 추가·수정 줄이 아닌 경우를 기존 결함의 필수 조건으로 둔다. 임시 Git 저장소에서 예전 파일의 문장을 새 파일로 이동하자 같은 내용이 삭제 줄과 추가 줄로 각각 표시됐다. 결함의 동작과 영향이 그대로인 이동도 이 조건으로는 기존 결함에서 빠진다. AC13은 변경 전부터 존재했는지를 기준으로 삼는다.
- Task 6은 변경 줄 밖의 기존 결함만 둔다. 세 일반 발견과 기존 결함의 상대 위험도도 지정하지 않아, 잘못된 입력을 추가해도 최고 위험도 기반의 종합 판정은 같은 값일 수 있다.

</details>

#### F-6: GitHub 폴백이 대상 식별 단계에 머문다

- **위험도**: 🟡 중간(MEDIUM)
- **영향 축**: 스펙·기능 달성 차단
- **발생확률 축**: 특수 조건·엣지
- **카테고리**: 아키텍처
- **관점**: 모호성 · GitHub 연동 계약
- **계보**: 신규
- **권장 조치**: `gh` 미설치·미인증 시 github.com에서 PR diff·커밋·연결 이슈·SHA 기준 파일 읽기를 어떤 가용 수단으로 완료할지 정한다. 수집에 실패한 경우 완료로 집계하기 전에 누락 입력과 중단 여부를 명시한다.
- **완료 기준**:
  - `gh`를 사용할 수 없지만 GitHub MCP 또는 로컬 객체가 있는 경우 어떤 입력을 어떻게 수집하는지 단계를 따라갈 수 있다.
  - 필수 diff를 얻지 못한 경우 빈 변경으로 보고하거나 코드 레벨 검증 완료로 기록하지 않는다. MCP를 사용할 수 없는 호스트에서도 중단 사유가 드러난다.

<details>
<summary>근거·상세 설명 펼치기</summary>

- plan 206행은 `gh`를 쓸 수 없으면 계약의 폴백을 따르도록 한다. 뒤의 208·212행은 각각 `gh pr diff`·`gh issue view`와 `gh api`를 지정한다. 계약은 CLI 우선과 MCP 호스트 범위를 정하고, 이 리뷰에 필요한 개별 수집 작업의 폴백 실행 순서나 누락 처리까지 정하지는 않는다.
- 동일 폴백으로 대상을 식별했더라도 diff와 이슈 본문 수집 단계에 가면 다시 `gh`를 전제로 한다. 이 세션의 GitHub MCP에는 PR diff·커밋 조회와 SHA를 받는 파일 읽기가 있어, 가용 수단과 사용 조건을 스킬 본문에 명시할 수 있다. Task 7의 정상 연결 사례는 이 경로를 확인하지 않는다. [GitHub 연동 계약](../../../30_contract/github-integration.md)

</details>

#### F-7: 완료의 정의 요약만 있는 PR의 대조 결과가 정의돼 있지 않다

- **위험도**: 🟡 중간(MEDIUM)
- **영향 축**: 스펙·기능 달성 차단
- **발생확률 축**: 특수 조건·엣지
- **카테고리**: 기능
- **관점**: 범위 · AC3 완화
- **계보**: 신규
- **권장 조치**: 완료의 정의 대조가 요약 줄만 있는 경우에도 PR이 주장한 값과 확인 결과 또는 확인 불가 사유를 출력하는 형식을 정한다.
- **완료 기준**:
  - 리뷰어 확인 요청 없이 완료의 정의 요약만 있는 PR도 `## PR 본문 대조`에 요약의 대조 결과가 나온다.
  - 기준 이슈나 세부 근거를 확보할 수 없는 경우 PR의 요약과 확인 불가 사유가 기록된다.

<details>
<summary>근거·상세 설명 펼치기</summary>

- AC3은 두 항목 중 하나라도 있으면 대조 결과를 요구한다. plan 217행은 완료의 정의 요약 줄과 AC 표를 모두 수집한다. 319·325행의 산출 형식은 AC별 상태 대조 표로만 정의돼 있어, 요약만 있는 경우 이미 수집한 값을 어디에 어떤 근거로 기록할지 정해져 있지 않다.
- spec 162행의 실행 채점은 두 항목이 있는 PR로 한정된다. Task 7의 PR #141에는 두 항목과 AC 표가 모두 있다. 형식이 간단한 다른 PR은 그 검증을 통과하고도 대조 결과에서 빠질 수 있다.

</details>
