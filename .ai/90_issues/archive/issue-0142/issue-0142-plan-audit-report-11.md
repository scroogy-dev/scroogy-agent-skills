#### F-30: 커밋 101개부터 PR의 커밋 메시지가 빠진다

- **위험도**: 🟡 중간(MEDIUM)
- **영향·발생확률**: 스펙·기능 달성 차단 × 특수 조건·엣지. R1은 PR 커밋 메시지를 수집 대상으로 삼고 개수 제한을 두지 않는다.
- **카테고리·관점·계보**: 기능 · 범위(AC1) · 신규
- **권장 조치**: 마지막 페이지까지 수집하는 절차와 수집 도중 PR이 갱신됐을 때의 재조회 기준을 Task 2에 명시한다.
- **완료 기준**: (1) 고정한 PR에 서로 다른 메시지를 가진 커밋 101개가 있으면 마지막 메시지까지 한 번씩 수집한다. (2) 다음 페이지 조회 실패를 수집 완료와 구별한다.

<details>
<summary>CLI 버전과 판정 근거</summary>

#### F-31: 두 파일의 이름이 변경 목록에서 같은 값으로 합쳐진다

- **위험도**: 🟡 중간(MEDIUM)
- **영향·발생확률**: 스펙·기능 달성 차단 × 특수 조건·엣지. AC2의 파일 식별과 AC9의 근거 확인이 이 이름 조합에서 성립하지 않는다.
- **카테고리·관점·계보**: 버그 · 모호성 · F-28 잔여(파일별 기록)
- **권장 조치**: 표시 문자열에서 원래 경로를 유일하게 식별할 수 있도록 목록과 조회 규칙을 함께 정한다.
- **완료 기준**: 두 경로를 같은 변경 유형으로 함께 수정했을 때 결과에서 각각 식별된다. 각 경로를 조회하면 해당 파일의 고유한 기준 줄이 나오거나, 조회할 수 없는 파일만 정확히 확인 필요로 남는다.

<details>
<summary>같은 목록 행과 서로 다른 Git 객체</summary>

한 이름은 `line`과 `feed.txt` 사이에 실제 줄바꿈이 있다. 다른 이름은 큰따옴표로 시작하고 끝나며 중간에 역슬래시와 문자 n이 있다. Task 1의 규칙을 로컬 Git 출력에 적용하면 두 행 모두 아래와 같다. 구분자는 탭 한 개다.

```text
M	"line\nfeed.txt"
M	"line\nfeed.txt"
```

두 파일의 기준 커밋 첫 줄을 각각 `marker 3`, `marker 4`로 둔 뒤 목록의 이름을 그대로 조회하자 두 경우 모두 `marker 4`를 읽었다. 인용 형태면 조회를 생략해도 어느 파일을 생략할지 행만으로 구분할 수 없다. F-29는 인덱스 표지 조회 명령에서 발생한다. 이 충돌에는 인덱스 표지가 필요 없다.

</details>

#### F-29: 표시한 경로 조회에서 줄바꿈 파일을 둘로 나눈다

- **위험도**: 🟢 낮음(LOW)
- **영향·발생확률**: 기능 저하 × 특수 조건·엣지. 주변 코드 탐색의 표지 목록이 틀릴 수 있다. 최종 확인에는 patch·merge-base를 읽는 절차가 있다.
- **카테고리·관점·계보**: 버그 · 모호성 · 같은 회차 Gemini F-29를 재현
- **권장 조치**: 기본 처리는 원장 이관이다. 보정한다면 표시 문자를 NUL 레코드 단위로 검사한다.
- **완료 기준**: 수용 시 원장에 사유·재검토 조건을 기록한다. 보정 시 줄바꿈 다음에 `h `가 있는 일반 파일은 제외되고, 줄바꿈이 있는 표시 파일은 하나의 전체 경로로 식별된다.

<details>
<summary>로컬 재현</summary>

표시하지 않은 파일의 이름을 `foo〈줄바꿈〉h bar.txt`, skip-worktree 파일의 이름을 `line〈줄바꿈〉feed.txt`로 뒀다. 계획의 `git ls-files -v -z | tr '\0' '\n' | grep '^[a-zS] '`가 `h bar.txt`와 `S line`을 반환했다. 첫 행은 실제 표시가 없고 둘째 행은 파일명의 뒷부분을 잃었다.

</details>

#### F-32: 경로 조회 검사의 대조 문장이 patch 헤더에도 나타난다

- **위험도**: 🟢 낮음(LOW)
- **영향·발생확률**: 기술 품질 의견 × 통상 사용. 명령이 목록의 경로로 `git show`를 직접 호출하므로 인용 문자열을 잘못 넘기면 여전히 검사가 실패한다. 약해진 부분은 대조 문장을 patch에서 읽을 수 없다는 시험 전제다.
- **카테고리·관점·계보**: 테스트 · 모호성 · F-28 잔여(검증 사례)
- **권장 조치**: 대조 문장이 patch 전체에서 사라지도록 입력을 조정하고, hunk 헤더까지 포함해 확인한다.
- **완료 기준**: (1) 올바른 경로로 merge-base에서 고유 문장을 읽는다. (2) 그 문장이 patch 본문이나 헤더에 한 번이라도 나타나면 해당 전제 검사가 실패한다.

<details>
<summary>spec 307행 사례의 검증 명령 재현</summary>

spec과 같이 첫 줄을 `base line`, 다음 다섯 줄을 숫자로 두고 끝에 `added`를 추가했다. Git 2.50.1은 `@@ -4,3 +4,4 @@ base line`을 냈다. spec의 `grep -qxF ' base line'`은 종료 코드 1을 반환해 대조 문장이 실제 patch에 있어도 위반을 보고하지 않았다.

</details>
