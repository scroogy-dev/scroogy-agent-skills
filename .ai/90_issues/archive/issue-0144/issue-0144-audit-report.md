### 상세 분석

#### F-12: 설정 응답에서 기존 중단점임을 확인할 수 있어도 정리 목록에 들어간다

- **위험도**: 🟢 낮음(LOW)
- **영향 축**: 기능 저하. 다른 에이전트가 걸어 둔 중단점 하나가 사라져 다시 설정해야 한다.
- **발생확률 축**: 특수 조건·엣지. 두 세션이 같은 IDE에서 같은 예외 클래스나 메서드 패턴을 사전 조회와 설정 사이에 함께 다뤄야 한다.
- **카테고리**: 버그
- **관점**: 엣지케이스(동시 설정)
- **계보**: 기등재 K-0038 재제기 · F-11 잔여. 원장이 재검토 조건으로 지정한 신규 생성 여부를 두 도구의 반환 명세에서 직접 확인했다. 버전 변경이나 실제 중단점 유실 사례를 전제로 삼지 않았다. [K-0038](../../../70_ledger/active/K-0038-debug-breakpoint-precheck-race.md)
- **권장 조치**: 기존 K-0038의 재검토 이력에 반환 계약을 기록한다. 삭제 후보는 설정 호출에서 새로 생성했다고 확인한 ID로 한정하고, 이미 적용된 설정 덮어쓰기는 경합의 잔여 범위로 기록한다.
- **완료 기준**
  1. 같은 대상이 사전 조회되면 설정을 건너뛰고 삭제 후보에도 추가하지 않는다.
  2. 예외·메서드 설정 응답이 `created=true`인 B와 `created=false`인 A를 함께 받아도 정리 요청에는 응답 ID B와 `owner=agent`만 들어간다. 후속 조회로 A를 다시 추가하지 않는다.
  3. 모든 응답이 `created=false`이면 정리 요청은 0건이다. 반환 필드를 확인할 수 없는 환경에서도 생성 주체가 확인되지 않은 ID는 자동 삭제에서 제외한다.

<details>
<summary>도구 반환 명세와 판단 범위 펼치기</summary>

| IntelliJ MCP 설정 도구 | 이번 세션에서 확인한 필수 반환 필드 |
|---|---|
| `jvm_debug_set_exception_breakpoint` | `created: boolean`, `breakpointId: string` |
| `jvm_debug_set_method_breakpoint` | `created: boolean`, `breakpointId: string` |

두 도구 모두 `created=false`를 기존 중단점의 설정을 다시 쓴 경우로 정의한다. 새 규칙의 대상별 목록 조회는 같은 종류의 다른 중단점을 구별하지만, 같은 대상에 대해 어느 호출이 중단점을 만들었는지는 알려 주지 않는다. 다른 세션이 만든 agent 중단점도 ID와 `owner=agent` 삭제 조건을 만족한다.

이 응답은 설정 후에 돌아온다. 이미 덮어쓴 설정을 보호하려면 사전 조회가 여전히 필요하며, 원자적 조건부 생성이 없는 동안 그 경합은 남는다. 이번 재제기의 범위는 후속 삭제다. 현행 R6은 이 경합을 명시적으로 수용했으므로 요구사항은 충족으로 판정했다. 원장의 수용 영향과 발생 조건도 유지했다.
