### 상세 분석

#### F-10: changelist 도구의 결정 변경을 일치 검사가 놓친다

- **위험도**: 🟡 중간(MEDIUM)
- **영향 축**: 스펙·기능 달성 차단 · **발생확률 축**: 특수 조건·엣지
- **카테고리**: 기능 · **관점**: 추적성·범위 · **관련 AC**: AC11·17 · **계보**: 신규
- R9는 `changelist 도구`라는 묶음 표기를 허용한다. R14는 백틱 안의 개별 도구 이름만 읽는다. `delete_changelist`의 결정을 `쓰지 않음`에서 `보류`로 바꾸면 요청 전용이라는 본문과 어긋나도 나머지 목록이 정상이라면 네 조건이 모두 성립한다.
- **권장 조치**: 요청 전용인 changelist 도구를 개별 이름으로 연결하거나 묶음의 구성원을 검사에 명시한다. 읽기 전용 `get_changelists`의 분류는 Task 3의 사용자 결정에 따른다.
- **완료 기준**:
  - 변경 목록을 수정하는 도구를 요청 전용으로 분류한 정상 사본이 통과한다.
  - 같은 사본에서 `delete_changelist`의 결정만 `보류`로 바꾸면 일반 `run-tests.sh`가 실패한다.

#### F-11: 로그 지점만 쓰는 디버깅도 일시 정지를 기다린다

- **위험도**: 🟡 중간(MEDIUM)
- **영향 축**: 기능 저하 · **발생확률 축**: 통상 사용
- **카테고리**: 기능 · **관점**: 모호성 · **관련 AC**: AC6 · **계보**: 신규
- R5는 값을 기록할 때 `suspendPolicy=NONE`을 쓰도록 한 뒤 모든 세션에서 `WAIT_FOR_PAUSE`로 기다리게 한다. 로그 지점만 있는 장기 실행 프로그램에서는 값이 기록되어도 그 지점이 일시 정지를 일으키지 않아 대기가 시간 초과될 수 있다.
- **권장 조치**: 정지 중단점이 있을 때만 멈춤을 기다리고, JVM 로그 지점만 쓸 때는 같은 세션의 `DRAIN_EVENTS`로 기록을 읽는 절차를 둔다.
- **완료 기준**:
  - 일반 중단점에서는 정지 후 스택·프레임·식 평가 순서를 따른다.
  - 로그 지점만 있으면 일시 정지를 기다리며 진행을 막지 않고 같은 세션에서 기록한 값을 확인한다.

#### F-12: 서버 구성 선택에 필요한 필드가 지정되지 않았다

- **위험도**: 🟡 중간(MEDIUM)
- **영향 축**: 스펙·기능 달성 차단 · **발생확률 축**: 특수 조건·엣지
- **카테고리**: 보안 · **관점**: 모호성·도메인 정합성 · **관련 AC**: AC5 · **계보**: 신규
- `get_run_configurations()`의 각 구성에는 이름 외에 `environment`와 `commandLine`이 포함될 수 있다. 구성 이름이 없는 기존 repo에서 반환 목록을 그대로 표시하면 설정에 든 자격 증명이 대화 기록에 들어갈 수 있다. 이번 감사에서는 도구 정의로 이 경로를 확인했다.
- **권장 조치**: 선택지에는 `configurations[].name`만 전달하도록 정한다. 호출 결과를 가공할 수 있는 환경에서는 원시 반환값을 대화에 출력하기 전에 이름만 추린다.
- **완료 기준**:
  - 이름과 임의의 환경 변수·명령행이 함께 있는 모의 결과에서 구성 이름만 사용자에게 표시된다.
  - 사용자가 고른 이름으로 서버를 시작할 수 있다.

#### F-13: 종료 코드는 있지만 전체 로그가 없을 때 테스트 판정이 비어 있다

- **위험도**: 🟡 중간(MEDIUM)
- **영향 축**: 스펙·기능 달성 차단 · **발생확률 축**: 특수 조건·엣지
- **카테고리**: 기능 · **관점**: 모호성 · **관련 AC**: AC4 · **계보**: 신규
- `execute_run_configuration`에서 `fullOutputPath`는 선택 필드이고 `output`은 앞 10,000자에서 잘릴 수 있다. 종료 코드 0과 잘린 미리보기만 있으면 R2가 요구하는 실패 건수를 알 수 없다. R2는 `exitCode`가 없을 때의 처리만 정했다.
- **권장 조치**: 실패 건수를 확인할 수 없을 때의 판정을 R2에 명시한다.
- **완료 기준**:
  - 종료 코드와 완전한 로그가 있으면 원래 두 근거로 판정한다.
  - 종료 코드 0, 전체 로그 경로 없음, 실패 건수를 확인할 수 없는 미리보기 조합을 통과로 기록하지 않는다.

#### F-14: 업데이트 때 사라진 도구를 결정 목록에서 정리하는 단계가 빠졌다

- **위험도**: 🟢 낮음(LOW)
- **영향 축**: 기능 저하 · **발생확률 축**: 특수 조건·엣지
- **카테고리**: 기능 · **관점**: 범위·모호성 · **관련 AC**: AC17·18·25 · **계보**: 신규
- 계획한 유지 절차는 새 도구를 결정하고 목록 사본과 메타데이터를 갱신한다. 도구가 하나 사라진 경우 그대로 따라가면 결정 표에 옛 행이 남아 같은 목록으로 대조해도 다시 종료 1이다. 규칙에 그 도구가 있으면 본문도 함께 고쳐야 한다.
- **권장 조치**: 삭제와 이름 변경 시 결정 표와 해당 규칙의 참조를 함께 정리하고 대조를 다시 실행하도록 적는다.
- **완료 기준**:
  - 삭제만 있는 예에서 옛 행을 정리한 뒤 같은 목록 대조가 무출력·종료 0이다.
  - 우선 도구의 이름이 바뀐 예에서는 갱신한 결정 표와 규칙이 내부 일치 검사도 통과한다.

#### F-15: ADR 0023의 별도 인수 조건이 AC25에 연결돼 있다

- **위험도**: 🟡 중간(MEDIUM)
- **영향 축**: 기능 저하 · **발생확률 축**: 통상 사용
- **카테고리**: 테스트 · **관점**: 범위·AC 확장 · **관련 AC**: AC25 · **계보**: 신규
- AC25는 결정 이력, 도구 목록 위치, 재비교 계기를 요구한다. 새 R21 검사는 ADR 0023의 로컬 서버 절과 테스트 라우팅까지 AC25 통과 조건에 넣었다. 이슈에는 이 결과가 없고 spec 90행도 추가 근거를 1차 F-6으로 적는다.
- **권장 조치**: ADR 정합화 작업은 유지하고, 이를 독립 인수 조건으로 승인할지 Task 5의 구현 검증으로 둘지 정한다.
- **완료 기준**:
  - 인수 조건으로 유지하면 별도 결과의 승인과 출처를 연결한다. 구현 검증이면 AC25 충족 건수에서 분리한다.
  - 기존 AC25의 결정 이력·목록 위치·재비교 계기는 계속 검증한다.
