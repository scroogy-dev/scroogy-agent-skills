# git-pr 스킬 단독 점검 보고서

- **대상**: `git-pr/SKILL.md` (189줄, 단일 파일 / 하위 `references/`·`templates/` 없음)
- **관점**: 이전 보고서와 무관하게 git-pr 하나를 처음 감사하는 독립 감사 관점
- **방식**: 파일 미수정. 프론트매터는 인라인 검증 스크립트(PyYAML)로 파싱·검증. 참조 경로 실존 여부 및 인접 스킬 13종 description 대조.
- **작성일**: 2026-06-16 (요청 파일명 기준일 2026-06-12)

## 종합 판정

전반적으로 **양호**하나, **반드시 고쳐야 할 모순 1건**이 있다. 본문 "테크 관점 > 호출 흐름" 지침은 **ASCII 트리 다이어그램 + `Class#method` 표기**를 강제하는데, 같은 문서 하단의 "작성 예시(템플릿)"는 **화살표 체인 + `Class.method()` 표기**를 보여준다. 예시를 모방하는 모델은 지침을 위반한 산출물을 만들게 된다. 그 외에는 description 트리거 보강(중하)과 문서 동기화 점검 섹션의 범위·토큰 비대(저)가 개선 후보다.

현재 description: `PR 제목과 메시지를 정책에 맞게 작성합니다. PR 작성, pull request, PR 메시지 작성 시 사용합니다.`

| 점검 항목 | 발견 사항 | 심각도 | 판정 |

| 다양한 표현 트리거 | "PR 설명 좀 써줘", "리뷰어가 보기 쉽게 정리해줘" 같은 우회 표현에서 언더트리거 가능성 | 중하 | 주의 |

## 기준 5 — 인접 스킬과 트리거 중복/충돌

| 점검 항목 | 발견 사항 | 심각도 | 판정 |
|-----------|-----------|--------|------|
| git-pr ↔ git-commit | 역할 분리 명확(PR 메시지 vs 커밋 메시지). 본문이 "PR 제목은 git-commit 형식 준수"로 의존을 명시 | — | 정상 |
| git-pr ↔ git-review | 둘 다 "PR" + "비즈니스/테크" 프레이밍 공유. 단 트리거어가 `작성` vs `리뷰/코드 리뷰`로 구분됨. "PR 봐줘"류 모호 입력에서만 경합 가능 | 저 | 정상(의도된 일관성) |
| git-pr ↔ git-qa | git-qa가 git-pr을 "참고"로 명시. QA 체크리스트 vs PR 메시지로 산출물 구분 명확 | — | 정상 |
| git-pr ↔ git-review-context | review-context는 "리뷰 전 사전 분석"으로 트리거·산출물 모두 구분 | — | 정상 |
| git-pr ↔ issue-audit | issue-audit는 구현 감사/검증으로 영역이 멀다 | — | 정상 |

판정: **통과**. 경계가 대체로 분명하며, git-review와의 "비즈니스/테크" 프레이밍 공유는 충돌이 아니라 저장소 전반의 의도된 일관성이다.

## 수정 방안 (우선순위순)

### P1 — 호출 흐름 표기 모순 해소 (중상)
"작성 예시(템플릿)"의 호출 흐름(144–145행)을 본문 지침(98–115행)과 동일한 **ASCII 트리 + `Class#method` + `├──/└──` + `# 설명`** 형식으로 교체한다. 예:
```
- 주문 생성:
  OrderController#create
  ├── OrderValidator#validate   # 필수 필드·재고 검증
  └── OrderService#process      # 주문 트랜잭션
      ├── InventoryCache#get     # 캐시 우선 조회
      └── OrderRepository#save (DB)
```
대안으로 둘 중 하나의 표기를 "허용 형식"으로 공식화하고 양쪽을 그 기준에 통일한다(단, 트리 형식이 추적성 측면에서 본문 의도에 부합).

### P2 — description 트리거 보강 (중하)
키워드 변형을 추가하고 어조를 약간 강하게 한다. 예시:
`PR 제목과 메시지를 정책(Conventional Commits + 이슈별 비즈니스/테크 섹션)에 맞게 작성합니다. PR 작성, PR 메시지/설명 작성, pull request, 풀리퀘스트, PR 올리기 전 정리, 리뷰어용 설명 정리 시 사용합니다. PR을 올리기 직전이거나 변경 사항을 리뷰어에게 설명해야 할 때 사용하세요.`
"PR을 실제로 생성/제출하는 기능이 아니라 *메시지 텍스트 작성*"임을 한 구절로 명확히 하면 경계 모호성도 해소된다.

### P3 — 명시적 실행 절차 추가 (중하)
본문 상단(또는 "작성 시점 및 주체" 뒤)에 번호 매긴 절차 요약을 둔다: ①공통 규칙·index 선택 적재 → ②PR 제목 → ③이슈 목록 → ④이슈별 비즈니스/테크 섹션 → ⑤마지막 패스로 문서 동기화 점검 1회. 모델이 순서를 추론하지 않고 따르게 된다.

### P4 — "문서 동기화 점검" 축약/분리 (저~중)
33줄 규모의 drift 표·승인형 절차가 본문 비중을 키운다. 핵심 규칙만 남기고 상세 표·승인형 흐름은 `references/doc-sync.md`로 분리하거나 3~4줄로 요약한다. 다만 단일 파일 유지가 설치·이식에 유리하므로, 분리보다 **축약**을 우선 권장.

### P5 — ADR/contract/domain 경로 안내 중복 정리 (저)
"참조 문서"(17–22행)와 "테크 관점 > 참고사항"(117–119행)의 경로 안내가 겹친다. 한쪽(참조 문서 섹션)에 모으고 다른 쪽은 포인터만 남긴다.

- 표기 모순 근거: 지침 101행(`Class#method`, `├──/└──`) vs 예시 144–145행(`Class.method()`, `->`).
