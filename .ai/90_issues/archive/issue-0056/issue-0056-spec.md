# Issue #56 스펙 issue-model-triage 구현 역할 추천을 역량 기반 토큰 효율 방식으로 전환

## 목표 (Goal)

`issue-model-triage`의 구현 역할 추천이 이슈의 구현 난이도를 별도 평가해 "역량이 충분한 최소 모델"을 배정하도록 바꾸고, "플랜·구현 같은 모델 기본"(세션 캐시 이점) 규칙을 판단 기준에서 제거한다.

---

## 범위 (Scope)

**포함 (In)**

- `issue-model-triage/SKILL.md`의 `## 판단 로직` 개편 — `### 구현 난이도 평가` 절 신설(신호는 Task 0에서 확정), `### 분류 기준`의 분류 결과별 추천 규칙 갱신
- `### 제약 검증` 갱신 — "플랜·구현 같은 모델 기본" 제약과 세션 캐시 근거 삭제, 벤더 제약 처리 방향 반영(Task 0에서 확정)
- `### 제약 검증`의 검증 역할에 **역량 하한 추가** — 구현에 배정한 모델과 최소 동급 이상 (3차 audit F-1로 범위 확장, 아래 `## 전제 (Assumptions)` 참조)
- `## 출력`·`## 예시`의 정합 갱신 — 캐시·같은 모델 근거 잔존 제거, 예시 1·3의 구현 행 선정 사유 재작성

**비포함 (Out)**

- 검증 역할의 타모델·타벤더 제약(교차모델 audit 전제) 완화·삭제 — 그대로 유지한다 (역량 하한 **추가**는 위 포함(In)으로 이동)
- `## 입력` 절(이슈 내용·후보 모델 확보 방식) 변경
- 다른 스킬 문서·AI-CONTEXT.md 스킬 목록 변경 (한 줄 설명은 추천 방식 변경의 영향을 받지 않음)
- 산출 스크립트·코드 추가 (문서 전용 스킬 유지)

## 완료의 정의 (Definition of Done)

> **검증 레벨** — 낮을수록 좋다(자동 검증에 가까움). 기본은 L1, 한 레벨 내릴 때마다 강등 사유를 함께 적는다.
>
> - `[D]`  L1 결정적   — 명령이 합/불을 판정, 사람 판단 없음
> - `[QD]` L2 준결정적 — 다른 AI·기준 체크리스트가 채점
> - `[ND]` L3 비결정적 — 사람이 직접 읽고 판단

- [x] [D] 캐시 우선 규칙이 문서에서 제거됨 — 잔존 문구 0건  (검증: repo 루트에서 `! grep -qE '캐시|같은 모델을 기본|플랜·구현 같은 모델' issue-model-triage/SKILL.md` 종료 코드 0. `grep -c … 출력 0`은 무일치 시 종료 코드가 1이라 자동화에서 거짓 실패가 된다)
- [x] [D] 구현 난이도 평가 절이 존재  (검증: repo 루트에서 `grep -cE '^### 구현 난이도 평가$' issue-model-triage/SKILL.md` 출력 1)
- [x] [D] 검증 역할 제약(다른 모델 + 다른 벤더) 유지  (검증: repo 루트에서 `grep -cE '^- \*\*검증\*\*: .*다른 모델 \+ 다른 벤더' issue-model-triage/SKILL.md` 출력 1)
- [x] [D] 검증 역할에 역량 하한(구현과 최소 동급 이상) 존재 — 검증 제약 행 총 1개이고 그 행이 타모델·타벤더·동급 이상 3조건을 모두 포함  (검증: repo 루트에서 `[ "$(grep -cE '^- \*\*검증\*\*:' issue-model-triage/SKILL.md)" = 1 ] && grep -qE '^- \*\*검증\*\*: .*다른 모델 \+ 다른 벤더.*동급 이상' issue-model-triage/SKILL.md` 종료 코드 0. 조건 포함 여부만 보면 검증 행이 여러 개로 갈라져 조건이 분산돼도 통과하므로 행 총개수를 함께 고정한다)
- [x] [QD] 구현 난이도 신호가 이슈 분류 4신호(설계 판단용)와 독립된 별도 정의이고, 추천 규칙이 "충분한 최소 역량 모델" 취지에 부합  (검증: 교차모델 audit 채점)  ← 강등 사유: 신호 정의의 독립성과 취지 부합은 의미 판단이라 명령으로 환원 불가
- [x] [QD] `## 출력`·`## 예시`(1~4)가 새 판단 로직의 분류 → 구현 난이도 평가 → 제약 검증 흐름과 정합  (검증: 교차모델 audit 채점)  ← 강등 사유: 예시 서술과 규칙의 정합성은 의미 대조라 명령으로 환원 불가

## 전제 (Assumptions)

- 이슈의 열린 설계 질문 3건은 구조 생성 시점에 미확정이었으며, Task 0(구현 시작 게이트)의 사용자 질의로 아래와 같이 **확정**했다.
  1. **구현 난이도 신호 정의** — 신호 3종 + 등급 3단계로 정의한다.
     - 신호: **변경 범위**(건드릴 파일·모듈 수와 산재 정도), **맥락 의존도**(기존 코드·문서를 얼마나 읽고 이해해야 하는가), **로직 복잡도**(알고리즘·상태·예외 경로의 까다로움)
     - 등급: 낮음(LOW) / 보통(MEDIUM) / 높음(HIGH) — 그 등급을 감당하는 **최소 역량 후보**를 구현에 배정한다.
     - 분류 4신호의 "완료 기준 비결정성"은 독립성 요구 때문에 난이도 신호로 재사용하지 않는다.
  2. **벤더 제약 처리** — "플랜·구현은 벤더를 섞지 않음" 제약을 **삭제**한다. 벤더를 묶으면 최소 역량 모델 선택지가 후보 일부로 좁아져 역량 기반 배정 취지와 충돌한다. 타이브레이커·선호로도 남기지 않으며, 벤더 제약은 검증 역할(타벤더)에만 남는다.
  3. **예시 갱신 범위** — 예시 1·3은 재작성하고, 예시 2·4는 새 축과의 정합에 필요한 최소 수정만 허용한다. 예시는 **4개를 유지**한다(추가·삭제 없음). 예시 1은 "설계 판단 필요 + 구현 난이도 보통(MEDIUM)"으로 조정해 플랜(최상위)과 구현(중위)이 갈리는 모습을 보이고, 예시 3은 선정 사유를 난이도 기준으로 교체한다.
- 판정 보류 원칙은 난이도 평가에도 동일 적용한다 — 이슈 내용이 얇아 난이도 신호를 가릴 수 없으면 단정하지 않고 보류한다 (현행 `### 분류 기준`의 "확신이 서지 않으면 질의" 철학과 같은 취지).
- 모델 목록·역량 등급표 하드코딩 금지 원칙(현행 SKILL.md `### 분류 기준`의 안내)은 신설하는 `### 구현 난이도 평가` 절에도 동일 적용한다 — 난이도 신호는 이슈 속성으로 정의하고, 특정 모델명 기준을 문서에 남기지 않는다.
- 분류·등급 값 표기는 한글 우선 병기 관례를 따른다 (예: 높음(HIGH)) — issue #45→#46 선례의 repo 관례로, 대상 문서에는 명시되어 있지 않다.
- **검증 역할 역량 하한 추가는 3차 audit F-1로 범위를 확장한 결정이다** (2026-07-28, `--response` 사용자 승인). 배경과 선택 근거는 아래와 같다.
  - **경위**: 구현 축에 난이도 평가를 신설하면서 플랜·구현은 "일을 감당하는 최소 역량"으로 배정하는데 검증만 역량 축이 없는 비대칭이 드러났다. 예시 1이 구현 중위 + 검증 하위 조합을 명시해 `issue-work/templates/issue-plan-template.md`의 audit 모델 조건(다른 벤더 + **최소 동급 이상 역량**)과 충돌했다. `origin/main`의 예시 1도 같은 위반이었으므로 이번 이슈의 회귀가 아니라 기존 공백이 가시화된 것이다.
  - **하한의 축**: 검증 난이도는 구현 난이도에 종속되므로(구현 산출물의 허점을 찾는 일) 하한을 **구현에 배정한 모델과 동급 이상**으로 잡는다. 구현 모델 자체가 난이도를 감당하는 최소 역량이라 결국 구현 난이도 축으로 환원되며, 세 역할이 모두 "일을 감당하는 최소 역량" 구조로 통일된다.
  - **만족 불가 시 처리**: 타벤더 후보 전체가 동급 이상에 미달하면 **하한 아래로 내려가 대체하지 않고 실패로 안내**한다 — 내림을 허용하면 하한이 사실상 무력해지고, 분기를 늘리는 것도 경량 스킬 취지에 어긋난다. 동급 후보가 없어 그 위에서 가장 낮은 후보를 고르는 것은 하한을 지킨 정상 선택이며 이 금지 대상이 아니다 (4차 audit F-1로 표현 정정 — 처음에는 금지 대상을 "상위로 올리기"로 잘못 적어 예시 1과 모순됐다). 추천 불가 빈도가 올라가는 것은 감수한 대가다.
  - **참조 원천**: 하한 규정은 지금까지 `issue-plan-template.md:106` 한 곳에만 있었다. 이 변경으로 `issue-model-triage`가 같은 규칙을 함께 말하게 되며, 두 문서의 문구 통일 자체는 이번 범위 밖이다.
- DoD의 "캐시 잔존 0건"은 설명성 언급도 남기지 않는다는 결정을 포함한다 — 규칙 제거의 이력은 이 이슈 문서와 git 이력이 담당하므로 SKILL.md 본문에는 남기지 않는다. Task 0에서 설명 문구 불필요로 확정했다(DoD 갱신 없음).
