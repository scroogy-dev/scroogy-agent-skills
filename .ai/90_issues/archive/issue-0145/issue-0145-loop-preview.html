이슈 #145 루프 예상안

이슈 본문(2026-11-23)의 범위와 완료의 정의(AC, Acceptance Criteria)를 그림으로 옮겼다. 본문이 정하지 않은 곳은 가정으로 그렸고 7절에 모았다. spec을 쓰기 전에 보는 자료이며 승인된 내용이 아니다.

1. 한눈에 보기

다섯 단계를 차례로 지나는 것이 한 회차다. 완료 확인에서 사용자가 다음 회차로 정하면 계획 수립으로 돌아간다.

지금 흐름과 다른 곳

지금 계획 수립→ 계획 검증 (한 번, 선택)→ 구현→ Task N: 교차 감사와 보정 반복→ 끝
  • 교차 감사가 Task N에서 4단계로 옮겨 간다. Task N은 완료 확인을 지난 뒤 한 번 하는 마무리만 맡는다.
  • 돌아가는 길이 생긴다. 감사 발견을 고치는 일은 다음 회차의 새 Task가 되고, 앞 Task 블록에 쌓이지 않는다.
  • 색인, 판 올리기, PR은 루프 밖에서 한 번만 한다. 보정에 맞춰 문서를 다시 고치는 커밋이 줄어든다.

2. 단계별로 하는 일

단계하는 일이 단계를 하는 조건실행AC
1 계획 수립 spec·plan이 없으면 쓴다. 지난 회차에서 바꿀 것이 나왔으면 고친다. 발견을 고치는 Task는 plan 끝에 이어 붙인다. 같은 종류의 발견이 이어지면 설계 결정부터 고친다. 회차마다 구현 AI. 요구사항, 확장, 완화는 사용자 승인 AC8, AC13, AC14
2 계획 검증 계획 감사를 받고 --response로 검토한다. 지난 검증 뒤에 AC·요구사항, 설계 결정, 테스트 계획 가운데 하나가 바뀌었을 때. 기존 AC 안에서 발견을 고치는 Task만 더했으면 건너뛴다. 사용자 (다른 벤더 모델) AC9
3 구현 Task마다 테스트 작성, 실패 확인, 구현, 통과 확인 순서로 진행한다 (4절). 닫지 않은 Task가 있을 때 구현 AI AC6, AC7
4 구현 검증 교차 감사를 전체 범위로 받고 --response로 검토한다. 발견마다 종류를 붙인다. 지난 검증 뒤에 구현이 바뀌었을 때 사용자 (다른 벤더 모델) AC10, AC12
5 완료 확인 마지막 교차 감사 리포트의 1단계 상태, 2단계 상태, 종합 판정과 plan 테스트 계획의 확인한 줄 수를 보인다. 1단계 상태가 충족이고 2단계 상태가 통과나 주의이며 모든 줄을 확인했고 반영으로 정한 발견을 모두 닫았으면 마무리를, 그 밖은 다음 회차를 권장한다. summary 루프 기록에 한 줄을 적는다. 기준에 못 미친 채 나가면 남은 항목마다 완화·원장·새 이슈 가운데 결정을 받는다. 회차마다 구현 AI가 기준대로 권장을 내고 사용자가 지날지 정한다 (2026-11-23 대화) AC11
Task N 전체 회귀, 색인(코드맵), --clear, PR을 한다. PR 뒤의 리뷰 피드백은 git-pr-feedback으로 처리한다. 완료 확인을 지난 뒤 한 번 구현 AI. 댓글과 PR은 사용자 승인 AC12, AC16

감사 리포트를 검토한 뒤 바뀌는 순서

--response는 발견마다 결정만 받고 소스를 고치지 않는다. 반영으로 정한 발견은 다음 회차의 계획 수립에서 문서가 먼저 바뀌고, 소스는 구현 단계의 새 Task에서 바뀐다.

반영으로 정한 발견specplan계획 검증소스
기존 AC 안의 결함 그대로 Task를 더한다 건너뛴다 새 Task에서 재현 테스트를 쓰고 고친다
설계를 바꿔야 하는 결함 제품·도메인 결정이 바뀌면 결정 사항과 변경 이력에 한 줄 설계 결정을 고치고 Task를 더한다 다시 받는다 위와 같다
테스트 층이나 대상이 바뀜 그대로 테스트 계획의 줄을 고치고 Task를 더한다 다시 받는다 위와 같다
확장 (AC에 없는 결과) 사용자 승인 뒤 R·AC와 변경 이력을 더하고 이슈 본문도 고친다 테스트 계획에 줄을 더하고 Task를 더한다 다시 받는다 위와 같다
완화 (AC를 약하게 하거나 뺌) 사용자 재승인 뒤 AC를 고치고 변경 이력에 한 줄 해당 줄을 고친다 다시 받는다 기대값을 고칠 때만 바뀐다
원장 이관, 보류 그대로 그대로 대상이 아니다 고치지 않는다
  • spec은 바뀔 때만 바뀌고, plan은 늘 뒤에 더해지며, 소스는 구현 단계에서만 바뀐다.
  • 계획 감사 리포트의 --response는 고칠 대상이 spec·plan이다. 그 보정은 계획 수립으로 돌아가는 짧은 길이고, 세 가지 가운데 하나가 바뀌었으면 계획 감사를 다시 받는다 (7절 A).

3. 회차가 넘어가는 모습

AC가 6개인 가상의 이슈가 세 회차를 도는 예시다. 칸의 색은 그 회차에서 그 단계가 어떻게 됐는지를 보인다.

회차1 계획 수립2 계획 검증3 구현4 구현 검증5 완료 확인
회차 1 spec·plan을 새로 쓴다. 요구사항을 승인받는다. 계획 감사 1차. 발견 2건을 고친다. Task 1~4. 테스트를 먼저 쓴다. 교차 감사 1차, 부적합. 발견 3건 (반영 2, 원장 1). 1단계 부분 충족 (AC3), 2단계 보완 필요, 종합 부적합. 권장도 결정도 다음 회차다.
회차 2 발견 2건을 고치는 Task 5·6을 더한다. AC는 그대로다. 건너뛴다. AC·요구사항, 설계 결정, 테스트 계획이 그대로다. Task 5·6. 재현 테스트부터 쓴다. 구현이 바뀌어 교차 감사 2차, 조건부 적합. 발견 2건이 회차 1과 같은 종류다. 1단계 부분 충족 (AC5), 2단계 주의, 종합 조건부 적합. 권장도 결정도 다음 회차다.
회차 3 같은 종류가 이어져 설계 결정부터 고친다. Task 7을 더한다. 설계 결정이 바뀌어 계획 감사 2차. 발견 0건. Task 7. 구현이 바뀌어 교차 감사 3차, 적합. 1단계 충족, 2단계 통과, 종합 적합. 테스트 계획 6줄을 모두 확인했다. 권장도 결정도 마무리다.

1spec·plan 작성, Task 1~4계획 수립계획 감사 1차 발견 2건 · 교차 감사 1차 발견 3건 · 1단계 부분 충족 (AC3), 2단계 보완 필요, 종합 부적합 · 테스트 계획 4/6줄 · 다음 회차

  • 완료 확인은 새 판정 값을 만들지 않는다. 마지막 교차 감사 리포트의 1단계 상태(충족, 부분 충족, 미충족, 판정 불가), 2단계 상태(통과, 주의, 보완 필요), 종합 판정(적합, 조건부 적합, 부적합)을 그대로 옮긴다. 에이전트의 권장과 사용자의 결정은 마무리나 다음 회차로 적는다.
  • 권장 규칙: 1단계 상태가 충족이고, 2단계 상태가 통과나 주의이며, 테스트 계획의 모든 줄을 확인했고, --response에서 반영으로 정한 발견을 모두 닫았으면 마무리, 그 밖은 다음 회차다. 판정 불가로 남은 AC는 권장과 함께 따로 나열한다.
  • 한 번만 돈 이슈는 이 표가 한 줄이다. 종류별 발견 기록과 Task의 대응 발견 칸은 쓸 내용이 있을 때만 둔다. 루프 때문에 빈 섹션이 생기지 않는다 (AC15).
  • 다시 시작한 단계는 계획 수립 뒤에 처음으로 다시 한 단계로 적었다 가정. 돌아가는 곳은 늘 계획 수립이라 그대로 적으면 모든 줄이 같은 값이 된다 (7절 B).

4. Task 하나의 순서

테스트 작성→ 실패 확인→ 테스트 커밋→ 구현→ 통과 확인→ 구현 커밋
  • 기능을 바꾸는 Task가 대상이다. 테스트를 먼저 쓰지 않는 Task의 기준(문서, 화면 배치, 스파이크)은 본문의 검토 필요 항목이다.
  • 감사 발견을 고치는 Task는 재현 테스트부터 쓴다. 회차 2 이후의 Task가 이 모양이다.
  • 커밋한 테스트의 기대값을 바꾸는 변경은 완화다. 사용자 승인 없이 반영하지 않는다 (AC7).
  • 단위 테스트를 먼저 고른다. 단위보다 위 층을 쓰면 plan 테스트 계획의 그 줄에 이유를 적는다 (AC5).

5. 템플릿에 넣을 아스키 그림 안

컨텍스트를 초기화한 AI가 읽는 파일에 그림을 두면 절차의 순서와 돌아가는 길을 문장보다 빨리 찾는다. 두 안을 그렸다.

안 A: 세로형 (권장)

       이슈 등록 (--create)
            |
            v
  +--> 1. 계획 수립
  |         |    spec·plan이 없으면 쓰고, 지난 회차에서 바꿀 것이 나왔으면 고친다
  |         v
  |    2. 계획 검증
  |         |    AC·요구사항, 설계 결정, 테스트 계획이 바뀌었을 때만 계획 감사를 받는다
  |         v
  |    3. 구현
  |         |    Task마다 테스트 작성 -> 실패 확인 -> 구현 -> 통과 확인
  |         v

  |         |    구현이 바뀌었을 때 교차 감사를 전체로 받는다

            |    감사 상태와 테스트 계획 확인 줄 수를 보이고 마무리나 다음 회차를 권장한다

  • 선이 한글보다 왼쪽에만 있다. 한글 폭이 글꼴마다 달라도 선이 어긋나지 않는다.

안 B: 가로형

계획 수립 -> 계획 검증 -> 구현 -> 구현 검증 -> 완료 확인 -> Task N (마무리)
    ^                                              |
    +-------- 다음 회차로 정하면 돌아간다 ---------+
  • 세 줄이라 짧다. 단계마다의 조건은 그림에 담지 못한다.
  • 한글 한 글자가 영문 두 칸 폭인 글꼴에서만 돌아가는 선이 맞는다. 이 화면에서 선이 어긋나 보이면 GitHub와 IDE 미리보기에서도 어긋난다.

파일안이유
issue-workflow-template.md안 A를 맨 위 절차 앞에 둔다repo마다 사본(active/issue-workflow.md)으로 배포되어 세션이 바뀐 AI가 가장 먼저 읽는다

그림을 템플릿에 넣는 일은 이슈 본문에 따로 적혀 있지 않다. 포함 항목 "issue-workflow 템플릿, README, 도메인 명세가 새 흐름을 설명한다"를 구체화한 것으로 보고 spec 승인 때 따로 표시해 묻는다.

6. 지금 있는 게이트가 놓이는 자리 가정

계획 종료 게이트계획 수립의 끝, spec·plan을 새로 쓰거나 고친 회차발견을 적는 자리가 spec 전제에서 결정 사항·plan 설계 결정으로 바뀔 수 있다 (본문 검토 필요)
이슈 본문 갱신 질의확장으로 AC가 늘 때의 계획 수립 안spec의 AC가 이슈 본문과 같은 문장이라 (AC 없음: …) 항목 때문에 묻는 일이 사라진다

7. 그림을 그리며 드러난 빈 곳

그림에 쓴 가정과 권장안이다. A·B는 본문의 검토 필요에 없던 항목이고, C~H는 본문의 검토 필요 가운데 그림의 모양을 바꾸는 항목이다.

A. 계획 검증에서 발견이 나왔을 때의 길 정함

  • 빈 곳: 본문은 돌아가는 길을 완료 확인에서만 둔다. 계획 감사의 발견을 고치면 설계 결정이나 테스트 계획이 바뀌고, 규칙대로면 계획 감사를 다시 받는다.
  • 그림의 가정: 계획 검증 단계 안에서 고치고 구현으로 넘어간다.
  • 정한 내용 (2026-11-23 대화): 예외를 두지 않고 본문 규칙대로 둔다. 고친 결과로 AC·요구사항, 설계 결정, 테스트 계획이 바뀌었으면 계획 감사를 다시 받고, 바뀌지 않았으면 받지 않는다. C와 같은 기준이다.

B. 루프 기록의 다시 시작한 단계 칸 정함

  • 빈 곳: 돌아가는 곳이 늘 계획 수립이라 칸의 값이 늘 같다.
  • 그림의 가정: 계획 수립 뒤에 처음으로 다시 한 단계를 적는다. 값은 계획 검증(세 가지 가운데 하나가 바뀜)이나 구현(Task만 더함)이다.
  • 정한 내용 (2026-11-23 대화): 가정대로 둔다. 이 칸 하나로 그 회차에 계획 감사를 받았는지가 드러난다.

C. 구현 검증을 다시 받지 않아도 되는 변경 정함

  • 예외를 두지 않는다. 구현이 바뀌면 고친 발견의 위험도와 관계없이 교차 감사를 전체로 다시 받는다 (2026-11-23 대화). 지금의 issue-audit 운영과 같다.
  • 이유: 품질을 시간과 토큰보다 앞에 둔다. 작은 수정도 다른 곳을 깨뜨릴 수 있고, 다시 받지 않으면 그 수정은 검증 없이 남는다.
  • 회차를 줄이는 길: 고치지 않기로 한 발견은 --response에서 이관이나 보류로 정한다. 구현이 바뀌지 않으므로 다시 감사받지 않는다.
  • 거둔 권장: 낮음·정보 발견의 보정을 감사에서 빼자는 안은 거뒀다. 루프를 나갈지는 사용자가 정하므로 예외가 없어도 회차는 사용자가 끝낼 수 있다.

D. 완료 확인이 충족을 판정하는 근거 정함

  • 결정 주체: 루프를 나갈지는 사용자가 정한다. 에이전트는 아래 규칙으로 권장만 낸다 (2026-11-23 대화).
  • 보이는 값: 마지막 교차 감사 리포트의 1단계 상태, 2단계 상태, 종합 판정과 테스트 계획의 확인한 줄 수다. 새 판정 값을 만들지 않는다.
  • 권장 규칙: 아래 네 가지가 모두 맞으면 마무리, 그 밖은 다음 회차다.
    • 1단계 상태가 충족이다.
    • 2단계 상태가 통과나 주의다. 높음 발견이 있는 보완 필요만 막는다.
    • 테스트 계획의 모든 줄을 확인했다.
    • --response에서 반영으로 정한 발견을 모두 닫았다. 이관이나 보류로 정한 발견은 세지 않는다.
  • 종합 판정으로 적지 않는 이유: 조건부 적합은 1단계 부분 충족에서도 나온다. 규칙을 "조건부 적합 이상"으로 적으면 AC가 부분 충족인 회차도 마무리 권장이 된다. 종합 판정은 보이기만 하고 규칙은 두 상태로 적는다.
  • 주의를 막지 않는 이유: 주의는 중간 발견이 하나만 있어도 나온다. 그 발견이 실제로 중요한지는 --response에서 사용자가 정한다.
  • 반영으로 정한 발견을 세는 이유: 2단계 주의를 막지 않으므로, 이 조건이 없으면 중간 발견을 고치기로 정해 놓고도 마무리 권장이 나온다 (2026-11-23 대화).
  • 권장과 다르게 나갈 때: 남은 AC와 발견마다 완화, 원장 등재, 새 이슈 가운데 결정을 받는다.

E. "지난 검증 뒤에 바뀌었다"를 가리는 방법 정함

  • 그림의 가정: 루프 기록의 바뀐 것 칸으로 가린다.
  • 정한 내용 (2026-11-23 대화): 검증한 커밋을 루프 기록에 적고 그 커밋 뒤의 diff로 가린다. 구현 검증은 코드 경로의 diff, 계획 검증은 spec의 요구사항·완료의 정의와 plan의 두 섹션 diff를 본다.

F. 계획 감사 수행 여부를 묻는 시점 정함

  • 그림의 가정: 회차 1에서 한 번 묻는다. 수행으로 고른 이슈만 뒤 회차에서 조건에 따라 다시 받는다.
  • 정한 내용 (2026-11-23 대화): 가정대로 둔다. 회차마다 물으면 질의가 루프보다 무거워진다.

G. "같은 종류가 이어진다"의 기준 정함

  • 그림의 가정: 같은 종류가 두 회차 연속으로 나오면 다음 회차의 계획 수립이 설계 결정부터 고친다. 종류는 --response 분류에서 붙인다.
  • 정한 내용 (2026-11-23 대화): 가정대로 둔다. 종류를 issue-audit의 카테고리 체계에 넣으면 git-review와 git-review-quiz까지 함께 고쳐야 한다.

H. 루프를 나간 뒤에 구현이 바뀔 때 정함

  • 빈 곳: Task N의 전체 회귀가 실패하거나 PR 뒤 피드백으로 구현을 고치면 구현 검증을 다시 받는지가 정해지지 않았다.
  • 그림의 가정: 그림은 루프로 돌아가는 선을 두지 않았다.
  • 정한 내용 (2026-11-23 대화): Task N에서 구현을 고치면 계획 수립으로 돌아간다. PR 뒤 피드백으로 구현을 고쳤을 때 교차 감사를 다시 받을지는 사용자가 고른다.
