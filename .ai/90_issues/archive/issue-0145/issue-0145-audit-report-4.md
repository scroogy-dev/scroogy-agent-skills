#### F-12: 실패한 AC를 이관해도 Task N의 전체 통과 조건이 남는다

- **위험도**: 🟡 중간(MEDIUM)
- **영향 축**: 스펙·기능 달성 차단
- **발생확률 축**: 특수 조건·엣지
- **카테고리**: 기능
- **관점**: 스펙 모호성
- **계보**: 신규
- **권장 조치**: 완료 확인에서 이관한 AC의 결정적 검사를 Task N에서 어떻게 처리할지 정하고, 사용자에게 제시하는 선택과 템플릿의 통과 조건을 맞춘다.
- **완료 기준**
  1. 전체 회귀는 통과하고, 후속 이슈로 넘긴 AC의 독립 검사만 실패하는 예에서 마무리 가능 여부와 필요한 기록이 하나로 정해진다.
  2. 이관되지 않은 AC 검사나 기존 회귀가 실패한 대조군에서는 이관 결정을 근거로 통과 처리할 수 없다.

<details>
<summary>근거와 실패 시나리오 펼치기</summary>

완료 확인은 기준 미달이어도 사용자가 마무리를 선택한 뒤 남은 AC를 원장이나 새 이슈로 넘기도록 한다. PR 표도 이 결정을 `이관` 상태로 표시한다. 반면 Task N의 1번 작업과 완료 기준은 테스트 계획의 모든 결정적 검사가 통과해야 한다. 이관한 줄의 처리 규칙은 양쪽에 없다.

임시 디렉토리에 CSV 산출물만 있는 경우를 확인했다. 기존 기능의 검사 `test -s export.csv`는 종료 0이고, 새 출력 형식 AC에만 걸린 독립 검사 `test -s export.json`은 종료 1이다. 후속 이슈로 이관한다는 결정은 이 명령의 결과를 바꾸지 않는다. 사용자가 허용된 마무리를 선택했어도 새 출력 기능을 구현하거나 계획의 검사를 별도로 바꿔야 Task N의 완료 기준을 채울 수 있다. 이번 저장소 회귀 테스트에서 발생한 실패와는 별개의 절차 모의 실행이다.

근거는 [완료 확인](../../issue-work/SKILL.md#완료-확인), [Task N](../../issue-work/templates/issue-plan-template.md#task-n-고정-마무리), [PR의 완료의 정의 대조](../../git-pr/SKILL.md)에서 확인했다.

</details>

#### F-13: 완료 확인에서 완화한 AC에 이전 문장의 판정이 붙는다

- **위험도**: 🟢 낮음(LOW)
- **영향 축**: 기능 저하
- **발생확률 축**: 특수 조건·엣지
- **카테고리**: 기능
- **관점**: 엣지케이스
- **계보**: F-3 잔여. 루프 안의 AC 변경은 보정됐고, 마지막 검증이 끝난 뒤 승인하는 완화에서 같은 문제가 남는다.
- **권장 조치**: 완료 확인 중 문장이 바뀐 AC는 마지막 감사가 본 문장과 연결해 처리한다. 검증을 갱신할지, 새 문장의 판정을 미검증으로 표시할지 정한다.
- **완료 기준**
  1. 같은 번호의 AC를 완료 확인에서 완화했을 때, PR에서 완화 전 판정을 새 문장의 감사 결과로 제시하지 않는다.
  2. AC 문장이 같고 확인 칸·체크박스만 바뀐 경우에는 기존 판정을 유지한다.

<details>
<summary>근거와 실패 시나리오 펼치기</summary>

한 AC를 감사인이 `[QD]`로 판정하는 예다. 산출물이 CSV뿐이면 “CSV와 JSON을 제공한다”는 부분 충족이다. 완료 확인에서 사용자가 “CSV를 제공한다”로 완화를 승인하면 구현은 그대로이고 새 문장이 요구하는 산출물은 이미 있다. 독립 검사 결과도 CSV는 종료 0, JSON은 종료 1이다. 변경 통제는 같은 번호로 spec과 이슈 본문의 문장을 갱신한다. 그 뒤 들어가는 Task N은 교차 감사를 받지 않고, PR은 같은 번호의 기존 리포트 판정을 복사한다. 그 결과 새 문장을 감사한 적이 없는데도 PR에는 이전 문장의 `부분 충족`이 표시된다. F-12의 결정적 검사 실패가 없어도 생긴다.

지정 위치는 issue-work/SKILL.md 193·197·199·218행, git-pr/SKILL.md 263~269행이다. 루프의 구현 검증 단계에서는 spec 문장 변경을 다시 검사하도록 167~171행에 이미 반영돼 있다.

</details>

#### F-14: 사람 확인 줄만 바뀐 경우 배포용 절차와 스킬의 안내가 갈린다

- **위험도**: 🟢 낮음(LOW)
- **영향 축**: 기능 저하
- **발생확률 축**: 특수 조건·엣지
- **카테고리**: 기능
- **관점**: 부작용

- **완료 기준**
  1. 계획 감사를 생략한 이슈에서 사람 확인 줄만 한 줄 추가하면 두 문서 모두 전체 구현 감사 생략으로 안내한다. 완료 확인에서는 해당 줄의 사용자 확인을 받는다.
  2. 같은 자리에 감사인이 채점할 `[QD]` 줄을 추가하면 두 문서 모두 전체 구현 감사를 다시 받도록 안내한다.

<summary>근거와 실패 시나리오 펼치기</summary>
