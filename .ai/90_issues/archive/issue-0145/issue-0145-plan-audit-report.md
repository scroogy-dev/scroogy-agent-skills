#### F-12: 첫 계획 감사가 아직 묻지 않은 본문 갱신 결정을 요구한다

- **위험도**: 🟡 중간(MEDIUM)
- **영향 축**: 스펙·기능 달성 차단
- **발생확률 축**: 특수 조건·엣지
- **카테고리**: 기능
- **관점**: 모호성
- **계보**: F-11 잔여
- **근거**: 본문에 R1·R2와 AC1만 있으면 3-2에서 AC2를 만들고 5단계의 첫 감사에서 `이슈 본문에 없는 AC`가 나온다. 이 번호를 예외로 삼는 `거절 · AC2`는 6단계에서야 쓸 수 있다. 승인·거절 뒤의 감사와 PR 규칙은 정해졌지만 첫 감사는 정상 보강 대기를 위반으로 센다. (AC2·AC17·AC18 · plan 213–219, 340, 386, 424행)
- **권장 조치**: 첫 감사에서 승인된 R의 보강 대기를 어떻게 판정할지 정하고, 사용자 답변 뒤의 대조까지 연결한다.

**완료 기준**

- [ ] AC가 일부만 있는 예시에서 첫 감사가 보강 대기와 근거 없는 spec 확장을 가른다.
- [ ] 6단계 승인·거절 각각에서 같은 R과 AC 번호로 다음 감사와 PR 대조를 마친다.

#### F-13: 새 테스트 행이 이전 감사의 AC 판정을 물려받는다

- **위험도**: 🟡 중간(MEDIUM)
- **영향 축**: 스펙·기능 달성 차단
- **발생확률 축**: 특수 조건·엣지
- **카테고리**: 기능
- **관점**: 모호성
- **계보**: 신규
- **근거**: 1차 최종 감사에서 AC1의 A 테스트만 통과한 뒤, 다음 계획에서 같은 AC에 기존 B 테스트를 추가하는 경우다. plan만 바뀌어 계획 감사를 받아도 B의 실행 결과는 없는데, 완료 확인은 마지막 리포트의 AC1 충족을 근거로 두 줄 모두에 1차를 적는다. (AC5·AC9·AC11·AC17 · plan 219, 260–264, 380–387행)
- **권장 조치**: 확인 근거를 그 감사가 실제로 평가한 테스트 계획 행에 연결하고, 추가·교체한 행의 검증 시점을 정한다.

**완료 기준**

- [ ] A만 확인한 뒤 B를 추가한 예시는 1/2로 표시하고 다음 회차를 권장한다.
- [ ] B의 현재 결과를 확인한 뒤에만 2/2가 되며, `확인` 값만 적는 변경은 계획 감사를 다시 유발하지 않는다.

#### F-14: 정리 명령을 직접 호출하면 마무리 결정 없이 완료로 기록할 수 있다

- **위험도**: 🟡 중간(MEDIUM)
- **영향 축**: 스펙·기능 달성 차단
- **발생확률 축**: 특수 조건·엣지
- **카테고리**: 기능
- **관점**: 모호성
- **계보**: 신규
- **근거**: 마지막 최종 감사와 일반 Task가 모두 끝났지만 사용자가 `다음 회차`를 고른 직후, 보정 Task가 아직 추가되기 전에 `--clear`로 중단·종료할 수 있다. 계획의 1단계 검사는 통과하고 4단계는 Task N을 완료로 기록한다. `다음 회차`와 `마무리`는 체크박스나 감사 모델 기록만으로 구별할 수 없다. (AC11·AC12 · plan 175, 266, 273–276행 · issue-work/SKILL.md 297–313행)
- **권장 조치**: `--clear`가 정상 완료를 기록할 때 해당 회차의 사용자 결정을 확인하고, 중단·종료로 이관한 경우의 결과를 구분한다.

**완료 기준**

- [ ] 동일한 plan에서 `마무리`로 결정했을 때만 Task N 완료와 `PR 대기`가 기록된다.
- [ ] 결정 전 또는 `다음 회차`에서 중단·종료를 선택한 예시는 종료 사유와 미완료 상태를 보존한다.

#### F-15: 원장 파일 자체가 구현 대상이면 변경을 재감사하지 않는다

- **위험도**: 🟡 중간(MEDIUM)
- **영향 축**: 스펙·기능 달성 차단
- **발생확률 축**: 특수 조건·엣지
- **카테고리**: 기능
- **관점**: 범위
- **계보**: F-4 잔여
- **근거**: 원본 문서 일반은 이제 diff에 들어간다. 그러나 `.ai/70_ledger/`는 항상 제외된다. 실제 #108 R6처럼 원장 항목과 색인 변경 자체가 승인된 결과라면 그 파일만 보정한 회차에 이전 구현 감사가 그대로 유효해진다. (AC10 · spec 594–596행 · plan 260–261행 · 보존 이슈 #108 spec R6)
- **권장 조치**: 승인된 R·AC의 구현 파일을 우선 포함하고, 감사 결과를 기록하기만 한 변경을 제외한다.

**완료 기준**

- [ ] 일반 문서와 원장 안의 AC 대상 문서를 각각 단독 보정한 예시에서 전체 구현 감사를 다시 받는다.
- [ ] 루프 기록이나 통상적인 원장 이관만 바꾼 예시에서는 구현 재감사를 건너뛴다.

#### F-16: 사람이 모든 항목을 확인해도 다음 회차를 계속 권장한다

- **위험도**: 🟢 낮음(LOW)
- **영향 축**: 기능 저하
- **발생확률 축**: 특수 조건·엣지
- **카테고리**: 기능
- **관점**: 모호성
- **계보**: 신규
- **근거**: `결정 사항`이 없고 AC마다 사람 확인([ND])만 있는 문서 이슈를 적용했다. 전부 사용자 확인 날짜가 있어도 리포트의 1단계는 `판정 불가(N/A)`라서 마무리 권장 조건에 닿지 않는다. 사용자가 마무리를 직접 선택할 수 있지만, 같은 입력으로 감사를 반복해도 권장은 달라지지 않는다. (AC5·AC11·AC17 · spec 582–586, 622–627, 636, 645행 · plan 263–264, 381행)
- **권장 조치**: 사람 확인만 있는 이슈에서 확인 뒤 내릴 권장과 종결 근거를 명시한다. AC11의 충족 조건을 바꾸는 선택은 변경 통제로 다룬다.

**완료 기준**

- [ ] 사람 확인 전·후의 권장과 필요한 결정을 예시에 구별해 적는다.
- [ ] 확인이 끝난 뒤 같은 감사를 반복할 필요와 사용자 확인이 남는 위치를 설명할 수 있다.

#### F-17: 한 회차 검사에서 루프와 관계없는 빈 표까지 실패한다

- **위험도**: 🟢 낮음(LOW)
- **영향 축**: 기능 저하
- **발생확률 축**: 특수 조건·엣지
- **카테고리**: 테스트
- **관점**: 범위
- **계보**: 신규
- **근거**: 이슈 AC15는 루프 때문에 생긴 빈 섹션만 대상으로 삼는다. R19의 DoD와 Task 3의 fixture는 spec·plan·summary 전체에서 표 머리만 있는 표와 빈 섹션을 금지한다. 기존 양식에 프로젝트 고유의 빈 선택 표 하나가 있어도 루프 산출물 검사가 실패한다. (AC15 · spec 409행 · plan 173행)
- **권장 조치**: AC15 검사의 범위를 루프 도입으로 생기는 섹션과 표에 맞춘다.

**완료 기준**

- [ ] 루프가 추가한 빈 섹션·표는 실패하고, 루프와 무관한 사용자 선택 표만 비어 있는 예시는 통과한다.

#### F-18: 영향 조사 표 밖의 행과 중복을 계속 허용한다

- **위험도**: 🟢 낮음(LOW)
- **영향 축**: 기능 저하
- **발생확률 축**: 특수 조건·엣지
- **카테고리**: 테스트
- **관점**: 추적성
- **계보**: F-7 잔여 · 보류 유지

**완료 기준**

- [ ] 정상 표에서 모든 스킬이 한 번씩 나오면 통과한다.
- [ ] 대상 표 밖에만 있는 스킬, 누락, 중복을 각각 검출한다.
