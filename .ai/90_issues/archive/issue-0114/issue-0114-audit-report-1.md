<details>
<summary>근거·상세 설명 펼치기</summary>

- doc.md:64는 `git diff <source_hash>..HEAD --name-only` 중 ssot_dir 아래 파일만 sync 대상으로 삼는다. 71행은 이름 변경 시 옛 행을 지우고 Why 태깅을 새 행으로 옮기라고 요구하지만, 옛 경로를 얻는 절차는 없다.
- 독립 임시 Git 저장소에서 동일 내용의 `docs/old.md`를 `docs/new.md`로 이름 변경했다. rename 감지를 켠 Git의 실제 출력은 다음과 같다.

```text
문서에 지정된 --name-only: docs/new.md
대조용 --name-status -M: R100  docs/old.md  docs/new.md
```

- 이어 `docs/new.md`를 `outside/new.md`로 옮기면 name-only는 `outside/new.md`만 출력하고 ssot_dir 필터 뒤 목록은 비어 있다. 3단계 파일 유효성 점검은 없어진 옛 행을 제거할 수 있으므로, 이 경우 옛 행이 반드시 잔존한다고 주장하지 않는다.
- 루트 내부 rename에서도 새 파일을 신규로 처리하고 3단계에서 옛 행을 제거하면, 원본 문서에 없고 색인에만 남긴 사람의 Why 설명은 이전되지 않는다. 이름 변경 대응 정보를 추가 조회하거나 이전 커밋을 대조하는 명시적 보완이 필요하다.
- 이 실험은 Git 입력 정보의 부족을 재현했다. 대화형 에이전트의 실제 sync를 실행해 태그 유실까지 관찰한 결과는 아니다. 임의의 추가 조회에 기대야 한다는 절차 결함으로 판정한다.
- 영향은 수동 태그 보존 보장이 깨지는 것이고, 조건은 rename이다. spec R9에는 rename 태그 이전의 완료 조건이 별도로 고정되어 있지 않아 1단계 판정을 낮추지 않았다. plan Task 4의 자기완결성 QD는 이 입력 부족을 보완할 필요가 있다.

</details>
