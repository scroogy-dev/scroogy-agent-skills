### 상세 분석

#### F-1: push 전에 승인한 원격 URL을 다시 결속하지 않음

- **위험도**: 낮음(LOW)
- **분류**: 부작용·누락된 검증
- **재평가 근거**: 발생하려면 승인과 push 사이의 짧은 구간에 동일 작업트리의 Git 원격 설정을 바꿀 수 있는 사용자·에이전트가 실제로 URL을 변경해야 한다. 일반적인 개인·단일 에이전트 사용에서는 자연 발생 경로가 없고 발생 가능성이 극히 낮으므로, 높은 영향과 별개로 종합 위험도를 낮음으로 조정했다.
- **설명**: 3단계는 대상 저장소와 push 대상 원격 이름을 승인받지만, 불변 값으로 보관하는 항목은 대상 저장소와 커밋 SHA뿐이다. 원격 URL 재검증은 `git push` 뒤의 PR 생성 직전에만 명시되어 있다.
- **영향**: 승인과 push 사이에 `remote.<name>.url`이 바뀌면 승인한 소스가 다른 저장소로 게시된다. 이후 재검증이 PR 생성을 막더라도 이미 발생한 코드 공개는 되돌리지 못한다.
- **재현**: 로컬 bare 저장소 A를 승인 대상으로 기록한 뒤 `origin` URL을 B로 바꾸고 문서의 push를 실행했다. A의 `refs/heads/main`은 없고 B에는 승인 SHA `c504195…`가 게시되어, 별칭을 다시 해석하는 push가 승인 URL에 결속되지 않음을 확인했다.
- **권장 조치**: 승인한 원격 URL도 불변 값으로 보관하고 첫 외부 쓰기 전에 원격 이름의 현재 URL·정규화 대상 저장소가 모두 승인값과 같은지 검증한다. 가능하면 mutable 원격 별칭이 아니라 승인한 URL 자체를 구조화된 argv의 push 대상으로 사용한다.

#### F-2: 메시지의 기준 diff가 승인한 소스 SHA와 결속되지 않음

- **위험도**: 중간(MEDIUM)
- **분류**: 암묵적 가정·누락된 검증
- **설명**: 메시지는 승인 SHA를 확정하기 전에 작성되며, 문서 동기화 점검도 기준 리비전 없이 “브랜치 diff”만 지시한다. clean worktree 요구나 staged·unstaged·untracked 변경 처리 규칙이 없다.
- **영향**: 미커밋 변경을 포함한 diff로 제목·본문을 작성한 뒤 현재 HEAD만 push하면 PR 설명이 실제 변경보다 앞서간다. 반대로 HEAD만 읽으면 작성자가 포함하려던 미커밋 변경이 조용히 누락될 수 있다.
- **현재 작업트리 증거**: HEAD는 `553aaad`지만 `git-pr/SKILL.md`에 `17`줄 추가·`11`줄 삭제가 미커밋 상태다. 현재 문서의 `--repo`·승인 SHA 결속 보정은 HEAD에 없으므로, 이 브랜치에서 바로 git-pr을 실행하면 diff 선택 방식에 따라 메시지와 게시 SHA가 달라진다.
- **권장 조치**: 메시지 작성 전에 dirty worktree를 중단·질의하고, 승인 대상 소스 SHA를 먼저 고정한다. 제목·본문·동기화 점검은 명시적인 베이스와 그 SHA 사이의 커밋·diff만 사용하며, 소스 SHA가 바뀌면 전 과정을 다시 수행한다.

#### F-3: 원격 SHA 확인과 PR 생성 사이의 경쟁 조건

- **위험도**: 중간(MEDIUM)
- **분류**: 엣지케이스·동시성
- **설명**: 로컬·원격 SHA를 승인 SHA와 비교한 뒤 `gh pr create --head <브랜치>` 또는 MCP를 호출한다. 두 동작 사이에 다른 사용자·에이전트가 같은 원격 브랜치를 갱신해도 생성 명령은 SHA가 아니라 최신 branch ref를 사용한다.
- **영향**: 검증 시점에는 승인 SHA였던 head가 생성 시점에는 다른 커밋이 되어, 승인받지 않은 diff로 PR이 생성될 수 있다.
- **재현**: 원격 확인값 `c504195…`을 얻은 직후 다른 브랜치에서 같은 원격 `main`을 `b4c9d82…`로 갱신했다. 로컬 `main`은 계속 승인 SHA였지만 원격 head만 이동해, 선행 로컬 검증으로는 이 변화를 잡지 못했다.
- **권장 조치**: 생성 직전에 원격 exact ref를 다시 확인하고, 생성 직후 반환된 PR의 head SHA도 승인 SHA와 대조한다. 불일치 시 자동 force-push하지 말고 상태를 보고해 별도 승인을 받는다.

#### F-4: MCP 폴백이 승인한 host를 전달·검증할 수 없음

- **위험도**: 중간(MEDIUM)
- **분류**: 암묵적 가정·부작용
- **설명**: 승인 대상 형식과 `gh --repo`는 `[HOST/]OWNER/REPO`지만, 감사 환경의 GitHub MCP `create_pull_request` 스키마는 `owner`·`repo`만 받고 host 인자가 없다. 본문은 MCP 연결이 어느 host를 가리키는지 확인하는 절차 없이 owner·repo 전달만 지시한다.
- **영향**: GitHub Enterprise나 여러 host를 쓰는 환경에서 gh 인증 실패 후 폴백하면 같은 owner/repo의 다른 host에 PR을 만들거나 제출에 실패할 수 있다. 제목·본문 같은 PR 메타데이터가 승인하지 않은 host에 공개될 가능성도 있다.
- **권장 조치**: MCP 연결 host를 확인할 수 있고 승인 host와 일치할 때만 폴백한다. 확인할 수 없거나 host-qualified 대상이면 폴백하지 않고 최종 제목·본문을 남겨 종료하며, 호출 시 `base`·`head`·`title`·`body`·`draft`도 승인값으로 명시한다.
