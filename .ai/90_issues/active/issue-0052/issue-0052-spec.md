# Issue #52 스펙 issue-work `--response`: 1단계 적합성 발견을 2단계 비판적 발견보다 우선 처리

## 목표 (Goal)

`--response` 검토 절차에 순서 게이트를 넣어, 1단계 적합성 검증(요구사항·DoD·범위) 발견의 처리 방향이 전부 확정되기 전에는 2단계 비판적 검증 발견의 보정에 들어가지 않게 한다.

---

## 범위 (Scope)

**포함 (In)**

- `issue-work/SKILL.md`의 `--response` 동작 2단계(피드백만 제시): 발견사항을 **1단계 발견 / 2단계 발견으로 나눠** 제시
- 동작 3단계(처리 방향 표): 1단계 발견을 표 상단에 배치하고, 미해소 1단계 항목이 있으면 그 사실을 명시
- 동작 4~5단계: 순서 게이트 — 1단계 미충족(FAIL)·부분 충족(PARTIAL) 항목의 처리 방향(반영/이관/보류)이 전부 확정되기 전에는 2단계 항목 보정에 들어가지 않음
- 기존 항목별 승인 원칙 유지 — 이 변경은 **처리 순서**만 규정하며 승인 게이트를 대체하지 않음
- `--response`를 언급하는 주변 문구(`SKILL.md` `작업 진행 중` 절, `templates/` 내 요약 문구)와의 정합 점검

**비포함 (Out)**

- `issue-audit` 리포트 형식 — 이미 1단계 → 2단계 순서로 생산되어 변경하지 않음
- 항목별 승인 게이트 자체의 변경 — 승인 원칙은 그대로 둠
- 설치본(`~/.claude/skills/` 등 5개 경로) 반영 — repo 본문이 SSoT이며, 배포는 사용자가 `install-skills`로 별도 수행

## 완료의 정의 (Definition of Done)

> **검증 레벨** — 낮을수록 좋다(자동 검증에 가까움). 기본은 L1, 한 레벨 내릴 때마다 강등 사유를 함께 적는다.
>
> - `[D]`  L1 결정적   — 명령이 합/불을 판정, 사람 판단 없음
> - `[QD]` L2 준결정적 — 다른 AI·기준 체크리스트가 채점
> - `[ND]` L3 비결정적 — 사람이 직접 읽고 판단

> **앵커 토큰 계약** — 아래 `[D]` 항목의 검증은 단계 범위 안 문구 존재 검사다. 앵커 토큰
> (`1단계 발견`, `2단계 발견`, `상단`, `미해소`, `순서 게이트`, `항목 단위로`, `자동 보정하지 않는다`)은
> 요구 토큰으로 계약에 포함한다 — 같은 의미라도 다른 표현으로 쓰면 불합격이며, 지정된 단계 범위 밖에서만
> 발견되어도 불합격이다. 토큰 존재가 의미까지 보증하지 못하는 부분(부정·모순 서술)은 [QD] 항목이 담당한다.

- [x] [D]  `--response` 동작 2단계 범위에 1단계 발견 / 2단계 발견 구분 제시가 기재된다 (검증: plan Task 1 완료 기준 — 2단계 범위 추출 후 `1단계 발견`·`2단계 발견` 각 1건 이상)
- [x] [D]  동작 3단계 범위에 1단계 발견 상단 배치와 미해소 1단계 항목 명시가 기재된다 (검증: plan Task 1 완료 기준 — 3단계 범위 추출 후 `상단`·`미해소` 각 1건 이상)
- [x] [D]  동작 4~5단계 범위에 순서 게이트가 기재된다 (검증: plan Task 1 완료 기준 — 4단계 이후 범위 추출 후 `순서 게이트` 1건 이상)
- [x] [D]  기존 항목별 승인 원칙 문구가 유지된다 (검증: `--response` 절 전체에서 `항목 단위로`·`자동 보정하지 않는다` grep 각 1건 이상 — 기존 문구가 `경계` 항목과 동작 4단계에 나뉘어 있어 절 전체 범위가 의도된 사양)
- [x] [D]  기존 회귀 테스트가 통과한다 (검증: `bash issue-work/tests/run-tests.sh` 0 실패)
- [ ] [QD] 앵커 토큰이 존재하되 의미가 뒤집히거나 모순되는 서술이 없다 (검증: 교차모델 issue-audit, 별도 세션)  ← 강등 사유: 부정·모순 여부는 의미 판단이라 명령으로 환원 불가
- [ ] [QD] 개정 문구가 이슈 #52의 결정 3건(강도·사용자 재정의·단계 중복 병합) 확정값과 의미상 일치한다 (검증: 교차모델 issue-audit, 별도 세션)  ← 강등 사유: 문구의 의미 적합성은 명령으로 환원 불가

## 전제 (Assumptions)

- 이 repo의 `issue-work/SKILL.md`가 SSoT다. `~/.claude/skills/issue-work/`는 `install-skills`로 배포된 사본이며, 이 이슈에서는 repo 본문만 수정한다 (배포 반영은 사용자가 별도 수행).
- 이슈 디렉토리·브랜치 명명은 4자리 0 패딩(`issue-0052`)이 repo 관례다.
- `--response` 동작의 번호 단계는 **5단계 구조를 유지**한다 — 이슈 본문이 "2단계에서", "3단계에", "4~5단계에"로 기존 단계 수정을 지시하므로, 게이트를 별도 6단계로 추가하는 안은 검토 후 배제했다 (다른 문서의 단계 번호 참조 안정성도 근거).
- 이슈 본문 "구현 시 결정할 것" 3건(강도 / 사용자 재정의 / 단계 중복 병합)은 spec 작성 시점에 미확정이었고, Task 0에서 사용자 질의로 아래와 같이 확정했다.
  - **강도 = 보정 보류**: 1단계 미충족(FAIL)·부분 충족(PARTIAL) 항목의 처리 방향이 전부 확정되기 전에는 2단계 항목 보정에 **착수하지 않는다**. 질의 순서만 앞세우는 약한 안은 배제했다 — 스펙 미충족이 남은 채 부가 개선이 진행되는 상황을 실제로 차단하기 위함이다.
  - **사용자 재정의 = 명시적 지시로만 개방**: 구현 AI는 위험도를 근거로 스스로 순서를 바꾸지 않는다. 위험도 높음(HIGH) 자동 예외 안은 배제했다 — 위험도가 audit 모델의 주관 평가라 게이트가 사실상 무력화된다.
  - **단계 중복 = 1단계로 병합해 1건**: 같은 결함이 1단계 부분 충족 근거이자 2단계 발견으로 함께 올라오면 한 항목으로 병합해 1단계 발견으로 취급하고, `audit 발견`·`보정 반영`에 1건만 센다. 기존 "한 발견이 여러 Task에 걸쳐도 주 Task 하나에만 귀속" 규칙(summary 템플릿)과 같은 취지다.
- 순서 게이트의 대상은 1단계 판정 중 **미충족(FAIL)·부분 충족(PARTIAL)**뿐이다 — 충족(PASS)·판정 불가(N/A)는 처리 방향 확정이 필요 없어 게이트를 막지 않는다.
- 1단계/2단계 용어는 `issue-audit` 리포트 구조(1단계 적합성 검증 / 2단계 비판적 검증)를 그대로 따른다. 판정값 표기도 `issue-audit`의 충족(PASS)·미충족(FAIL)·부분 충족(PARTIAL)·판정 불가(N/A)를 재사용한다.
