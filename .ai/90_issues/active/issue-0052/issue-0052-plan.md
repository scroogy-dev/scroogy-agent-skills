### Task 1: `--response` 동작 개정 — 단계 구분 제시·표 배치·순서 게이트

- [x] 완료
- **목표**: `issue-work/SKILL.md` `--response` 동작 5단계에 이슈 작업 내용 4건(구분 제시·상단 배치·순서 게이트·승인 원칙 유지)을 반영한다.
- **작업 내용**:
  1. 동작 2단계(피드백만 제시): 발견사항을 **1단계 발견 / 2단계 발견으로 나눠** 제시하도록 개정한다.
  2. 동작 3단계(처리 방향 표): 1단계 발견을 표 상단에 배치하고, 미해소 1단계 항목이 있으면 그 사실을 명시하도록 개정한다.
  3. 동작 4~5단계: 순서 게이트를 넣는다 — 1단계 미충족·부분 충족 항목의 처리 방향(반영/이관/보류)이 전부 확정되기 전에는 2단계 항목 보정에 들어가지 않는다. Task 0에서 확정한 결정 3건(강도·사용자 재정의·단계 중복)을 문구에 반영한다.
  4. 기존 항목별 승인 원칙 문구는 유지한다 — 순서만 규정하고 승인 게이트를 대체하지 않는다.
  5. 개정 문구에는 spec `완료의 정의`의 **앵커 토큰 계약**에 나열된 토큰을 지정된 단계 범위 안에 포함한다 — 같은 의미의 다른 표현은 불합격이다.
- **완료 기준**: repo 루트에서 아래 절 추출 함수를 먼저 정의한 뒤, 전 항목 충족 —

  ```bash
  RESP() { sed -n '/^### `--response`/,/^### `--clear`/p' issue-work/SKILL.md; }
  ```

  - 번호 단계 구조 유지: `RESP | grep -cE '^  [0-9]+\. \*\*[^*]+\*\*'` = 5 (정확히 5 — 그 외 번호 단계 0건을 겸한다)
  - 2단계 구분 제시: `RESP | awk '/^  2\. /{f=1} /^  3\. /{f=0} f' | grep -c '1단계 발견'` ≥ 1 그리고 같은 범위 추출에서 `grep -c '2단계 발견'` ≥ 1
  - 3단계 상단 배치·미해소 명시: `RESP | awk '/^  3\. /{f=1} /^  4\. /{f=0} f' | grep -c '상단'` ≥ 1 그리고 같은 범위 추출에서 `grep -c '미해소'` ≥ 1
  - 4~5단계 순서 게이트: `RESP | awk '/^  4\. /{f=1} f' | grep -c '순서 게이트'` ≥ 1
  - 승인 원칙 유지: `RESP | grep -c '항목 단위로'` ≥ 1 그리고 `RESP | grep -c '자동 보정하지 않는다'` ≥ 1 (절 전체 범위 — 기존 문구가 `경계` 항목과 동작 4단계에 나뉘어 있어 의도된 사양)
  - 단계 범위 추출(`awk`)은 다음 번호 단계 시작 행 직전까지 포함하므로, 단계 본문이 여러 행·하위 목록으로 늘어나도 판정이 유지된다. 토큰이 지정 범위 밖에서만 발견되면 불합격이다 (spec 앵커 토큰 계약).

### Task N (고정): 교차모델 issue-audit 검증 — 사용자 수동 수행

<!--

audit은 L2 [QD] 보완 검증 — L1 [D] 결정적 게이트의 대체가 아니라 보완이다.
이 Task는 사용자가 직접 수행하며, 구현 AI는 자동으로 닫지 않는다.
-->

- [ ] 완료
- **목표**: 스펙 위반·누락·소스코드와의 모순을 구현 모델과 다른 시각으로 잡는다.
- **실행 주체**: **사용자가 직접** 수행한다. 구현 AI는 이 Task를 **자동으로 닫지 않으며**, `issue-audit`를 자동 실행하지도 않는다.
- **작업 내용**:
  1. spec `완료의 정의`의 `[D]` 항목 검증 명령을 전부 재실행해 통과를 확인한다.
  2. 구현을 수행한 모델과 **다른 벤더 모델**(최소 동급 이상 역량)로 사용자가 직접 `issue-audit`를 실행한다. 방향은 칭찬이 아니라 허점 탐색("스펙 위반·누락·소스코드와의 모순을 찾아라").
  3. 사용자가 audit 결과(지적 사항·감사 모델)를 summary에 반영·기록한다. 발견사항 보정은 issue-work `--response`로 검토한다 — **피드백 먼저, 항목별 승인 후에만** 앞 Task를 보정하며, 리포트를 받자마자 자동 보정하지 않는다.
- **완료 기준**: `[D]` 검증 명령 전부 통과 + summary `모델 기록` 표의 `구현 모델`·`audit 모델` 두 행이 서로 다른 벤더로 채워진다("벤더, 모델명" 형식). 구현에 여러 벤더가 관여했으면 audit 모델의 벤더는 Task 0 및 일반 실행 Task의 비어 있지 않은 모든 `수행 모델` 값에 나열된 벤더 전부와도 달라야 한다 — 표의 대표값 비교만으로는 audit 벤더의 구현 참여를 놓치고, 한 Task를 여러 모델이 수행했으면 그 값에 나열된 벤더를 모두 비교 대상에 넣는다. 이때 완료·부분 완료 Task의 `수행 모델`은 `-`일 수 없다(`-`는 미착수·스킵 전용) — 전부 `-`로 남기면 이 강화 조건이 공집합이 되어 우회가 된다. 또한 이 검증 전에 Task 0 및 모든 일반 실행 Task의 summary `결과`가 완료·부분 완료·스킵 중 하나로 확정돼 있어야 한다 — `결과`를 비워 두면 "완료·부분 완료면 값 필수" 조건이 발동하지 않아 강화 조건이 다시 공집합이 되기 때문이다.
