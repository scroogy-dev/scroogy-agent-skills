# K-0031: git-review 브랜치 모드 수집은 Git이 스테이징하는 내용을 따라 일부 경로에서 작업 트리와 다르다

- **유형**: known issue
- **등재일**: 2026-11-20
- **출처**: 이슈 #142 / audit 발견 F-21, F-22 (계획 감사 7차)
- **위험도**: 낮음(LOW)
- **수용 사유**: 이슈 #142의 범위 줄·AC2와 spec R1이 브랜치 모드의 대상을 "지금 작업 트리를 전부 스테이징해 커밋하면 들어갈 변경"으로 정하고, 무엇이 스테이징되는지는 Git의 결과를 따른다고 적어 승인한 동작이다(2026-11-20, 7차 검토에서 예외 경로 2종을 승인하고 8차 검토에서 기준 문장을 바꿔 범위를 넓힘). 리뷰에 보이는 변경이 커밋 결과와 같다. Git의 상태와 설정의 조합은 열거로 닫히지 않아, 경로마다 작업 트리 기준을 맞추는 수정은 회차마다 새 사례를 만든다.
- **재검토 조건**: 브랜치 모드 리뷰에서 Git이 스테이징 내용을 정하는 경로 때문에 리뷰 대상이나 읽은 내용이 사용자 기대와 달랐던 사례 관측 시, 또는 `collect-branch-changes.sh`의 스냅샷 방식(실제 인덱스 사본에 `git add -u`·`git add -A`)을 바꿀 때
- **상태**: 수용

## 내용

git-review 브랜치 모드의 수집 헬퍼 `collect-branch-changes.sh`는 Git이 스테이징하는 내용을 대상으로 삼는다. 일반 파일은 작업 트리의 내용과 같지만, Git이 인덱스나 설정으로 스테이징 내용을 정하는 경로(변경을 보지 않도록 표시한 경로, 무시 규칙에 걸린 파일과 `.ai/99_workspace/` 아래 파일, 하위 모듈, 내용 변환 필터, 희소 체크아웃 등)는 작업 트리와 다를 수 있다. 이 경로에서는 리뷰가 주변 코드를 찾아 읽는 작업 트리의 내용도 커밋될 내용과 다를 수 있다. 발견의 성립은 수집한 내용(merge-base 커밋과 헬퍼의 patch)으로 확인한다. spec R1이 보장하는 네 성질(일반 파일의 인덱스 상태 무관, 목록의 완전성, 저장소 무변경, 발견을 수집한 내용으로 확인)이 성립하지 않는 사례는 이 항목의 수용 범위가 아닌 결함이다.

<summary>근거·배경 펼치기</summary>

- **관측**: 이슈 #142 7차 계획 감사가 계획한 스냅샷 명령을 임시 저장소에서 실행해 두 동작을 재현했다(F-21은 5차 F-19의 잔여, F-22는 신규). 8차는 같은 구조에서 읽기 기준(F-24)과 하위 모듈 무시 설정(F-25)을 지적했다. 9차는 내용 변환 필터가 걸린 주변 파일의 읽기(F-27)를 지적했다.
- **영향**: 기능 저하. 리뷰는 수행되고, 해당 경로의 변경만 작업 트리와 다르게 잡힌다. 잡힌 내용은 지금 전부 스테이징해 커밋하면 들어갈 내용과 같다.
- **발생확률**: 특수 조건·엣지. 변경을 보지 않게 하는 표시, 기준 커밋이 추적하는 무시 파일·작업공간 파일의 스테이징 삭제, 하위 모듈, 필터 같은 Git 기능을 쓰는 저장소에서 브랜치 모드를 실행할 때만 나타난다.
- **위험도 산출**: `classify-risk.sh --impact '기능 저하' --likelihood '특수 조건·엣지'` → 낮음(LOW). 7차 감사 리포트는 당시 AC2 문장을 기준으로 영향을 스펙·기능 달성 차단으로 보아 중간(MEDIUM)으로 산출했다. 같은 검토에서 AC2에 예외 경로를 적어 승인했으므로 영향 축을 다시 판정했다.
- **수용 범위의 동작**:
  - 변경을 보지 않도록 표시한 경로(`assume-unchanged`, `skip-worktree`)는 인덱스의 내용을 쓴다. 작업 트리만 고친 수정은 빠지고, 스테이징한 뒤 작업 트리에서 되돌린 수정은 들어간다. 읽을 때도 인덱스의 내용을 읽는다.
  - 무시 규칙에 걸린 파일과 `.ai/99_workspace/` 아래 파일은 인덱스에 있을 때만 읽는다. 기준 커밋이 추적하던 파일을 인덱스에서만 지우면 작업 트리에 파일이 있어도 삭제로 나온다.
  - 하위 모듈은 가리키는 커밋이 바뀐 것만 나온다. 하위 모듈 안의 커밋하지 않은 변경은 나오지 않는다.
  - 내용 변환 필터(줄 끝 변환 등)를 쓰는 파일은 변환을 거친 내용이 대상이다. 스테이징할 때 내용을 바꾸는 필터는 9차 검토에서 실행해 확인했다(Git 2.50.1, 작업 트리의 바이트와 커밋될 내용이 다르다).
  - 희소 체크아웃으로 작업 트리에 없는 경로는 인덱스의 내용 그대로다. 이 동작은 `git add`의 규칙에서 나온 것이며 실행해 확인하지 않았다.
  - 위 경로의 주변 코드를 작업 트리에서 찾아 읽으면 커밋될 내용과 다른 값이 보일 수 있다. 발견을 기록하기 전의 확인은 merge-base 커밋과 patch로 한다.
- **통상 용도에서의 동작**:
  - 무시 파일을 `git rm --cached`로 지우는 것은 추적 해제이며 그대로 커밋하면 저장소에서 삭제된다. 삭제로 보고하는 쪽이 커밋 결과와 맞는다.
  - 변경을 보지 않게 하는 표시는 커밋하지 않을 로컬 수정을 숨기는 데 쓴다. 그 수정이 리뷰에 나오지 않는 쪽이 `git status`와 커밋 결과에 맞는다.
- **채택하지 않은 대안(지금 고치지 않은 이유)**:
  - 임시 인덱스를 `HEAD` 트리로 채워 인덱스를 입력에서 빼는 안: 위 통상 용도의 동작이 반대로 바뀐다. macOS처럼 대소문자를 구분하지 않는 파일 시스템에서 대소문자만 바꾼 이름 변경이 커밋 전까지 빠지고, 희소 체크아웃(sparse checkout)에서는 작업 트리에 없는 경로가 삭제로 나와 별도 처리가 필요하다.
  - 경로마다 분기를 더하거나 예외 경로를 열거하는 안: 3~6차 계획 감사에서 같은 원인의 발견(F-14·F-17·F-19·F-20)을 사례별로 막다가 6차에 수집 정의와 헬퍼로 바꿨고, 7차에 예외 경로 2종을 열거했으나 8차에 열거 밖의 설정(F-25)이 다시 나왔다. 8차에 기준 문장을 "커밋하면 들어갈 변경"으로 바꾸고 보장하는 성질을 넷으로 고정했다.
- **우회**: 해당 경로의 작업 트리 변경을 리뷰에 넣으려면 표시를 풀거나(`git update-index --no-assume-unchanged`·`--no-skip-worktree`) 파일을 다시 추적(`git add -f`)한 뒤 실행한다. 커밋한 뒤에는 PR 모드가 커밋 내용을 그대로 리뷰한다.
