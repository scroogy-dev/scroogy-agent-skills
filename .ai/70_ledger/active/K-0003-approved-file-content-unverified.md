# K-0003: 승인한 제목·본문 파일의 내용 동일성이 제출 직전에 검증되지 않는다

- **유형**: known issue
- **등재일**: 2026-08-07
- **출처**: 이슈 #74 / audit 발견 F-1
- **위험도**: 낮음(LOW)
- **수용 사유**: 이번 이슈가 만든 회귀가 아니다 — 변경 전에도 제출값은 `--title "$(cat …)"`·`--body-file`이 읽는 파일이었고, 오히려 승인 대상(대화 텍스트)과 제출 대상(파일)이 어긋나 있던 구조가 이번 변경으로 같은 객체로 일치했다. 스펙 #74가 요구한 것은 "게이트 절차 불변"이고 절차는 유지되므로 내용 동일성 검증은 스펙 밖의 추가 보장이다. 해시 고정·보관·재검증 3단계를 스킬 문서에 넣는 실행 부담에 비해 실현 조건(승인~생성 사이 수 초 창에 제3자가 파일을 수정)이 좁다.
- **재검토 조건**: `git-pr/SKILL.md` 3·4단계의 승인 게이트를 다시 수정할 때, 또는 승인 후 제출 전에 제목·본문 파일이 바뀌어 승인하지 않은 내용이 게시된 사례가 관측될 때
- **상태**: 수용

## 내용

`git-pr`는 승인받은 대상 저장소와 커밋 SHA를 불변 값으로 보관해 4단계에서 재검증하지만, 제목·본문 파일에는 동등한 검증이 없다. 3단계 승인과 4단계 외부 쓰기 사이에 사용자·다른 에이전트·도구가 `.ai/99_workspace/pr-<이슈번호>-{title,body}.md`를 수정하면 승인 화면의 요약과 실제 PR 내용이 달라질 수 있다. `issue-work --clear` 3단계의 이슈 댓글 파일(`issue-<번호>-comment.md`)도 같은 구조다.

## 재검토 이력

없음

- **발생확률**: 특수 조건·엣지. 사용자가 수정을 요청하는 정상 경로는 같은 파일을 갱신한 뒤 다시 제시하도록 규정되어 있어(`git-pr/SKILL.md` 2단계 마지막 불릿) 승인 없이 내용이 바뀌지 않는다. 실현하려면 승인 직후~생성 직전의 좁은 구간에 제3자 개입이 필요하다.

- **채택하지 않은 대안**: 3단계에서 파일별 내용 해시를 승인값과 함께 고정하고 `gh`·MCP 외부 쓰기 직전에 재검증해 불일치 시 중단·재승인하는 안. 보장은 확실하지만 `git-pr/SKILL.md`·`issue-work/SKILL.md` 양쪽에 해시 계산·보관·재검증 절차를 추가해야 하고, 스펙 #74의 범위(중복 생성 제거)를 넘는다.
