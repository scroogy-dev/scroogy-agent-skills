# 이슈 워크플로우

> 이 파일은 AI가 컨텍스트 초기화 후에도 작업 절차를 따를 수 있도록 제공됩니다.

---

## 디렉토리 구조

```
.ai/90_issues/
├── active/
│   ├── issue-workflow.md          ← 이 파일
│   └── issue-<번호>/
│       ├── issue-<번호>-spec.md      ← 목표, 요구사항, 완료의 정의, 결정 사항, 변경 이력, 연관 문서
│       ├── issue-<번호>-plan.md      ← 설계 결정, 테스트 계획, 실행 Task 목록 + 완료 체크박스
│       └── issue-<번호>-summary.md   ← 다음 작업, 루프 기록, 종류별 발견, Task별 수행 결과
└── archive/    ← 완료 또는 종료된 이슈 디렉토리 (명시적 요청 시에만 읽음)
```

**AI 컨텍스트 적재 규칙:**
- `active/` 하위 파일은 작업 시작 시 **항상** 읽는다.
- `archive/` 하위 파일은 사용자가 명시적으로 언급하지 않는 한 **읽지 않는다.**

## 진행 루프

```
       이슈 등록 (--create)
            |
            v
  +--> 1. 계획 수립
  |         |    spec, plan이 없으면 쓰고, 지난 회차에서 바꿀 것이 나왔으면 고친다
  |         v
  |    2. 계획 검증
  |         |    AC, 요구사항, 설계 결정, 테스트 계획이 바뀌었을 때만 계획 감사를 받는다
  |         v
  |    3. 구현
  |         |    Task마다 테스트 작성 -> 실패 확인 -> 구현 -> 통과 확인
  |         v
  |    4. 구현 검증
  |         |    구현이 바뀌었을 때 교차 감사를 전체로 받는다
  |         v
  +--- 5. 완료 확인
            |    감사 상태와 테스트 계획 확인 줄 수를 보이고 마무리나 다음 회차를 권장한다
            |    사용자가 다음 회차로 정하면 1로 돌아간다
            v
       Task N (마무리)
            |    전체 회귀, 색인, --clear, PR
            v
       PR 뒤 피드백은 git-pr-feedback으로 처리한다
```

계획 수립에서 완료 확인까지 한 번 지나는 것이 한 회차다. 회차를 시작할 때 summary `루프 기록`에 한 행을 더하고 단계를 지날 때마다 채운다. 감사를 받기 전에 감사 대상에 미커밋 변경이 있으면 커밋할지 사용자에게 묻는다. 커밋하지 않고 받으면 커밋한 대상으로 다시 받을 때까지 바뀐 것으로 본다. 상세는 issue-work SKILL.md `## 진행 루프`를 따른다.

1. **계획 수립**: spec·plan이 없으면 쓰고, 있으면 지난 회차의 결정을 반영해 고친다. 반영으로 정한 발견은 plan에 Task로 더하고, 같은 종류의 발견이 지난 두 회차에 이어서 나왔으면 plan `설계 결정`부터 고친다.
2. **계획 검증**: 계획 감사를 받기로 한 이슈는 지난 검증 뒤에 AC·요구사항, `설계 결정`, `테스트 계획` 가운데 하나가 바뀌었으면 계획 감사를 다시 받는다. 6단계(이슈 본문 갱신 질의)나 Task 0에서 바뀐 것도 같으며 일반 Task를 시작하기 전에 받는다. 기존 AC 안에서 발견을 고치는 Task를 더한 것만으로는 다시 받지 않는다.
3. **구현**: Task마다 테스트 작성 → 실패 확인 → 테스트 커밋 → 구현 → 통과 확인 → 구현 커밋 순서로 진행한다. 동작을 바꾸지 않는 Task는 구현 → 통과 확인 두 단계로 진행한다.
4. **구현 검증**: 지난 검증 뒤에 구현이 바뀌었으면 사용자가 구현 모델과 다른 벤더 모델로 교차 감사를 전체로 다시 받는다. spec·plan의 변경(체크박스와 `확인` 칸만 바뀐 것은 빼고)과 Git이 무시하지 않는 미추적 파일도 구현이 바뀐 것으로 센다. 구현 AI는 감사를 실행하지 않는다.
5. **완료 확인**: 감사 상태와 `테스트 계획`의 확인한 줄 수를 보이고 아래 기준으로 `마무리`나 `다음 회차`를 권장한다. 루프를 나갈지는 사용자가 정하고, 정한 값을 summary `루프 기록`의 `결정` 칸에 적는다.

- **권장 기준**: 아래 네 가지가 모두 맞으면 `마무리`, 그 밖은 `다음 회차`를 권장한다. 기준에 못 미친 채 `마무리`로 정하면 남은 AC와 발견마다 완화·원장 등재·새 이슈 가운데 결정을 받는다.
  - 1단계 상태: 충족(PASS)이다.
  - 2단계 상태: 통과(PASS)나 주의(WARN)다.
  - 확인한 줄 수: `테스트 계획`의 모든 줄을 확인했다.
  - 반영으로 정한 발견: 모두 닫았다. 이관이나 보류로 정한 발견은 세지 않는다.
- **마무리**: 사용자가 `마무리`로 정한 뒤에만 Task N에 들어간다. Task N은 전체 회귀, 색인, 충족 AC 체크, repo 고유 마무리, `--clear`, PR을 이 순서로 하고, 교차 감사를 받지 않는다. PR은 Task N에서 git-pr로 만든다. Task N에서 구현을 고치면 계획 수립으로 돌아간다.
- **PR 뒤 피드백**: PR에 달린 리뷰 피드백은 git-pr-feedback으로 처리한다. 피드백으로 구현을 고쳤을 때 교차 감사를 다시 받을지는 사용자가 고른다. PR을 만든 뒤에는 이슈 문서를 고치지 않는다.

## 작업 진행 중

- 계획 감사를 수행한 이슈는 그 리포트(`.ai/99_workspace/issue-<번호>-plan-audit-report.md`)를 issue-work `--response`로 검토하고 승인분을 spec·plan에 반영한다. 발견·보정 건수는 summary `모델 기록` 표 아래 `계획 감사` 줄에 적고, 건너뛴 이슈는 그 줄과 `계획 audit 모델` 행에 `생략`을 적는다. 감사 수행 여부와 관계없이 summary `이슈 본문 갱신` 줄이 비어 있으면 issue-work "새 이슈 시작 시" 6단계(이슈 본문 갱신 질의)를 거친 뒤 Task 0에 착수한다. 갱신하면 그 줄에 `갱신 · <AC 번호>`를, 거절하면 `거절 · <AC 번호>`를 적고, 거절하면 본문을 바꾸지 않고 spec의 AC가 기준이 된다.
- **구현 착수 전 Task 0(구현 시작 게이트)을 먼저 수행한다**. spec/plan만으로는 알 수 없는 전제·모호점을 나열하고, 항목이 있으면 코드를 쓰기 전에 사용자에게 질의해 답변을 spec `## 결정 사항`이나 plan `## 설계 결정`에 적는다. 없으면 summary에 `전제 누락 없음`을 기록한다. 문서를 쓴 세션과 구현하는 세션이 다르면 모델이 같아도 수행한다.
- **변경 통제**: 3-2 작성과 작업 진행 중에 spec 요구사항·완료의 정의·결정 사항이나 커밋한 테스트를 바꾸는 변경은 구체화·확장·완화로 분류한다. 구체화(판정 기준만 명확히 하는 변경)는 질의 없이 반영하고, 확장(AC에 없는 결과를 더하는 변경)은 범위 확장·원장 등재·새 이슈(`--create`) 중에서 고르게 묻는다. 완화(오류 상황·성공 조건을 빼거나 약하게 하거나 AC를 빼거나 제외로 옮기는 변경)는 재승인 없이 반영하지 않는다. 커밋한 테스트의 기대값을 바꾸거나 단언을 줄이거나 테스트를 지우는 변경도 완화다. 결과는 그대로이고 이름·위치·준비 코드·호출 방식만 바뀌는 테스트 수정은 질의 없이 반영한다. 승인 뒤에 바뀐 요구사항·AC·결정은 spec `변경 이력`에 적는다. 기준선과 처리 상세는 issue-work SKILL.md `## 작업 진행 중`의 변경 통제를 따른다.
- Task 완료 시 `issue-<번호>-plan.md`의 해당 Task 체크박스를 체크한다.
- Task 완료 시 `issue-<번호>-summary.md`의 수행 결과(`테스트`·`대응 발견` 포함)를 갱신하고 다음 작업을 업데이트한다.
- 구현 검증 단계의 교차 감사 리포트(`.ai/99_workspace/issue-<번호>-audit-report.md`)를 받으면 issue-work `--response` 옵션으로 검토한다. 발견사항에 **피드백 먼저, 항목별 결정 다음**이며 이 단계에서는 소스를 고치지 않는다. 반영으로 정한 발견은 다음 회차의 계획 수립에서 plan에 Task로 더해 고치고, 발견의 종류는 summary `종류별 발견`에 적는다.
- 검토에서 "이관"으로 정한 발견은 원장 `.ai/70_ledger/active/`에 등재한다. 등재 형식은 `.ai/70_ledger/ledger-entry-template.md`를 따르고 **수용 사유·재검토 조건**을 필수로 기재한다. 별도 이슈 승격은 등재 후 항목 `상태`를 바꾸는 후속 단계다. 이미 등재된 항목이 다시 올라오면(계보 `기등재 K-<번호> 재제기`) 새 번호를 따지 않고 그 항목을 갱신하거나 종결한다.

## 이슈 완료 시

1. `issue-<번호>-plan.md`의 계획 종료 게이트 `점검 완료`, Task 0, 일반 Task의 체크박스가 체크되었는지 확인한다 (게이트 체크박스는 `## Tasks` 밖에 있어 Task 체크박스만 세면 누락된다). Task N의 미체크는 미완료로 세지 않는다. summary `루프 기록` 마지막 행의 `결정`이 `마무리`인지도 본다. 미완료 항목이 있으면 보여 주고 계속할지 묻는다.
   - 단, **사용자가 직접 받은 교차 감사의 결과와 최종 audit 모델("벤더, 모델명 (모델 ID)")이 summary `모델 기록` 표의 `최종 audit 모델` 행에 기록된 경우에만 완료로 간주**한다. 구현 AI는 이 기록을 **대신 채우지 않는다.**
2. `issue-<번호>-summary.md` 상단의 다음 작업을 `✅ 모든 작업이 완료되었습니다.`로 업데이트한다.
3. `issue-<번호>/` 디렉토리를 `active/`에서 `archive/`로 디렉토리 단위로 이동한다. 1단계를 미완료 항목 없이 마쳤으면 이관 직전에 plan의 Task N 체크박스를 체크하고, summary Task N 블록의 `결과`에 `완료`를, `수행 내용 요약`에 `PR 대기(git-pr로 생성)`를 적는다.
   이 이동은 **PR 머지 전, 작업 브랜치에서 수행해 같은 PR에 포함**한다 (머지 후 실행하면 `main` 직접 푸시가 된다).
   - **원장 해소 기재**: spec 요구사항에 `(함께 해소: K-<번호>)`로 표기한 원장 항목 가운데 이번 작업으로 원인이 사라진 항목을 종결한다. `해소(PR #N)`은 PR 번호를 알 때만 확정한다.
     - PR이 이미 있으면 상태를 `해소(PR #N)`으로 바꾸고 `.ai/70_ledger/archive/`로 옮긴 뒤 `.ai/70_ledger/index.md`를 갱신해 머지 전 같은 PR에 포함한다.
     - PR이 아직 없으면(확인할 수 없을 때 포함) 해소를 확정하지 않고 `active/`에 둔다. PR 생성 후 git-pr 4단계 "원장 해소 기재"가 번호를 적는다.
     - 원장 항목을 `archive/`로 옮겼으면 그 항목을 가리키는 다른 `.ai/` 문서의 링크(원장 항목 파일끼리의 링크 포함, `.ai/90_issues/archive/` 제외)를 새 경로로 고치고 `check-ledger-links.sh`로 끊긴 원장 링크가 0건인지 확인한다 (상세는 issue-work SKILL.md `## 이슈 완료 시`의 들어오는 링크 갱신).
   - **보류 항목 원장 등재 질의**: spec `제외` 목록에서 사유가 `보류`인 항목을 보여 주고 원장 등재 여부를 묻는다. 승인한 항목만 `.ai/70_ledger/ledger-entry-template.md` 형식으로 등재하며, `출처`는 `이슈 #N`이고 수용 사유·재검토 조건은 필수다. 같은 대상을 기록한 원장 항목이 이미 있는 보류 항목만 건너뛴다 (중복 판정 상세는 issue-work SKILL.md `## 이슈 완료 시`).
4. 이동한 파일 본문의 **경로 참조 갱신**을 수행하고 잔존 참조 0건을 확인한다 (갱신 규칙·검증 스니펫은 issue-work `--clear` 6단계와 동일).

> 위 절차에 더해 `99_workspace` 정리와 이슈 댓글 요약 등록까지 한 번에 수행하려면 issue-work `--clear` 옵션을 사용한다.
