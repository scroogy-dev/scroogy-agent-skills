## 개요

이슈 단위로 스펙·실행 계획·수행 요약 파일을 생성하고 관리하는 워크플로우입니다.

## 관련 skill

- ai-workspace (권장): `.ai/` 구조가 이미 존재하면 해당 구조를 따릅니다.
  구조가 없으면 필요한 디렉토리를 직접 생성합니다.
- issue-audit (권장): 진행 루프의 구현 검증 단계에서 사용합니다. 구현 모델과 **다른 벤더 모델**로 **사용자가 직접** `issue-audit`를 실행하고, 그 결과를 `issue-<번호>-summary.md`의 `루프 기록`, `모델 기록` 표 `최종 audit 모델` 행(모델·effort), Task별 수행 결과(`audit 발견` 건수)에 반영합니다. **구현 AI는 감사를 실행하지 않습니다.**
  계획 검증 단계의 **계획 감사**(`issue-audit --plan`)에도 같은 원칙을 적용합니다. 이슈마다 수행 여부를 선택하고("새 이슈 시작 시" 5단계), 수행하면 계획 모델과 다른 벤더 모델로 사용자가 직접 실행하며, 결과는 `모델 기록` 표 `계획 audit 모델` 행(모델·effort)과 `계획 감사` 줄에 반영합니다.
- git-pr (권장): 마무리(Task N)에서 PR을 만들 때 사용합니다.
- git-pr-feedback (권장): PR 뒤의 리뷰 피드백을 처리할 때 사용합니다.

## 디렉토리 구조

```
.ai/90_issues/
├── active/     ← 현재 진행 중인 이슈 디렉토리 (항상 읽음)
│   ├── issue-workflow.md         ← 작업 절차 가이드 (컨텍스트 초기화 후에도 절차 유지)
│   └── issue-<번호>/
│       ├── issue-<번호>-spec.md      ← 목표, 요구사항, 완료의 정의, 결정 사항, 변경 이력, 연관 문서
│       ├── issue-<번호>-plan.md      ← 설계 결정, 테스트 계획, 실행 Task 목록 + 완료 체크박스
│       └── issue-<번호>-summary.md   ← 다음 작업, 루프 기록, 종류별 발견, Task별 수행 결과
└── archive/    ← 완료 또는 종료된 이슈 디렉토리 (명시적 요청 시에만 읽음)
    └── issue-<번호>/   ← 이슈 디렉토리 단위로 active에서 이관
```

**AI 컨텍스트 적재 규칙:**
- `active/` 하위 파일은 작업 시작 시 **항상** 읽는다.
- `archive/` 하위 파일은 사용자가 명시적으로 언급하지 않는 한 **읽지 않는다.**

## 새 이슈 시작 시

이 절은 `## 진행 루프`의 다섯 단계 가운데 **계획 수립**(1~4단계)과 **계획 검증**(5단계)에 해당한다. 6단계는 구현으로 가기 전의 질의다.

- **첫 회차의 계획 수립**: spec·plan이 없으면 1단계부터 차례로 쓴다.
- **뒤 회차의 계획 수립**: 지난 회차의 결정을 반영해 spec·plan을 고친다. 1~3단계를 다시 밟지 않는다. 고친 뒤 계획 검증을 다시 받을지는 5단계의 조건으로 정한다.
  - **spec**: 요구사항·AC·결정이 바뀔 때만 고친다. `## 작업 진행 중`의 변경 통제를 따르고 `변경 이력`에 한 줄을 적는다.
  - **plan**: 발견을 고치는 Task를 Task N 앞에 다음 번호로 더한다. 구조나 테스트를 바꿔야 하면 `설계 결정`·`테스트 계획`도 고친다.
  - **summary**: 더한 Task의 블록을 plan과 같은 순서로 더한다.

1. `active/` 안에 있는 기존 이슈 디렉토리를 모두 `archive/`로 이동한다.
2. `active/issue-workflow.md`가 없으면 이 skill 디렉토리의 `templates/issue-workflow-template.md`를 참조하여 생성한다. 이미 있으면 템플릿과 내용을 비교해, 다르면 최신 템플릿으로 갱신(덮어쓰기)하고 동일하면 그대로 둔다. (템플릿이 SSoT이며 이 파일은 그 사본이므로, 템플릿 개선이 자동 반영된다.)
3. `active/issue-<번호>/` 디렉토리를 생성하고 이 skill 디렉토리의 `templates/`를 참조하여 3개 파일을 아래 두 단계에 나눠 생성한다. 3-1에서는 spec만 만들고, plan·summary 파일은 3-2에서 만든다. spec은 **요구사항 승인 게이트**를 사이에 두고 두 번에 나눠 쓴다.
   - **3-1. 승인 전 (요구사항까지)**: spec 템플릿의 목표·요구사항(포함·제외)·연관 문서 후보까지 쓴다. 요구사항은 이슈 본문의 묶음 제목과 문장을 그대로 옮긴다. 연관 문서 후보는 `.ai/30_contract/index.md`, `.ai/40_domain/index.md`, `.ai/50_adr/index.md`를 훑어 제안한다. 쓴 뒤 사용자에게 **승인**을 요청한다.
     - 승인 요청은 spec 파일 경로와 **목표 한 줄**·**포함 목록**·**제외 목록**만 대화에 제시하고 spec **전문을 대화에 출력하지 않는다** (`--clear` 3단계 댓글 승인과 같은 방식). 승인 대상은 파일이고, 같은 텍스트를 대화에 다시 만들면 응답만 늦어진다.
     - 포함·제외 목록은 spec의 묶음대로 나눠 보여 주고, R은 한 문장 그대로 보여 준다.
     - GitHub **이슈 본문에 근거가 없는** 요구사항(작성 AI가 대화·추론으로 더한 항목)은 목록에서 따로 표시하고, 추가로 확정할지 제외할지 질의한다. 표시 없이 섞이면 사용자가 요청하지 않은 범위를 그대로 승인하게 된다.
     - **함께 해소 후보**: 연관 문서 후보를 제안할 때 `.ai/70_ledger/index.md`도 훑어, 이슈 범위와 관련된 `active/` 항목을 `함께 해소 후보`로 제시한다. 후보도 이슈 본문 근거 없는 요구사항처럼 목록에서 따로 표시하고 포함 여부를 질의한다. 포함하면 요구사항(R)에 넣고 R 첫 줄 끝에 `(함께 해소: K-<번호>)`를 병기하며, 포함하지 않은 후보는 spec 어디에도 기록하지 않는다. 원장 index가 없으면 건너뛴다. 이 단계에서는 원장 상태를 바꾸지 않으며, 포함한 항목의 종결은 `## 이슈 완료 시` 3단계의 원장 해소 기재가 맡는다.
     - 수정 요청을 받으면 spec을 갱신하고 같은 형식으로 다시 요청한다. 승인 전에는 완료의 정의·결정 사항·plan·summary를 쓰지 않는다.
   - **3-2. 승인 후**: 승인받은 요구사항을 기준으로 spec의 **완료의 정의**·**결정 사항**을 채우고 plan·summary를 쓴다. summary에는 `모델 기록` 표의 `계획 모델` 행의 모델과 effort를 이때 채운다(모델은 계획 감사가 벤더 차이를 확인하는 근거, 모델 ID와 effort를 읽는 위치는 `## 작업 진행 중`의 `수행 effort` 규칙). 완료의 정의 AC 행의 `(R<n>)` 표기와 plan Task의 `대상 요구사항` 필드는 승인받은 R 번호만 참조한다.
     - **AC 옮기기**: 이슈 본문의 AC를 같은 묶음 제목·문장·번호로 옮기고, 행 끝에 그 AC가 판정하는 요구사항을 `(R<n>)`이나 `(R<n>, R<m>)`으로 붙인다. 이슈 본문에 `- [ ] AC<n>: ` 또는 `- [x] AC<n>: ` 형식 행이 1개 이상 있으면 AC가 있는 이슈다.
       - **연결**: 모든 AC 행에 R 표기가 있고 포함 R마다 AC가 1개 이상 연결된다. 같은 AC 번호의 행은 하나다.
       - **AC 없는 R**: 이슈 본문의 AC가 대응하지 않는 R마다(AC가 없는 이슈는 모든 R) spec이 AC를 다음 번호로 직접 쓴다. 이슈 본문에 올릴지는 6단계가 묻는다. 이슈 본문의 AC가 이미 대응하는 R에 AC를 더하는 것은 변경 통제의 확장이다.
       - **번호 유지**: AC 번호는 뒤에만 추가하고 다시 매기지 않는다. 이슈 본문·spec·PR이 같은 번호로 AC를 가리키기 때문이다.
       - **적지 않는 것**: 레벨 태그, 검증 명령, 케이스 목록을 적지 않는다. 검증은 plan `테스트 계획`이 맡는다.
     - **결정 사항**: 이슈 본문의 `정한 것`과 사용자가 답한 `검토 필요`를 `- D<n> <이름>: <내용>` 행으로 옮기고, 계획을 쓰며 정한 제품·도메인 결정을 더한다. 적을 결정이 없으면 섹션을 두지 않는다.
     - **테스트 계획**: plan에 AC마다 어느 층의 어느 테스트가 보는지 한 줄 이상 적는다. 단위 테스트를 먼저 고르고, 단위보다 위 층을 쓰면 단위로 못 보는 이유를 적는다. 명령으로 판정하지 못하는 것은 `테스트로 못 보는 항목` 표에 적는다.
     - **설계 결정**: 필요할 때만 plan에 쓴다. 적을 것과 섹션을 두지 않는 기준은 plan 템플릿을 따른다.
     - **테스트 층 표**: `.ai/10_rules/testing-principles-local.md`가 있으면 plan `테스트 계획`의 `층` 칸은 그 파일의 테스트 층 표에서 고르고, plan Task의 러너 호출·출력 판독·실행 셸도 그 표와 실행 셸을 따른다. 기기 확인 Task는 두지 않는다(실기기 확인은 이슈 진행과 무관하게 사용자가 요청할 때만 한다). 파일이 없으면 이 항목을 건너뛰고 템플릿 그대로 쓴다.
     - **변경 통제**: 3-2에서 쓰는 중의 변경은 `## 작업 진행 중`의 변경 통제를 따른다. 확장·완화로 분류한 변경은 질의·재승인 없이 spec에 반영하지 않는다.
4. plan 작성을 끝내기 직전에 plan 템플릿의 **계획 종료 게이트**(`## Tasks` 앞 고정 블록)를 수행한다. spec/plan만 보고 작성에 참여하지 않은 쪽이 구현할 수 있는지 자기점검하고, 문서에 없던 것을 spec `## 결정 사항`이나 plan `## 설계 결정`에 적는다. 제품·도메인 내용은 spec에, 설계 내용은 plan에 둔다. 발견이 없으면 체크만 한다.
5. 계획 종료 게이트를 지나면 **계획 감사**(`issue-audit --plan`) 수행 여부를 사용자에게 질의한다. 수행 여부는 이슈에 한 번 묻고 **기본값 없이** 사용자가 정하며, 구현 AI가 수행 여부를 스스로 판정하지 않는다.
   - **수행**: 사용자가 계획 모델과 **다른 벤더** 모델로 `issue-audit --plan`을 직접 실행한다(구현 AI는 자동 실행하지 않는다). 리포트 `.ai/99_workspace/issue-<번호>-plan-audit-report.md`를 받으면 `--response`로 검토해 승인분을 spec·plan에 반영한다. 반영한 결과가 아래 다시 받는 조건에 맞으면 계획 감사를 다시 받고, 맞지 않으면 6단계로 진행한다. summary `모델 기록` 표의 `계획 audit 모델` 행에 감사 모델("벤더, 모델명 (모델 ID)")과 effort(리포트의 `감사 effort` 줄 값)를, 표 아래 `계획 감사` 줄에 `수행 · 발견 N건 · 보정 N건`을 적는다.
   - **건너뜀**: summary `모델 기록` 표의 `계획 audit 모델` 행과 `계획 감사` 줄에 `생략`을 적고 6단계로 진행한다. 생략을 기록해 두어야 뒤에 감사가 없었다는 사실이 남는다. 건너뛰기로 정한 이슈는 뒤 회차에서 다시 묻지 않는다.
   - **다시 받는 조건**: 수행으로 정한 이슈는 지난 계획 검증 뒤에 아래 셋 가운데 하나라도 바뀌면 계획 감사를 다시 받는다. 조건은 이 셋이 전부다.
     - AC·요구사항: spec 요구사항과 완료의 정의가 바뀌었다.
     - `설계 결정`: plan `설계 결정`이 바뀌었다.
     - `테스트 계획`: plan `테스트 계획`이 바뀌었다. `확인` 칸만 바뀐 것은 변경으로 보지 않는다.
   - **5단계 뒤의 변경**: 6단계나 구현 시작 게이트에서 다시 받는 조건에 맞는 변경이 생기면 그 단계를 마친 뒤, 일반 Task를 시작하기 전에 계획 감사를 다시 받는다. 건너뛰기로 정한 이슈와 조건에 맞지 않는 변경은 그대로 진행한다.
   - **다시 받지 않는 변경**: 기존 AC 안에서 발견을 고치는 Task를 더한 것만으로는 다시 받지 않는다.
   - **바뀌었는지의 판별**: summary `루프 기록`에서 `계획 검증 커밋` 칸에 값이 있는 가장 최근 행의 커밋 뒤 diff로 한다. 그 칸에 `(미커밋 포함)`이 있으면 diff로 가리지 않고 바뀐 것으로 본다. 감사한 내용이 그 커밋에 없어 원복한 변경이 diff에 나타나지 않기 때문이다.
6. 5단계 계획 감사 처리(수행이면 `--response` 반영까지)를 마친 뒤 Task 0 전에 **이슈 본문 갱신 질의** 대상인지 판정한다. 대상은 이슈 본문에 없어 spec이 직접 쓴 AC가 있는 이슈다(3-2 `AC 옮기기`의 AC 없는 R). 대상이 아니면 summary `이슈 본문 갱신` 줄에 `대상 아님`을 적고 Task 0으로 진행한다. 대상이면 아래 순서로 질의하며, 사용자가 승인할 때만 이슈 본문을 바꾼다.
   - **대상 저장소**: `--create` 3단계의 대상 저장소 규칙으로 정한다. 대상 저장소와 이슈 번호는 작은따옴표로 감싸고, 값 속 작은따옴표는 그 자리만 `'\''`로 바꾼다. `gh`를 쓸 수 없으면 `--create` 4단계와 같은 조건으로 GitHub MCP에 폴백하고 `owner`·`repo`를 대상 저장소로 넘기며, 폴백해도 아래 기준 본문 비교는 그대로 거친다.
   - **기준 본문**: 초안을 쓰기 직전에 아래 명령으로 이슈 본문을 다시 받아 `.ai/99_workspace/issue-<번호>-body-base.md`에 둔다(디렉토리가 없으면 만든다). spec을 쓸 때 읽은 본문은 쓰지 않는다. 계획 감사 동안 GitHub에서 고친 내용이 초안에서 빠져 덮어쓰이기 때문이다. 조회가 실패하면 초안을 쓰지 않고 오류를 보고한 뒤 다시 시도할지 묻는다.

     ```bash
     gh issue view '<앞자리 0 제거한 이슈 번호>' --repo '<대상 저장소>' --json body -q .body > '.ai/99_workspace/issue-<번호>-body-base.md'
     ```

   - **초안**: 기준 본문은 그대로 두고 AC 행만 더한 전체 본문을 `.ai/99_workspace/issue-<번호>-body.md`에 1회 쓴다. 더하는 행은 spec이 직접 쓴 AC이고, 이슈 본문 템플릿 형식 `- [ ] AC<n>: `으로 spec과 같은 번호와 문장을 쓰며 행 끝의 `(R<n>)` 표기는 옮기지 않는다. 행은 spec과 같은 묶음 제목 아래에 두고, AC가 없는 이슈는 `## 완료의 정의` 섹션을 더한다. 대화에는 파일 경로와 추가할 AC 목록만 제시하고 전문을 출력하지 않는다. 수정 요청을 받으면 같은 파일을 갱신하고, AC 문장이 바뀌면 spec도 같은 문장으로 맞춘다.
     - 기준 본문의 AC가 3-2에서 옮긴 AC와 다르면 초안을 쓰기 전에 변경 통제에 따라 spec을 먼저 맞춘다. 번호가 겹치면 이슈 본문의 번호를 두고, spec이 직접 쓴 AC에 다음 번호를 주며 plan `테스트 계획`의 AC 칸도 고친다.
   - **실행**: 사용자가 승인할 때만 실행한다. 실행 직전에 같은 조회 명령으로 본문을 임시 파일에 다시 받아 기준 본문 파일과 `cmp -s`로 비교하고, 같을 때만 본문을 바꾼다. 기준 본문과 다르면 실행하지 않고, 바뀐 본문으로 기준 본문과 초안을 다시 만들어 다시 묻는다. 조회가 실패해도 실행하지 않는다. 본문 편집이 성공했을 때만(아래 블록은 종료 코드 0) 기록 단계로 넘어간다. `gh issue edit`가 실패하면 기록하지 않고 오류를 보고한 뒤 다시 시도할지 묻는다.

     ```bash
     # 분기마다 결과를 rc에 받아 두고, 임시 파일을 지운 뒤 블록 종료 코드로 돌려준다.
     now=$(mktemp)
     if ! gh issue view '<앞자리 0 제거한 이슈 번호>' --repo '<대상 저장소>' --json body -q .body > "$now"; then
       echo '조회 실패: 실행하지 않음'; rc=1
     elif ! cmp -s "$now" '.ai/99_workspace/issue-<번호>-body-base.md'; then
       echo '기준 본문과 다름: 실행하지 않음'; rc=1
     else
       gh issue edit --repo '<대상 저장소>' '<앞자리 0 제거한 이슈 번호>' --body-file '.ai/99_workspace/issue-<번호>-body.md'
       rc=$?
     fi
     rm -f "$now"
     (exit "$rc")
     ```

   - **기록**: 갱신하면 summary `이슈 본문 갱신` 줄에 `갱신 · <AC 번호>`를, 거절하면 `거절 · <AC 번호>`를 적고, 5단계의 `5단계 뒤의 변경`을 확인한 뒤 Task 0으로 진행한다. AC 번호는 spec이 직접 쓴 AC의 번호다. 거절하면 이슈 본문을 바꾸지 않고 spec의 AC가 기준이 된다. 어느 쪽이든 spec의 AC 행은 그대로 둔다.

> 게이트 2건(계획 종료·구현 시작)은 **문서를 쓴 주체와 읽는 주체가 다를 수 있다**는 것만 전제한다. 모델을 나눠 쓰든 한 모델로 진행하든, 세션이 바뀌면 전제는 똑같이 유실되므로 동일하게 수행한다.

| 파일명                       | 참조 템플릿                      | 역할                        | 생명주기                                                          |
|------------------------------|----------------------------------|-----------------------------|-------------------------------------------------------------------|
| `active/issue-workflow.md`   | `issue-workflow-template.md`     | 작업 절차 가이드             | 고정 — 최초 1회 생성, 이슈와 무관하게 유지                          |
| `issue-<번호>-spec.md`      | `issue-spec-template.md`         | 목표, 요구사항, 완료의 정의, 결정 사항, 변경 이력, 연관 문서 | 안정 — 작성 후 거의 변경 없음. 승인 뒤의 변경은 `변경 이력`에 기록 |
| `issue-<번호>-plan.md`      | `issue-plan-template.md`         | 설계 결정, 테스트 계획, 실행 Task 목록 + 체크박스 | 가변 — Task 완료 시 체크, 실행 결과에 따라 Task 추가·수정·삭제 가능   |

## 진행 루프

이슈는 **계획 수립 → 계획 검증 → 구현 → 구현 검증 → 완료 확인**의 다섯 단계를 이 순서로 지난다. 계획 수립에서 완료 확인까지 한 번 지나는 것이 한 회차다.

- **돌아가는 길**: 완료 확인에서 사용자가 `다음 회차`로 정하면 계획 수립으로 돌아간다. `마무리`로 정하면 루프를 나가 Task N(마무리)에 들어간다.
- **건너뛰는 검증**: 계획 검증과 구현 검증은 지난 검증 뒤에 바뀐 것이 없으면 건너뛰고 다음 단계로 간다.
- **회차 기록**: 회차를 시작할 때 summary `루프 기록`에 한 행을 더하고 단계를 지날 때마다 그 행을 채운다. 칸의 뜻은 summary 템플릿을 따른다.
- **감사 전 커밋**: 감사를 받기 전에 감사 대상(계획 감사는 spec·plan, 교차 감사는 구현과 spec·plan)에 미커밋 변경이 있으면 커밋할지 사용자에게 묻는다. 커밋하지 않고 받으면 검증 커밋 칸에 `(미커밋 포함)`이 남아, 커밋한 대상으로 다시 받을 때까지 바뀐 것으로 본다는 사실을 함께 알린다.
- **검증 기록**: 감사를 받으면 그 회차 행의 `계획 검증 커밋`이나 `구현 검증 커밋` 칸에 감사 대상 커밋을, `검증 결과` 칸에 감사 종류와 리포트 머리말의 감사 회차(`계획 2차`, `최종 1차`)를 적는다. 한 회차에 같은 감사를 여러 번 받으면 커밋 칸에는 마지막 감사의 대상 커밋을 둔다. 감사 대상 커밋은 리포트 머리말의 `감사 대상 커밋` 줄에서 옮기고 리포트를 받은 시점의 HEAD로 대신하지 않는다. 그 줄에 미커밋 산출물이 적혀 있으면 커밋 뒤에 `(미커밋 포함)`을 붙인다.

### 계획 수립

spec·plan이 없으면 쓰고, 지난 회차에서 바꿀 것이 나왔으면 고친다. 절차는 "새 이슈 시작 시" 1~4단계와 그 절 첫머리의 뒤 회차 규칙을 따른다.

- **발견을 고치는 Task**: `--response`에서 반영으로 정한 발견을 plan에 Task로 더한다. 더한 Task의 번호를 summary `종류별 발견`의 `고친 Task` 칸에 적는다.
- **같은 종류의 발견**: summary `종류별 발견`에서 같은 종류가 지난 두 회차에 이어서 나왔으면(종류가 같고 회차 번호가 지난 회차와 그 앞 회차인 두 행), Task를 더하기 전에 plan `설계 결정`부터 고친다. 섹션이 없으면 이때 만든다.

### 계획 검증

계획 감사를 받을지와 다시 받는 조건은 "새 이슈 시작 시" 5단계를 따른다. 조건에 맞지 않으면 구현으로 간다.

### 구현

Task 0을 마친 뒤 plan의 일반 Task를 차례로 진행한다.

- **테스트 먼저**: 기능을 바꾸는 Task는 테스트 작성 → 실패 확인 → 테스트 커밋 → 구현 → 통과 확인 → 구현 커밋 순서로 진행한다. 감사 발견을 고치는 Task는 재현 테스트를 먼저 쓴다. 테스트 커밋과 그 커밋에서 실패한 테스트 수를 summary Task 블록의 `테스트`에 적는다.
- **테스트를 먼저 쓰지 않는 Task**: 동작을 바꾸지 않는 Task다. 구현 → 통과 확인 두 단계로 진행하고, 통과 확인은 기존 테스트 전체 통과다. 러너도 결정적 명령도 없는 repo만 통과 확인을 건너뛴다. plan Task의 `테스트 먼저` 필드에 먼저 쓰지 않는 이유를 한 줄 적는다. 기준은 아래 넷이 전부다.
  - 문서만 고치는 Task
  - 자동 테스트가 보지 못하는 화면 배치
  - 버릴 코드를 쓰는 스파이크
  - 기존 테스트가 그대로 통과해야 하는 리팩터링

### 구현 검증

- **감사 실행**: 지난 검증 뒤에 구현이 바뀌었으면 사용자가 구현 모델과 **다른 벤더 모델**(최소 동급 이상 역량)로 `issue-audit`를 직접 실행해 교차 감사를 전체로 다시 받는다. 고친 발견의 위험도에 따른 예외는 없다. 구현 AI는 감사를 실행하지 않는다. 감사의 방향은 허점 탐색(스펙 위반·누락·소스코드와의 모순)이다.
- **바뀌었는지의 판별**: summary `루프 기록`에서 `구현 검증 커밋` 칸에 값이 있는 가장 최근 행의 커밋 뒤 diff로 한다. 값이 있는 행이 없으면 받는다. 그 칸에 `(미커밋 포함)`이 있으면 diff로 가리지 않고 바뀐 것으로 본다. diff는 그 커밋과 지금 작업 트리의 차이이며, 저장소 최상위에서 실행한 `git diff --name-only --no-renames <커밋>`과 `git ls-files --others --exclude-standard`의 출력을 합친 파일이다. 커밋하지 않은 변경, 지운 파일, Git이 무시하지 않는 미추적 파일이 모두 들어간다. diff에 아래 넷에 들지 않는 변경이 하나라도 있으면 바뀐 것이고, 세지 않는 변경은 이 넷이 전부다. 교차 감사가 읽는 구현과 spec·plan이 바뀌면 지난 판정을 그대로 쓸 수 없기 때문이다. 문서만 고친 회차도 넷에 들지 않는 변경이 있으면 다시 받는다.
  - 이슈 작업 기록: `.ai/90_issues/`, `.ai/99_workspace/`, `.ai/70_ledger/` 아래 파일의 변경이다. 이 이슈의 spec·plan과 plan 일반 Task가 고친다고 적은 파일은 여기에 들지 않는다. 원장 항목처럼 이 경로의 파일이 AC의 산출물인 이슈가 있기 때문이다.
  - 마무리 문서: plan Task N이 마무리로 적은 문서의 변경이다.
  - 체크박스: spec·plan에서 체크 표시만 바뀐 것이다.
  - `확인` 칸과 `[ND]` 줄: plan `테스트 계획`에서 `확인` 칸만 바뀐 것과 `[ND]` 줄의 변경이다.
- **모델 기록**: 사용자가 감사 모델("벤더, 모델명 (모델 ID)" 형식)과 effort(리포트의 `감사 effort` 줄 값, 확인 불가면 `-`)를 summary `모델 기록` 표의 `최종 audit 모델` 행에 적는다.
- **검토**: 리포트(`.ai/99_workspace/issue-<번호>-audit-report.md`)를 받으면 `--response`로 검토한다. 이 단계에서는 소스를 고치지 않는다.

### 완료 확인

아래 순서로 진행한다. 완료 확인은 건너뛰지 않는다.

- **확인 칸**: 마지막 교차 감사 리포트가 충족으로 판정한 AC의 `[D]`·`[QD]` 줄에 그 감사 회차를 적는다. 감사 회차는 감사 대상 커밋의 `테스트 계획`에 같은 내용으로 있던 줄에만 적고, 감사 뒤에 더하거나 `확인` 외 칸을 바꾼 줄은 비워 둔다.
  - 구현 검증을 다시 받은 회차에는 새 회차로 다시 적고, 새 리포트가 충족으로 판정하지 않은 AC의 줄은 비운다.
  - `확인`이 빈 `[ND]` 줄과 지난 확인 뒤에 구현이 바뀐 `[ND]` 줄은 사용자에게 보여 주고 확인받은 날짜를 적는다. 사용자가 확인하지 않은 줄은 비워 둔다.
- **보이는 값**: 아래 네 가지를 보인다. 앞의 세 값은 마지막 교차 감사 리포트에서 옮기며 새 판정 값을 만들지 않는다.
  - 1단계 상태
  - 2단계 상태
  - 종합 판정
  - 확인한 줄 수: plan `테스트 계획`의 두 표에서 `확인` 칸이 채워진 줄 수와 전체 줄 수다. `이관`을 적은 줄은 채워진 줄로 세지 않는다.
- **권장**: 아래 네 가지가 모두 맞으면 `마무리`, 그 밖은 `다음 회차`를 권장한다. 판정 불가(N/A)로 남은 AC는 권장과 함께 따로 보인다.
  - 1단계 상태: 충족(PASS)이다.
  - 2단계 상태: 통과(PASS)나 주의(WARN)다.
  - 확인한 줄 수: `테스트 계획`의 모든 줄을 확인했다.
  - 반영으로 정한 발견: 모두 닫았다. 고친 Task가 완료된 발견을 닫은 것으로 보고, 이관이나 보류로 정한 발견은 세지 않는다.
- **결정**: 루프를 나갈지는 사용자가 정하고, 정한 값(`마무리`나 `다음 회차`)을 summary `루프 기록`의 `결정` 칸에 적는다. 구현 AI는 권장만 낸다.
- **기준에 못 미친 마무리**: 권장 기준에 못 미친 채 `마무리`로 정하면 남은 AC와 발견마다 완화·원장 등재·새 이슈 가운데 결정을 받는다. 완화는 `## 작업 진행 중`의 변경 통제를 따른다.
  - **넘긴 AC**: 원장 등재나 새 이슈로 넘긴 AC는 spec에 그대로 두고, plan `테스트 계획`에서 그 AC의 줄마다 `확인` 칸에 `이관 K-<번호>`나 `이관 #<이슈 번호>`를 적는다. Task N 전체 회귀는 이 줄을 실행하지 않고, repo 전체 테스트와 나머지 `[D]` 줄은 그대로 전부 통과해야 한다. 그 AC를 위해 커밋한 테스트가 실패하면 그 테스트를 지우거나 건너뛰게 바꾸는 변경을 변경 통제의 완화로 함께 승인받는다. 승인하지 않으면 그 AC를 넘길 수 없다.
  - **완화한 AC**: 완화로 문장을 바꾼 AC는 마지막 교차 감사 리포트가 그 문장을 판정하지 않았으므로 PR의 완료의 정의 대조에서 `미검증`으로 보인다. git-pr이 리포트 행의 문장과 spec의 AC 문장을 견주기 때문이다.

### 마무리

완료 확인에서 사용자가 `마무리`로 정한 뒤에만 Task N에 들어간다. Task N은 전체 회귀, 색인, 충족 AC 체크, repo 고유 마무리, `--clear`, PR을 이 순서로 하고, 교차 감사를 받지 않는다. 작업 내용과 완료 기준은 plan 템플릿의 고정 블록을 따른다.

- **구현을 고칠 때**: Task N에서 구현을 고치면 계획 수립으로 돌아간다. summary `루프 기록`에 다음 회차의 행을 더하고, spec에서 체크한 AC의 체크를 지운다.
- **PR**: PR은 Task N에서 git-pr로 만든다. `--clear`가 이슈 디렉토리를 옮긴 뒤에 만든다.

### PR 뒤 피드백

PR에 달린 리뷰 피드백은 git-pr-feedback으로 처리한다. 처리 기록은 git-pr-feedback의 방식을 따른다.

- **교차 감사**: 피드백으로 구현을 고쳤을 때 교차 감사를 다시 받을지는 사용자가 고른다.
- **이슈 문서**: PR을 만든 뒤에는 이슈 문서를 고치지 않는다. 이슈 디렉토리가 이미 archive에 있기 때문이다.

## 작업 진행 중

- 계획 감사를 수행한 이슈는 그 리포트(`.ai/99_workspace/issue-<번호>-plan-audit-report.md`)를 `--response`로 검토하고 승인분을 spec·plan에 반영한다(질의·기록 규칙은 "새 이슈 시작 시" 5단계). 감사 수행 여부와 관계없이 summary `이슈 본문 갱신` 줄이 비어 있으면 "새 이슈 시작 시" 6단계를 먼저 수행한 뒤 Task 0에 착수한다. 세션이 바뀐 뒤 summary `다음 작업`만 보고 6단계를 건너뛰지 않기 위해서다.
- 구현 착수 전 **Task 0(구현 시작 게이트)**을 먼저 수행한다. spec/plan만으로는 알 수 없는 전제·모호점을 나열하고, 항목이 있으면 **코드를 쓰기 전에 사용자에게 질의**해 답변을 spec `## 결정 사항`이나 plan `## 설계 결정`에 적고, "새 이슈 시작 시" 5단계의 `5단계 뒤의 변경`을 확인한 뒤 구현을 시작한다(`--resume`의 "요약 보고 → 승인 시 진행"과 같은 방식). 항목이 없으면 summary Task 0에 `전제 누락 없음` 한 줄을 기록하고 진행한다.
- **변경 통제**: 3-2 작성과 작업 진행 중에 spec 요구사항·완료의 정의·결정 사항을 바꾸는 변경과 커밋한 테스트를 바꾸는 변경은 아래 셋으로 분류하고, 확장·완화만 사용자에게 질의한다. 분류 기준선은 이슈 본문의 AC다. 이슈 본문의 AC가 대응하지 않는 R은 3-1에서 승인받은 요구사항이 기준이고, 6단계를 마친 뒤에는 spec의 AC가 기준이다.
  - **구체화**: AC가 다루는 상황과 결과는 그대로 두고 판정 기준만 명확히 하는 변경이다. 질의 없이 반영한다. AC 문장은 바꾸지 않고 `결정 사항`이나 `테스트 계획`에 적는다. 예: AC "승인 없이 등록하지 않는다" → 결정 사항 "승인 거절 시 생성 호출 0회".
  - **확장**: AC에 없는 결과를 더하는 변경이다. 범위 확장(이슈 본문 갱신 + 재승인), 원장 등재(`--response` 5단계 원장 등재 형식), 새 이슈(`--create`) 중에서 고르게 질의하고, 고르기 전에는 spec에 반영하지 않는다. 범위 확장은 "새 이슈 시작 시" 6단계와 같은 파일·명령·승인 규칙(기준 본문 재조회 포함)으로 이슈 본문에 AC를 더하고, spec 요구사항이 바뀌면 3-1 승인 게이트를 다시 거친다.
  - **완화**: 오류 상황을 빼거나 성공 조건을 약하게 하거나 AC를 빼거나 제외로 옮기는 변경이다. 커밋한 테스트의 기대값을 바꾸거나 단언을 줄이거나 테스트를 지우는 변경도 완화다. 기대값이 처음부터 틀렸던 경우도 같다. 재승인 없이 반영하지 않는다. 재승인받아 AC를 고치거나 빼면 확장과 같은 파일·명령·승인 규칙으로 이슈 본문도 고친다.
  - **테스트 수정**: 결과는 그대로이고 이름·위치·준비 코드·호출 방식만 바뀌는 테스트 수정은 위 셋에 들지 않으며 질의 없이 반영한다.
  - **기록**: 승인 뒤에 바뀐 요구사항·AC·결정은 번호, 분류, 계기를 spec `변경 이력`에 적는다.
- Task 완료 시 `issue-<번호>-plan.md`의 해당 Task 체크박스를 체크한다.
- Task 완료 시 `issue-<번호>-summary.md`의 수행 결과를 갱신하고 다음 작업을 업데이트한다. Task 0 및 일반 실행 Task(Task N 제외) 블록의 지표 5종(`수행 모델`·`수행 effort`·`audit 발견`·`보정 반영`·`재시도`)은 값이 없어도 필드를 남긴다. 사후 집계(보정률 = `보정 반영` / `audit 발견`)가 표기 고정에 의존하기 때문이다. Task N 블록에는 지표를 두지 않는다(근거는 summary 템플릿의 Task N 블록 주석). 일반 Task 블록에는 `테스트`와 `대응 발견`도 적으며 두 필드는 집계하지 않는다.
  집계와 표기 검사는 헬퍼로 한다. 헬퍼의 검사 대상은 수치 3종(`audit 발견`·`보정 반영`·`재시도`)뿐이며, 이 세 필드의 표기가 깨졌으면(`-`·비수치·필드 누락·Task N 블록의 지표) 종료 코드 1과 함께 사유가 나온다. `수행 모델`·`수행 effort`는 검사하지 않는다.

  ```bash
  # <skill 디렉토리>는 이 SKILL.md가 있는 디렉토리. 실행 시 실제 경로로 바꿔 쓴다.
  metrics='<skill 디렉토리>/scripts/summarize-metrics.sh'

  "$metrics" '.ai/90_issues/active/issue-<번호>/issue-<번호>-summary.md'
  ```

  `수행 effort`는 아래 규칙으로 적는다. 값 형식(도구가 기록한 표기 그대로, 한 Task 안에서 바꿨을 때의 ` / ` 나열과 `수행 모델`과의 위치 대응)은 summary 템플릿 주석을 따른다.
  - **구현 AI가 채운다**: 자기 세션의 모델·effort를 아래 위치에서 읽어 Task 블록의 `수행 모델`·`수행 effort`와 표의 `구현 모델` 행에 적는다. 계획 모델 행도 계획을 쓴 AI가 같은 방식으로 채운다.
  - **실행 기록 우선**: 설정 파일 값은 모델별 재정의나 세션 중 변경 때문에 실제 적용값과 다를 수 있어 보조로만 쓴다.
    - Claude Code 실행 기록: `~/.claude/projects/<repo 디렉토리>/<세션 ID>.jsonl`의 assistant 항목 `model`·`effort`, 또는 셸 환경변수 `CLAUDE_EFFORT`
    - Codex 실행 기록: `~/.codex/sessions/<년>/<월>/<일>/rollout-*.jsonl`의 `turn_context` 레코드 `payload.model`·`payload.effort`
    - 설정 파일(보조): Claude Code `~/.claude/settings.json`의 `effortLevel`·`modelSettings.<모델>.effortLevel`, Codex `~/.codex/config.toml`의 `model_reasoning_effort`
  - **모델 ID 읽기**: 모델 ID는 effort와 같은 레코드에서 읽는다. Claude Code는 assistant 항목의 `model`, Codex는 `turn_context` 레코드의 `payload.model`이며, 그 값을 `수행 모델`과 표 모델 열의 괄호 안에 적는다.
  - **컨텍스트 접미어 제거**: 모델 ID에 컨텍스트 접미어(`[1m]` 등)가 붙어 있으면 `[`부터 끝까지 ID에서 제거한다(`<모델 ID>[1m]` → `<모델 ID>`). 접미어는 API 모델 ID가 아니다. 실행 기록의 모델 값에는 붙지 않고, 시스템 프롬프트·설정값처럼 다른 출처의 모델 ID에 붙는다.
  - **로컬 기록이 없는 도구**(ChatGPT 웹·앱 등): 화면에서 고른 값을 사람이 적는다. 화면에서 모델 ID를 확인할 수 없으면 `(-)`로 적는다.
  - **audit 모델의 effort**(표의 `계획 audit 모델`·`최종 audit 모델` 행): 사용자가 감사 리포트의 `감사 effort` 줄 값을 옮겨 적는다.
  - **확인할 수 없으면 `-`**: 위 헬퍼는 수치 3종만 검사하므로 `수행 effort`의 `-`는 위반이 아니다. 모델 ID는 괄호를 남겨 `(-)`로 적는다.

  도구 이름과 경로는 값을 읽는 위치 안내이며 특정 도구·벤더를 절차 조건으로 두지 않는다. 도구 버전에 따라 키 이름·경로가 바뀔 수 있다. effort는 벤더끼리 비교하지 않으며, effort와 모델 ID는 게이트 조건에도 쓰지 않는다.
- 완료 기준은 가능한 한 결정적 검증 단계(명령·테스트·스크립트)로 내린다. 검증 레벨(`[D]`/`[QD]`/`[ND]`)과 기록 형식은 plan 템플릿의 `테스트 계획`을 따르고, 완료의 정의와 완료 기준의 배치는 `## 산출물 접기 기준`의 "완료 기준 형식"을 따른다.
- 계획의 마지막 Task는 마무리(Task N)로 고정한다. 교차 감사는 Task N 앞의 구현 검증 단계에서 **사용자가 직접** 받는다(상세는 `## 진행 루프`의 구현 검증·마무리).
- audit 리포트(`.ai/99_workspace/issue-<번호>-audit-report.md`)를 받으면 `--response` 옵션으로 검토한다. 발견사항에 **피드백 먼저, 항목별 결정 다음**이며, 구현 AI가 리포트를 받자마자 자동 보정하지 않는다. 반영으로 정한 발견은 다음 회차에서 고친다(상세는 `## 옵션`의 `--response`).

## 이슈 완료 시

1. `issue-<번호>-plan.md`의 계획 종료 게이트 `점검 완료`, Task 0, 일반 Task의 체크박스가 체크되었는지 확인한다 (게이트 체크박스는 `## Tasks` 밖에 있어 Task 체크박스만 세면 누락된다). Task N의 미체크는 미완료로 세지 않는다. 루프 기록의 결정 확인은 `--clear` 1단계와 같다.
   - 단, **사용자가 직접 받은 교차 감사의 결과와 최종 audit 모델("벤더, 모델명 (모델 ID)")이 summary `모델 기록` 표의 `최종 audit 모델` 행에 기록된 경우에만 완료로 간주**한다. 같은 행의 effort는 완료 조건이 아니라 `-`여도 완료를 막지 않는다. 구현 AI는 이 기록을 **대신 채우지 않는다.**
2. `issue-<번호>-summary.md` 상단의 다음 작업을 `✅ 모든 작업이 완료되었습니다.`로 업데이트한다.
3. `issue-<번호>/` 디렉토리를 `active/`에서 `archive/`로 디렉토리 단위로 이동한다. 이관 직전의 Task N 기록은 `--clear` 4단계와 같다.
   이 이동은 **PR 머지 전, 작업 브랜치에서 수행해 같은 PR에 포함**한다 (머지 후 실행하면 `main` 직접 푸시가 된다).
   - **원장 해소 기재**: spec 요구사항에 `(함께 해소: K-<번호>)`로 표기한 원장 항목 가운데 이번 작업으로 원인이 사라진 항목을 종결한다. `해소(PR #N)`은 PR 번호를 알 때만 확정한다.
     - **PR이 이미 있으면**: 항목 `상태`를 `해소(PR #N)`으로 바꾸고 `.ai/70_ledger/active/`에서 `.ai/70_ledger/archive/`로 옮긴 뒤 `.ai/70_ledger/index.md` 항목 목록을 갱신해, 머지 전 같은 PR에 포함한다. PR 유무는 대상 저장소를 고정해 확인한다. 작업 브랜치의 원격(`git config branch.<작업 브랜치>.remote`) URL을 `[호스트/]소유자/저장소`로 읽어 대상 저장소로 확정하고 `gh pr list --repo '<확정한 대상 저장소>' --head '<작업 브랜치>' --state open --json number`로 조회한다. `--repo`를 생략하면 `GH_REPO` 환경변수나 로컬 `gh` 컨텍스트가 저장소를 골라, head 이름이 같은 다른 저장소의 PR 번호를 해소 근거로 적을 수 있다. 대상 저장소를 확정하지 못했거나 조회가 실패했거나 PR이 2개 이상이면 번호를 고르지 않고 아래 "PR이 아직 없으면" 경로로 처리한다.
     - **PR이 아직 없으면**: 해소를 확정하지 않고 항목을 `active/`에 그대로 둔다. PR 유무를 확인할 수 없을 때도 이 경로로 처리한다. git-pr 문서 동기화 점검의 원장 대조가 diff의 원인 파일 변경으로 종결을 권고하고, 승인되면 git-pr 4단계 "원장 해소 기재"가 생성된 PR 번호를 적는다. 사용자에게 이 후속 처리를 안내한다.
     - **들어오는 링크 갱신**: 원장 항목을 `archive/`로 옮겼으면 `.ai/` 아래 문서(`.ai/90_issues/archive/` 제외)에서 그 항목을 가리키는 링크를 새 경로로 고친다. 대상은 `70_ledger/active/K-<번호>-` 경로 링크와 원장 항목 파일끼리의 같은 디렉토리 링크이며, 옮긴 항목 안에서 `active/`에 남은 항목을 가리키는 링크도 고친다. 상대 경로 깊이는 링크가 있는 문서 위치에서 다시 계산한다. 고친 뒤 `check-ledger-links.sh`로 끊긴 원장 링크가 0건인지 확인한다.

       ```bash
       # <skill 디렉토리>는 이 SKILL.md가 있는 디렉토리. 실행 시 실제 경로로 바꿔 쓴다.
       ledger_links='<skill 디렉토리>/scripts/check-ledger-links.sh'

       "$ledger_links" '.ai'
       ```

       끊긴 원장 링크가 0건이면 무출력·종료 코드 0이고, 1건 이상이면 `<파일>:<줄>: <대상>`을 1행씩 출력하고 종료 코드 1이다. 이번 이동으로 끊긴 링크는 고치고, 이동과 무관하게 이미 끊겨 있던 링크는 목록으로 알려 고칠지 묻는다.
   - **보류 항목 원장 등재 질의**: spec `제외` 목록에서 사유가 `보류`인 항목을 보여 주고 원장 등재 여부를 묻는다. 권고까지만 하며 승인한 항목만 등재한다. 원장 index가 없거나 `보류` 항목이 없으면 건너뛴다.
     - **등재 형식**: `--response` 5단계의 원장 등재와 같다. `.ai/70_ledger/ledger-entry-template.md` 형식으로 `.ai/70_ledger/active/K-<번호>-<slug>.md`를 신설하고 `.ai/70_ledger/index.md` 항목 목록을 갱신한다. `출처`는 `이슈 #N`이고 **수용 사유**와 **재검토 조건**은 필수다. spec 제외 줄에 적은 보류 이유와 재검토 조건 예시를 초안의 출발점으로 쓴다.
     - **중복 판정**: 보류 항목 하나씩 판정한다. 이슈 번호(`출처`의 `이슈 #N`)는 `.ai/70_ledger/active/`·`archive/`를 검색하는 범위로만 쓰고, 검색한 원장 항목 가운데 그 보류 항목과 같은 대상(제목·내용)을 기록한 항목이 있을 때 그 보류 항목만 건너뛴다. 예를 들어 보류 A만 등재된 상태면 B는 질의하고, A·B가 모두 등재됐으면 둘 다 건너뛴다. 이슈 번호만으로 판정하면 하나만 등재된 이슈의 나머지 보류 항목이 질의에서 빠진다.
     - 이 등재는 PR 번호가 필요 없어 위 해소 기재의 시점 규칙을 받지 않는다.
4. 이동한 파일 본문의 **경로 참조 갱신**을 수행하고 잔존 참조 0건을 확인한다 (갱신 규칙·검증 스니펫은 `--clear` 6단계와 동일).

> 위 절차에 더해 `99_workspace` 정리와 이슈 댓글 요약 등록까지 한 번에 수행하려면 `--clear` 옵션을 사용한다.

## 산출물 접기 기준

산출물의 상세 내용은 `<details>` 접기로 분량을 줄이되, 아래 기준을 따릅니다.

- **접기 가능**: 근거·대안 비교·상세 절차·코드 예시·참고자료
- **접기 금지**: 결정사항·리스크·액션 아이템

`.ai/10_rules/writing-principles.md`가 있으면 그 원칙을 따르고, repo 고유 확장 `writing-principles-local.md`와 충돌하면 local이 우선합니다. 이 블록은 파일이 없을 때의 기본값입니다.

### 완료 기준 형식

완료의 정의에는 판정할 결과를, plan에는 판정하는 방법을 적습니다. 완료의 정의를 사람이 한 문장씩 읽을 수 있게 하는 것이 목적입니다.

- **완료의 정의**: spec에는 `- [ ] AC<n>: <이슈 본문과 같은 문장> (R<n>)` 행만 둡니다. 완료 항목은 결정사항이라 접지 않습니다.
- **테스트 관점**: spec 완료의 정의는 관찰할 수 있는 결과만 적고 검증 명령과 케이스 목록을 적지 않습니다. plan `## 테스트 계획`이 AC마다 층과 테스트, 검증 레벨, 강등 사유를 잇고, 케이스는 그 기능을 만드는 plan Task의 테스트 코드가 맡습니다.
- **고정 Task의 완료 기준**: Task 0·Task N의 완료 기준은 본문(접기 금지)에 레벨 태그 + 무엇이 보장되는지 한 문장, 필요하면 강등 사유를 두고, 검증 명령·기대 출력·명령 설계 주의점은 접기에 둡니다. 접기 제목에 기대 출력을 함께 적습니다 (기본형: `검증 명령 — 출력 0건이면 통과`).
- **접지 않는 경우**: 접을 상세가 없어 판정 주체만 적는 완료 기준(주로 `[QD]`·`[ND]`)은 본문 한 줄로 둡니다.
- **의존 관계**: 다른 게이트의 선행 조건이 되는 완료 기준은 선행 사실과 **선행 조건이 무너졌을 때의 결과**(그대로 통과·공집합 우회 등)를 함께 본문 문장에 남기고, 그렇게 되는 메커니즘만 접기에 둡니다. 우회 가능성 경고는 리스크라 접기 금지에 해당하며, 선행 사실만 적고 결과를 접으면 접기를 열지 않는 독자가 위험을 놓칩니다.

접기 안의 명령은 코드 블록으로 감싸 복사·재실행이 쉽게 유지합니다.
문서 구조를 앵커로 판정하는 검증 명령(`^### Task `, `^- \*\*…\*\*:`)이 있으므로, 접기는 앵커 행 아래에 들여쓰기로 붙여 앵커 자체를 깨지 않게 배치합니다.
구체 형태는 이 skill 디렉토리의 `templates/issue-spec-template.md`·`templates/issue-plan-template.md`의 예시를 따릅니다.

## 옵션

### `--create`

대화에서 정한 작업을 GitHub 이슈로 등록하고, 이어서 이슈 작업을 시작할지 묻는다.

- **용도**: 작업 내용을 대화에서 정한 뒤 이슈로 남길 때 사용한다. 초안을 이슈 본문 템플릿 구조로 쓰므로 등록 때부터 완료의 정의(AC)가 있는 이슈가 된다.
- **경계**: 이 옵션은 이슈 등록까지만 한다. 이슈 작업 시작(기존 이슈 디렉토리 이관, 이슈 디렉토리 생성)은 시작 질의를 승인한 뒤 "새 이슈 시작 시"가 맡으며, 그 전까지 active 작업 파일을 옮기거나 지우지 않는다.
- **동작**:
  1. **초안 작성**: 대화에서 정한 내용을 이 skill 디렉토리의 `templates/issue-body-template.md` 구조로 `.ai/99_workspace/issue-create-body.md`에 1회 쓴다. 디렉토리가 없으면 만들고, 파일이 이미 있으면 덮어쓸지 묻는다. 제목은 초안 파일을 하나로 두기 위해 파일에 넣지 않고 따로 정한다.
  2. **요약 제시**: 파일 경로, 제목 전문, 목표 한 줄, 포함·제외 목록, 완료의 정의의 묶음별 항목 수, 정한 것, 검토 필요를 제시하고 초안 **전문은 대화에 출력하지 않는다**. 승인 대상은 파일이고, 같은 텍스트를 대화에 다시 만들면 응답만 늦어진다.
     - **목록 제시**: 포함·제외 목록은 초안의 묶음대로 나눠 보여 주고, 항목은 한 문장 그대로 보여 준다. 완료의 정의는 포함과 같은 묶음 제목마다 AC 수를 적는다.
     - **분할 권고**: 초안 범위 안에 서로 독립으로 머지할 수 있는 항목이 있으면 이슈 분할을 권고한다. 수치 기준은 두지 않고 권고까지만 하며, 결정은 사용자가 한다.
     - **AC 대응 점검**: 템플릿의 대응 기준(포함 항목 하나가 AC 하나 이상의 결과로 판정되면 그 항목에 대응한 것으로 본다)으로 포함 항목과 AC를 맞춰 보고, AC가 대응하지 않는 포함 항목을 보고한다. 보고할 항목이 없으면 `없음`을 적는다. AC를 더할지는 사용자가 정한다.
  3. **승인**: 승인 대상은 제목, 초안 파일, 대상 저장소다. 승인 전에는 `gh issue create`를 실행하지 않는다.
     - **대상 저장소**: 현재 브랜치 upstream 원격 URL에서 `[호스트/]소유자/저장소`를 정해 제시한다. upstream이 없으면 `git config branch.<브랜치>.remote`의 원격을 쓰고, 원격이 없거나 여럿이라 정할 수 없으면 사용자에게 묻는다. 저장소를 정하지 못하면 등록하지 않는다.
     - 수정 요청을 받으면 같은 파일을 갱신하고 2단계 요약 제시부터 다시 한다. 회차마다 새 파일을 만들지 않는다.
     - 거절하면 초안 파일을 남기고 그 경로를 안내한 뒤 끝낸다.
  4. **등록**: 승인한 제목·초안 파일·대상 저장소를 그대로 써서 아래 명령으로 등록한다.

     ```bash
     gh issue create --repo '<대상 저장소>' --title '<제목>' --body-file '.ai/99_workspace/issue-create-body.md'
     ```

     - 대상 저장소와 제목은 작은따옴표로 감싸고, 값 속 작은따옴표는 그 자리만 `'\''`로 바꾼다. 작은따옴표 안에서는 `$`·백틱이 해석되지 않는다.
     - `gh`가 없거나 인증되지 않았으면 GitHub MCP의 이슈 생성 도구로 폴백하고, `owner`·`repo`(승인한 대상 저장소)와 제목·본문(승인한 제목·초안 파일 내용)을 모두 승인값으로 넘긴다. MCP 도구는 호스트를 받지 않으므로 대상 저장소가 `github.com`일 때만 폴백한다. 다른 호스트면 폴백하지 않고 그 사실을 알린 뒤 초안 파일 경로를 안내하고 끝낸다.
     - 등록이 실패하면 다시 시도하지 않고 오류를 보고하며, 초안 파일은 남긴다.
  5. **번호 보고**: 만든 이슈의 번호와 URL을 보고한다.
  6. **시작 질의**: 만든 이슈로 "새 이슈 시작 시"를 진행할지 묻고, 승인하면 그 절차 1단계부터 진행한다. `active/`에 진행 중인 이슈 디렉토리가 있으면 1단계가 그것을 `archive/`로 옮긴다는 사실을 질의에 함께 적는다. 거절하면 등록에서 끝낸다.

### `--workflow-only`

`active/issue-workflow.md`만 생성한다. 이슈 파일은 생성하지 않는다.

- **용도**: 컨텍스트 초기화 후, 또는 가이드 파일이 유실·손상됐을 때 이슈 작업과 무관하게 작업 절차만 복구하고 싶을 때 사용한다.
- **동작**: `active/issue-workflow.md`를 내용 비교 없이 **무조건** 템플릿으로 덮어쓴다(강제 복구). 내용이 다를 때만 갱신하는 "새 이슈 시작 시" 흐름과 달리, 손상된 파일까지 강제로 되살린다.

### `--resume`

중단된 이슈 작업의 컨텍스트를 복구하고 사용자에게 진행 여부를 확인한다.

- **용도**: 세션 종료, 컨텍스트 초기화 등으로 작업이 중단된 후 재개할 때 사용한다.
- **동작**:
  1. `.ai/90_issues/active/` 하위의 모든 파일을 읽는다 (디렉토리 포함 재귀 탐색).
  2. `.ai/99_workspace/` 하위의 모든 파일을 읽는다 (이슈 작업 중 생성한 임시 파일 포함).
  3. 읽은 내용을 기반으로 현재 진행 상황을 사용자에게 요약 보고한다. summary `루프 기록` 마지막 행으로 지금의 회차와 단계를 함께 알린다.
  4. 다음 작업을 이어서 진행할지 사용자에게 확인한 후, 승인 시에만 작업을 진행한다.

### `--response`

교차모델 `issue-audit`이 만든 감사 리포트를 검토하고, **피드백 먼저 → 항목별 승인 → 승인분만 반영**하는 게이트를 절차로 고정한다. 최종 감사 리포트에서는 결정만 받고, 고치는 일은 다음 회차가 맡는다.

- **용도**: 구현 검증 단계의 교차 감사 리포트(`.ai/99_workspace/issue-<번호>-audit-report.md`)를 받았을 때, 구현 AI가 리포트를 받자마자 자동 보정으로 넘어가지 않도록 "피드백 먼저, 실행은 승인 후"를 표준화한다. 자연어 지시로만 유지되던 흐름을 옵션으로 고정해 신규 세션·다른 모델에서도 재현되게 한다.
  계획 감사 리포트(`.ai/99_workspace/issue-<번호>-plan-audit-report.md`)도 같은 게이트로 검토한다. 이때 보정 대상은 spec·plan이다.
- **경계**: audit **수행**(= 사용자가 타벤더 모델로 `issue-audit` 실행)과 audit 리포트 **검토·피드백·결정**(= 이 옵션)을 구분한다. 이 옵션은 audit을 **실행하지 않으며**, 승인 없이 **자동 보정하지 않는다**.
- **동작**:
  1. **리포트 확보**: 인자가 있으면 그 경로를 읽고, 생략하면 `active/` 이슈 번호로 최종 감사 리포트 `.ai/99_workspace/issue-<번호>-audit-report.md`와 계획 감사 리포트 `.ai/99_workspace/issue-<번호>-plan-audit-report.md`를 자동 탐색한다. 두 종류가 다 있거나 회차 리포트가 여러 개면 목록을 제시해 선택받는다. 리포트가 없으면 그 사실을 알리고 중단한다. 선택한 리포트가 계획 감사 리포트면 보정 대상은 spec·plan이다(5단계).
  2. **피드백만 제시**: 발견사항별로 동의 / 부분동의 / 반론, 위험도 재산출, 보정 시 **영향 파일 목록**을 제시한다. 위험도는 등급을 직접 바꾸지 않고 **영향·발생확률 축의 근거를 검토해 매트릭스로 다시 산출**하며, 축 판정을 바꿀 때는 변경 근거를 함께 적는다. 등급을 직접 고칠 수 있으면 `issue-audit`이 매트릭스로 걷어낸 재량이 이 단계에서 되살아난다. 이때 audit 리포트의 단계 구분을 그대로 살려 **1단계 발견**(적합성 검증: 완료의 정의(AC)·결정 사항 대조. 계획 감사 리포트에서는 GitHub 이슈 본문 요구 항목 대비 spec 요구사항 대조와 완료의 정의 대조)과 **2단계 발견**(비판적 검증)으로 나눠 제시한다. 같은 결함이 1단계 부분 충족(PARTIAL) 근거이자 2단계 발견으로 함께 올라오면 한 항목으로 병합해 1단계 발견으로 취급하고 집계도 1건으로 센다. **이 단계에서는 파일을 수정하지 않는다.**
  3. **처리 방향 표**: 보정 대상과 처리 방향(반영 / 이관 / 보류)을 표로 정리해 보여준다. 2단계 발견의 처리 방향 열은 아래 **등급별 기본 제시값**에서 끌어와 채운다. 등급이 처리 방향을 정하므로 낮음(LOW)·정보(INFO)가 매번 보정 대상으로 올라오지 않는다. **이관의 목적지는 원장 `.ai/70_ledger/`로 고정한다**. "별도 이슈로 이관"이 기본값이 아니라 원장 등재가 기본값이며, 이슈 승격은 등재한 항목의 `상태`를 `승격(이슈 #N)`으로 바꾸는 후속 단계다. **1단계 발견을 표 상단에 배치**하고 2단계 발견을 그 아래에 둔다. 처리 방향이 정해지지 않은 1단계 미충족(FAIL)·부분 충족(PARTIAL) 항목이 있으면 **미해소 건수를 표 아래에 명시**한다.
     - **종류**: 최종 감사 리포트의 처리 방향 표에는 발견의 `종류` 칸을 둔다. 종류는 발견의 원인을 짧게 부르는 이름이고, summary `종류별 발견`에 같은 원인이 있으면 이미 있는 이름을 그대로 쓴다. 사용자는 승인 질의에서 이름을 고칠 수 있다.
  4. **항목별 승인 질의**: 사용자에게 **항목 단위로** 실행 여부를 확인받는다. **순서 게이트**를 적용해 1단계 미충족(FAIL)·부분 충족(PARTIAL) 항목의 처리 방향을 먼저 전부 확정받고, 미해소가 0건이 되기 전에는 2단계 항목의 승인 질의로 넘어가지 않는다. 충족(PASS)·판정 불가(N/A)는 확정할 처리 방향이 없어 게이트를 막지 않는다. 예외는 사용자가 명시적으로 지시한 경우에만 열며, 구현 AI는 위험도를 근거로 스스로 순서를 바꾸지 않는다.
     - **기본 제시값의 성격**: 등급에서 끌어온 처리 방향은 질의의 출발점일 뿐 결론이 아니다. 사용자는 항목별로 뒤집을 수 있다. 다만 낮음(LOW)은 사용자가 명시적으로 승격하지 않는 한 보정 루프에 넣지 않는다. 구현 AI가 스스로 등급을 올려 승격시키지 않는다. 등급이 처리를 정하는 구조가 무너지면 사소한 지적이 다시 재검증 루프로 들어온다.
  5. **승인분만 반영**: 승인된 항목만 반영으로 정하고, 미승인 항목은 보류하거나 원장으로 이관한다. 최종 감사 리포트에서는 결정만 받고 소스를 고치지 않는다. 같은 순서 게이트를 적용해 1단계 미충족(FAIL)·부분 충족(PARTIAL) 항목의 처리 방향이 모두 확정된 뒤에 2단계 승인분을 정한다.
     - **최종 감사 리포트의 반영**: 반영으로 정한 발견은 다음 회차의 계획 수립에서 plan에 Task로 더하고 구현 단계에서 고친다. 아래 기등재 처리 가운데 해소는 고친 Task를 마친 뒤에 적는다.
     - **종류 기록**: 최종 감사 리포트의 발견을 종류별로 묶어 summary `종류별 발견`에 적는다. `회차` 칸은 루프 회차 번호다. 반영으로 정한 발견의 `고친 Task` 칸은 다음 회차에 Task를 더할 때 채우고, 이관·보류로 정한 발견은 이때 `이관 K-<번호>`나 `보류`를 적는다.
     - **지표**: 발견이 나온 Task 블록의 `audit 발견`에 건수를 적는다. **실제로 보정한 건수**는 고친 Task를 마칠 때 발견이 나온 Task 블록의 `보정 반영`에 적고, 고친 Task의 `대응 발견`에는 발견 번호를 적는다. 미승인·보류·이관 항목은 `보정 반영`에 세지 않으므로, 루프를 마친 뒤 두 값의 차이가 승인 게이트에서 걸러진 양이 된다.
     - **계획 감사 리포트의 보정**: 보정 대상이 spec·plan이면 2단계의 영향 파일 목록에 `issue-<번호>-spec.md`·`issue-<번호>-plan.md`를 적고 승인분만 그 두 파일에 반영한다. 발견·보정 건수는 Task 블록의 `audit 발견`·`보정 반영`에 세지 않고, summary `모델 기록` 표 아래 `계획 감사` 줄에 `수행 · 발견 N건 · 보정 N건`으로 적는다. Task 블록 지표는 구현 Task 축이라 계획 감사 건수가 섞이면 `summarize-metrics.sh` 보정률이 왜곡된다. 보정으로 spec 요구사항이 바뀌면 3-1 승인 게이트를 다시 거친다.
     - **원장 등재**: 이관으로 정한 항목은 `.ai/70_ledger/ledger-entry-template.md` 형식으로 `.ai/70_ledger/active/K-<번호>-<slug>.md`를 신설하고 `.ai/70_ledger/index.md`의 항목 목록 표를 갱신한다. 등재 시 **수용 사유**(왜 지금 고치지 않는지)와 **재검토 조건**(언제 다시 볼지)을 필수로 기재한다. 수용 사유가 없으면 사유 없는 무한 보류가 되고, 재검토 조건이 없으면 `issue-audit`이 기등재 항목을 언제 다시 제기해야 하는지 판정할 수 없어 같은 발견이 매 감사마다 신규로 올라온다.
     - **기등재 재제기 처리**: 발견의 계보가 `기등재 K-<번호> 재제기`이면 **새 항목을 만들지 않고 기존 `K-<번호>` 파일을 갱신**한다. 처리 방향에 따라 세 갈래다.
       - **계속 수용(이관)**: 항목의 `재검토 이력`에 이번 재검토 결과를 추가하고 `재검토 조건`을 다음 기준으로 갱신한다. 상태·위치는 `수용`·`active/` 그대로다.
       - **이슈 승격**: 상태를 `승격(이슈 #N)`으로 바꾸고 `active/`에서 `archive/`로 옮긴 뒤 index 항목 목록을 갱신한다.
       - **이번에 반영(보정)**: 상태를 `해소(PR #N)`으로 바꾸고 같은 방식으로 `archive/`로 옮긴다. PR 번호를 알 때만 확정한다(아래 시점 규칙).
     - **보정으로 원인이 사라진 기등재 종결**: 계보가 재제기가 아니어도, 이번 승인분 보정으로 원장 `active/` 항목의 원인이 사라졌으면 그 항목을 `해소(PR #N)`으로 종결해 `archive/`로 옮긴다. PR 번호를 알 때만 확정한다(아래 시점 규칙).
     - **해소 기재 시점**: 위 두 해소는 `## 이슈 완료 시` 3단계의 원장 해소 기재와 같은 규칙을 따른다. PR이 있으면 이 단계에서 기재하고, 없으면 확정하지 않고 항목을 `active/`에 둔 채 git-pr 4단계 "원장 해소 기재"로 넘긴다. 넘긴 경우에도 항목의 `재검토 이력`에 이번 판단을 남겨 git-pr 원장 대조가 종결 대상을 알아보게 한다. 승격은 이슈 번호를 그 자리에서 얻으므로 이 규칙의 대상이 아니다.

       위 두 규칙 모두 새 `K` 번호를 따지 않는다. 같은 결함에 번호가 늘면 원장이 중복 보고를 막지 못하고, 종결 갱신을 빠뜨리면 이미 해결된 항목이 `active/`에 남아 다음 감사가 그것을 억제 기준으로 삼는다.

     - **옮긴 뒤 링크 갱신**: 이슈 승격, 이번에 반영(보정), 보정으로 원인이 사라진 기등재 종결 가운데 하나로 항목을 `archive/`로 옮겼으면 `## 이슈 완료 시` 3단계 원장 해소 기재의 들어오는 링크 갱신을 같이 수행한다. 해소를 확정하지 않아 `active/`에 둔 항목은 옮기지 않았으므로 대상이 아니다.

**등급별 기본 제시값** — 2단계 발견의 처리 방향 열을 채우는 기본값이다. 등급은 `issue-audit`의 영향×발생확률 매트릭스로 산출된 값을 쓴다. 리포트의 최초 등급이거나, 2단계에서 축 근거를 검토해 매트릭스로 재산출한 등급이며 둘 중 하나만 입력이 된다 (등급별 기본 처리 기준은 `issue-audit/SKILL.md` 참조).

| 등급 | 처리 방향 | 근거 |
|------|-----------|------|
| 높음(HIGH) | 반영 | 보정 필수 — 보정 후 재검증 대상 |
| 중간(MEDIUM) | 기본값 없음 | 사용자 판단 — 승인 질의에서 방향을 정한다 |
| 낮음(LOW) | 이관 | 원장 등재 — 수용 사유·재검토 조건 기재 |
| 정보(INFO) | 보류 | 기록만 — 리포트에 남기고 원장 등재는 선택 |

1단계 미충족(FAIL)·부분 충족(PARTIAL) 발견에는 이 표를 적용하지 않는다. 등급과 무관하게 순서 게이트로 먼저 처리한다.

### `--clear`

진행 중인 이슈를 마무리하고 작업공간을 비워 다음 이슈를 준비한다.

- **용도**: 이슈 작업이 끝났을 때(완료 또는 중단·종료) 이슈 디렉토리 이관, 임시 파일 정리, 이슈 댓글 요약 등록을 한 번에 수행한다.
- **시점**: 마무리(Task N)에서 **PR을 만들기 직전**에 실행한다. 중단·종료는 그렇게 정한 때에 실행한다. archive 이관(git 파일 이동)을 머지 전 작업 브랜치에 포함시키기 위함이며, 머지 후 실행하면 이관이 `main` 직접 푸시가 되어 혼선이 생긴다.
- **동작**: 이슈 디렉토리는 삭제가 아니라 `archive/`로 이관하며 비운다.
  1. **완료 확인**: 아래 두 검사를 하고 `## 이슈 완료 시` 1단계의 최종 audit 모델 기록을 확인한다.
     미완료 항목이 있으면 목록을 보여주고 계속 진행할지 질의한다 (중단·종료 케이스).
     - **체크박스**: plan의 계획 종료 게이트 `점검 완료`, Task 0, 일반 Task를 아래 헬퍼로 확인한다. 게이트 체크박스가 `## Tasks` 밖에 있어 Task 체크박스만 세면 누락된다. Task N의 미체크는 미완료로 세지 않는다. `--clear`가 Task N의 한 단계이기 때문이다.
     - **루프 기록의 결정**: summary `루프 기록` 마지막 행의 `결정`이 `마무리`인지 본다. `마무리`가 아니면(결정 전이거나 `다음 회차`) 미완료 항목으로 보여 준다. 헬퍼는 plan만 읽으므로 이 검사는 직접 한다.

     ```bash
     # <skill 디렉토리>는 이 SKILL.md가 있는 디렉토리. 실행 시 실제 경로로 바꿔 쓴다.
     clear_check='<skill 디렉토리>/scripts/check-clear.sh'

     "$clear_check" --completion '.ai/90_issues/active/issue-<번호>/issue-<번호>-plan.md'
     ```

     헬퍼는 통과하면 무출력, 미완료는 항목을 1행씩 출력하고 종료 코드 1이다. 그 목록을 그대로 사용자에게 보여준다.
  2. **summary 갱신**: `issue-<번호>-summary.md` 상단의 다음 작업을 갱신한다.
     완료 시 `✅ 모든 작업이 완료되었습니다.`, 중단·종료 시 종료 사유를 한 줄로 기재한다.
  3. **이슈 댓글 질의**: summary의 Task별 수행 결과를 기반으로 댓글 초안을 작성하고,
     GitHub 이슈에 댓글로 등록할지 질의한다. 승인 시에만 등록한다.
     - **초안은 `.ai/99_workspace/issue-<번호>-comment.md`에 1회만 쓴다.** 파일명의 `<번호>`는
       이슈 디렉토리명 표기를 그대로 쓴다(`issue-0015` → `issue-0015-comment.md`, 기존 `issue-<번호>-audit-report.md`와 정합).
       `.ai/99_workspace/`가 없으면 만들고 쓴다.
     - **대화에는 파일 경로와 작업내용 요약·본문 승격 목록만 제시하고 전문을 대화에 출력하지 않는다**.
       승인 대상은 등록될 파일이고, 같은 텍스트를 대화에 다시 만들면 응답만 그만큼 늦어진다.
     - 승인하면 그 파일을 그대로 등록한다: `gh issue comment '<앞자리 0 제거한 이슈 번호>' --body-file '.ai/99_workspace/issue-<번호>-comment.md'`.
     - 댓글 파일은 같은 `--clear` 실행의 5단계가 곧바로 회수하므로 별도 정리 타이밍을 두지 않는다.
     - 수정 요청을 받으면 같은 파일을 갱신한다. 회차마다 새 파일을 만들지 않는다.

     댓글 파일은 작업내용 요약을 본문에 두고, Task별 상세는 접어서 작성한다 ("산출물 접기 기준" 참조).
     단, 접기 전에 각 Task의 `수행 내용 요약`·`특이 사항`에서 결정사항·미해결 리스크·다음 액션을 추출해
     작업내용 요약 아래 본문 목록으로 승격한다. `--clear`는 중단·종료 시에도 실행되므로,
     남은 위험·후속 조치가 접힌 영역에 묻히면 안 된다.
     **이 승격 목록은 위 대화 제시분에도 그대로 포함한다**. 파일 안에서만 본문으로 올리면,
     파일을 열지 않고 대화만 보고 승인하는 사용자에게는 접어둔 것과 다를 바 없다.
     해당 항목이 없을 때만 이 목록을 생략한다:

     ```markdown
     <작업내용 요약 — 본문 유지>

     <결정사항·미해결 리스크·다음 액션 목록 — 본문 유지, 해당 항목이 없으면 생략>

     <details>
     <summary>Task별 상세</summary>

     <Task별 수행 결과 상세>

     </details>
     ```
     등록 대상 이슈 번호(`gh` 인자)는 디렉토리명 `issue-<번호>`에서 앞자리 0을 제거해 사용한다 (예: issue-0015 → #15).
     파일명의 `<번호>`는 디렉토리명 표기를 그대로 쓰므로 두 값의 표기가 다르다. 예: `gh issue comment '15' --body-file '.ai/99_workspace/issue-0015-comment.md'`.
     거절하거나 GitHub 연동 수단(gh CLI 등)이 없으면 건너뛰고 다음 단계를 진행한다. 초안 파일은 그대로 남아 5단계 정리 대상이 된다.
     이 댓글 등록은 git 변경이 아니므로 4단계 archive 이관과 타이밍이 분리되어 **머지 전·후 어느 시점이든 가능**하다.
  4. **archive 이관**: `issue-<번호>/` 디렉토리를 `active/`에서 `archive/`로 디렉토리 단위로 이동한다.
     이 이동은 **PR 머지 전, 작업 브랜치에서 수행해 같은 PR에 포함**한다 (머지 후 실행하면 `main` 직접 푸시가 된다).
     같은 단계에서 `## 이슈 완료 시` 3단계의 **원장 해소 기재**를 수행한다. PR이 없을 때 `해소(PR #N)`을 확정하지 않고 git-pr 4단계로 넘기는 규칙도 그대로 적용한다.
     같은 3단계의 **보류 항목 원장 등재 질의**도 이 단계에서 수행하며, 승인한 보류 항목만 등재한다.
     - **Task N 기록**: 1단계의 두 검사가 모두 통과하고 미완료 항목이 없는 실행에서, 이관 직전에 plan의 Task N 체크박스를 체크하고 summary Task N 블록의 `결과`에 `완료`를, `수행 내용 요약`에 `PR 대기(git-pr로 생성)`를 적는다. 미완료를 안고 진행한 실행(중단·종료)에서는 체크하지 않는다.
  5. **99_workspace 정리**: `.ai/99_workspace/` 하위 파일 목록을 재귀로 보여주고
     (`.gitkeep`은 항상 보존, `notes/`는 context-save 산출물이므로 기본 보존이며 사용자가 요청할 때만 정리 대상에 포함),
     보존할 파일은 `archive/issue-<번호>/`로 이동을 제안한다. 나머지는 삭제 확인 후 삭제한다.
  6. **경로 참조 갱신·검증**: 4·5단계로 이동한 **모든 파일**(표준 3종 외 audit 리포트·하위 디렉토리·임의 md 포함)의
     본문에서 이관으로 무효가 되는 경로 참조를 아래 규칙으로 재작성하고, 검증 스니펫으로 잔존 참조 0건을 확인한다.
     - 함께 이동한 파일 간 참조는 `./<파일명>` 상대 링크로 재작성한다 (디렉토리 단위 이동에 안전).
     - 이관으로 무효가 되는 경로(`active/issue-<번호>/…`, `99_workspace/…`) 참조는 이관 후 위치 기준으로 재작성한다.
     - `../` 상대 링크는 이동 후 깊이 기준으로 재계산한다 (`99_workspace/`는 `.ai` 하위 1단, `archive/issue-<번호>/`는 3단).
     - 작성 시점 맥락이 중요한 참조는 새 경로 뒤에 표준 병기 문구를 붙인다: (작성 시점 경로는 `<옛 경로>`, --clear로 이관).
     - archive 파일 본문에 `99_workspace/` 참조를 남기지 않는다 (99_workspace는 언제든 비워질 수 있음).
       내용이 중요하면 파일 자체를 archive로 이관해 `./` 참조로, 이력 서술이면 병기 문구로 전환한다.

     갱신 후 아래 헬퍼 결과가 **0건이면 통과**한다(무출력, 종료 코드 0). 1건 이상이면 잔존 행을 출력하고 종료 코드 1이며, AI가 건별로 판정한다.
     갱신 누락(진탐)은 위 규칙으로 보정하고, 옵션 동작을 설명하는 일반 서술 등 정당한 표기(오탐)는 유지한다.

     ```bash
     # <skill 디렉토리>는 이 SKILL.md가 있는 디렉토리. 실행 시 실제 경로로 바꿔 쓴다.
     clear_check='<skill 디렉토리>/scripts/check-clear.sh'

     "$clear_check" --refs '.ai/90_issues/archive/issue-<번호>/'
     ```

     제외 2건의 근거를 보면 `active/issue-workflow.md`는 이동하지 않는 상주 파일이라 참조가 항상 유효하고,
     "작성 시점 경로는"은 표준 병기 문구 안의 옛 경로(의도된 이력 표기)다.

  `active/`에 이슈 디렉토리가 여러 개면 1~4단계를 이슈별로 반복한 뒤 5단계를 1회 수행하고, 6단계는 이관한 이슈 디렉토리별로 수행한다.

> `## 이슈 완료 시` 절차는 이 옵션의 1·2·4·6단계에 포함된다.
