PR 리뷰와 Self 리뷰 모두 **비즈니스 리뷰**와 **테크 리뷰** 두 단계로 진행합니다.
리뷰 결과는 `.ai/99_workspace/temp_review_result.md`에 판정 한 줄·요약을 맨 위에 두는

## 비즈니스 리뷰

> 목적: 변경 사항이 `.ai/30_contract/` 및 `.ai/40_domain/`에 기록된 소프트웨어 계약·도메인 지식과 일치하는지 검증하고,
> 차이가 있는 경우 AI가 이해한 내용을 정리하여 해당 문서에 반영합니다.

### 1단계: 참조 문서 확보

아래 순서로 비즈니스 리뷰에 필요한 참조 문서를 확보합니다.

1. `.ai/30_contract/index.md`와 `.ai/40_domain/index.md`를 읽어 각 파일의 내용을 파악합니다.
   - index.md는 디렉토리 내 파일별 요약 목차입니다.
   - 리뷰 대상 변경사항과 관련 있는 파일만 선택적으로 읽어옵니다.
   - 사용자가 특정 `.md` 파일을 직접 지정한 경우 해당 파일도 읽어옵니다.
2. index.md가 없거나 참조할 문서가 부족한 경우 → **[문서 부재 시 처리](#문서-부재-시-처리)** 진행

### 문서 부재 시 처리

index.md나 관련 문서가 없어 도메인/계약 정보를 참조할 수 없는 경우:

1. 리뷰 대상 변경 파일(소스 파일 포함)을 읽어 도메인 지식과 소프트웨어 계약을 추정합니다.
2. 추정 내용을 아래 임시 파일에 정리합니다.
   - `.ai/99_workspace/temp_domain.md` — 도메인 관련 내용
   - `.ai/99_workspace/temp_contract.md` — 소프트웨어 계약 관련 내용
3. 사용자와 내용을 검토하고 확정합니다.
4. 확정된 내용을 아래 위치로 이동합니다. 파일명과 하위 경로는 내용에 맞게 선택합니다.
   - `.ai/30_contract/` 하위 적절한 위치
   - `.ai/40_domain/specs/` 또는 `.ai/40_domain/policies/` 하위 적절한 위치
5. 이동 완료 후 `temp_domain.md`, `temp_contract.md`를 삭제합니다.
6. **1단계**로 돌아가 확보된 문서를 기반으로 비즈니스 리뷰를 진행합니다.

### 2단계: 비즈니스 리뷰 수행

확보한 참조 문서를 바탕으로 아래 항목을 검토합니다.

- 변경 사항이 도메인 정책 및 비즈니스 규칙에 부합하는지
- 소프트웨어 계약(API 명세, 연동 규약 등)을 위반하지 않는지

### 3단계: 결과 기록

`.ai/99_workspace/temp_review_result.md`의 **비즈니스 리뷰** 섹션에 검토 결과를 기록합니다 (구조는 "결과 기록 형식" 참조).

## 테크 리뷰

### 1단계: 코드베이스 색인 참조

`.ai/60_codebase/index.md`에 내용이 있으면 참고하여 리뷰 대상과 관련된 기능의 호출 흐름을 빠르게 파악한다.
단, SSoT는 소스코드이므로 색인을 신뢰하지 않고 반드시 실제 코드를 확인한다.
리뷰 과정에서 색인과 실제 코드가 다른 부분을 발견하면, 리뷰 결과에 "코드베이스 색인 갱신이 필요해 보입니다 (`/code-map`)" 의견을 남긴다.

### 2단계: 카테고리별 검증

아래 7개 카테고리를 각각 검증합니다. 카테고리 검증은 **상호 독립**(순서 무관)입니다.
실행 순서·병렬 여부는 실행 환경이 판단하며, 이 스킬은 실행 방식을 지시하지 않습니다.

| 카테고리 | 검증 내용 |
|----------|-----------|
| 기능 | 도메인·비즈니스 내용에 해당하는 주요 기능이 올바르게 구현되었는지 |
| 아키텍처 | 프로젝트 아키텍처 방향(`.ai/10_rules/architecture.md` 참고)에 부합하는지, 관련 ADR(`.ai/50_adr/index.md` 참고)과 설계 정합성이 맞는지 |
| 버그 | 논리 오류·경계 조건·예외 처리·동시성 등 결함 가능성이 없는지 |
| 보안 | 입력 검증 누락·비밀값 노출·권한 확인 누락 등 취약점이 없는지 |
| 코드품질 | 가독성·중복·기존 패턴 준수 등 유지보수성이 유지되는지 |
| 성능 | 불필요한 연산·반복 조회·자원 누수 등 성능 저하 요인이 없는지 |
| 테스트 | 변경 기능에 대한 테스트 케이스가 충분한지, 회귀를 막는지 |

이 카테고리 체계는 git-review가 **원본**입니다 (issue-audit이 복사해 사용하므로 한쪽 변경 시 양쪽 동기화).

## 위험도 분류

비즈니스·테크 리뷰 포인트의 각 지적 사항에 **영향 축**과 **발생확률 축**을 먼저 판정하고, 두 값의 조합으로 위험도를 산출합니다.
리뷰어가 등급을 직접 고르지 않습니다. 리뷰마다 등급이 갈리면 등급이 우선순위 신호로 기능하지 못합니다.
축 정의·매트릭스는 `issue-audit`의 위험도 분류와 동일합니다 (스킬 단독 실행을 위해 복사해 두었으므로 한쪽 변경 시 양쪽 동기화).

**영향 축** — 발견이 실현됐을 때 무엇이 무너지는가

| 값 | 의미 |
|----|------|
| 스펙·기능 달성 차단 | 스펙이 요구한 기능·보장이 성립하지 않음. 데이터 손실·보안 침해처럼 결과가 기능 달성을 무효화하는 결함을 포함한다 |
| 기능 저하 | 동작하나 품질·사용성이 떨어짐 |
| 기술 품질 의견 | 동작·보장에 영향 없는 구조·가독성 지적 |

리뷰 맥락에서는 소프트웨어 계약·도메인 정책 위반(비즈니스 리뷰의 검토 대상)도 "스펙·기능 달성 차단"으로 판정합니다. 계약·정책은 스펙과 동등한 보장입니다.

**발생확률 축** — 어떤 조건에서 실현되는가

| 값 | 의미 |
|----|------|
| 통상 사용 | 정상 사용 경로에서 발생 |
| 특수 조건·엣지 | 경계값·비정상 입력·드문 조합에서만 발생 |

**영향 × 발생확률 매트릭스**

| 영향 \ 확률 | 통상 사용 | 특수 조건·엣지 |
|-------------|-----------|----------------|
| 스펙·기능 달성 차단 | 높음(HIGH) | 중간(MEDIUM) |
| 기능 저하 | 중간(MEDIUM) | 낮음(LOW) |
| 기술 품질 의견 | 낮음(LOW) | 정보(INFO) |

**등급 산출** — 두 축을 판정한 뒤 아래 헬퍼로 매트릭스를 조회합니다. 표를 눈으로 읽어 등급을 고르지 않습니다.

```bash
# <skill 디렉토리>는 이 SKILL.md가 있는 디렉토리. 실행 시 실제 경로로 바꿔 씁니다.
classify='<skill 디렉토리>/scripts/classify-risk.sh'

"$classify" --impact '기능 저하' --likelihood '통상 사용'   # → 🟡 중간(MEDIUM)
```

허용되지 않은 축 값은 종료 코드 2로 걸러집니다. 위 매트릭스와 "판정 산출"의 이모지 대응표가 SSoT이며,
어느 표든 고치면 헬퍼와 `tests/`의 기대값을 함께 갱신합니다.

등급은 리뷰 포인트의 **우선순위 표시와 수용 판단 근거**로만 사용합니다.
등급별 처리 기준(보정 강제·원장 이관)은 두지 않습니다. 보정 여부는 리뷰를 받는 작성자가 판단하며,
작성자 입장의 수용·방어 판단은 `git-pr-feedback`의 영역입니다.

## 상태 산출

카테고리 상태와 비즈니스·테크 리뷰 상태는 리뷰어가 직접 고르지 않고 **최고 위험도로 산출**합니다.
등급 산출과 같은 철학으로, 같은 발견에 리뷰마다 다른 상태가 붙지 않게 합니다.

| 최고 위험도 | 상태 |
|-------------|------|
| 높음(HIGH) | 보완 필요(FAIL) |
| 중간(MEDIUM) | 주의(WARN) |
| 낮음(LOW) 이하 또는 발견 없음 | 통과(PASS) |

같은 헬퍼의 `--status` 모드로 산출합니다. 위험도 목록을 넘기면 최고값 기준 상태가 나오고, 인자가 없으면 발견 없음으로 보고 통과(PASS)를 냅니다.

```bash
"$classify" --status '낮음(LOW)' '중간(MEDIUM)'   # → 🟡 주의(WARN)
"$classify" --status                               # 발견 없음 → 🟢 통과(PASS)
```

- **카테고리 상태**: 그 카테고리 리뷰 포인트의 최고 위험도 기준
- **비즈니스 리뷰 상태·테크 리뷰 상태**: 각 리뷰 전체 리뷰 포인트의 최고 위험도 기준
- 낮음(LOW)·정보(INFO)는 우선순위 신호일 뿐 보완을 강제하지 않으므로 상태를 낮추지 않습니다. 건수는 요약 표에 그대로 드러납니다.

## 판정 산출

리뷰 결과 첫 줄의 판정은 리뷰어가 직접 고르지 않고 **비즈니스 리뷰 상태와 테크 리뷰 상태 2개의 최고값**으로 산출합니다.
등급·상태 산출과 같은 철학으로, 같은 발견에 리뷰마다 다른 판정이 붙지 않게 합니다.

| 최고 상태 | 판정 |
|-----------|------|
| 보완 필요(FAIL) | 변경 요청(REQUEST CHANGES) |
| 주의(WARN) | 조건부 승인(CONDITIONAL) |
| 통과(PASS) | 승인(APPROVE) |

같은 헬퍼의 `--verdict` 모드로 산출합니다. 상태 2개를 위치 인자로 넘기며 순서는 무관합니다.

```bash
"$classify" --verdict '통과(PASS)' '주의(WARN)'   # → 🟡 조건부 승인(CONDITIONAL)
```

Self 리뷰에서 승인(APPROVE)은 **제출 가능**을 뜻합니다. 리뷰어의 승인이 아니라 작성자 본인이 PR을 올려도 되는 상태라는 의미입니다.
판정도 등급·상태와 마찬가지로 우선순위 신호이며, 보정 여부는 리뷰를 받는 작성자가 판단합니다
(작성자 입장의 수용·방어 판단은 `git-pr-feedback`의 영역입니다).

**이모지 대응표**

| 구분 | 값 | 이모지 |
|------|----|--------|
| 등급 | 높음(HIGH) | 🔴 |
| 등급 | 중간(MEDIUM) | 🟡 |
| 등급 | 낮음(LOW) | 🟢 |
| 등급 | 정보(INFO) | ⚪ |
| 상태 | 보완 필요(FAIL) | 🔴 |
| 상태 | 주의(WARN) | 🟡 |
| 상태 | 통과(PASS) | 🟢 |
| 판정 | 변경 요청(REQUEST CHANGES) | 🔴 |
| 판정 | 조건부 승인(CONDITIONAL) | 🟡 |
| 판정 | 승인(APPROVE) | 🟢 |

이모지는 헬퍼가 등급·상태·판정 출력 앞에 붙이며 리뷰어가 손으로 붙이지 않습니다.
항목의 색은 그 항목이 만드는 상태의 색과 같습니다. 정보(INFO)는 상태를 올리지 않으므로 무색(⚪)입니다.
요약 표의 건수 열은 이모지 없이 텍스트 등급만 씁니다. 색이 반복되면 상태 열의 신호가 묻힙니다.
`--status`·`--verdict`는 이모지 접두가 붙은 값과 붙지 않은 값을 모두 받으므로, 헬퍼 출력을 그대로 되넘길 수 있습니다.
위험도 매트릭스·상태 산출 표·판정 표의 셀 값은 텍스트로 유지합니다. 논리 표와 표시 규칙을 분리해 이모지의 SSoT를 이 대응표 한 곳에 둡니다.

## 결과 기록 형식

이 skill 디렉토리의 `templates/review-result-template.md`를 참조하여 `.ai/99_workspace/temp_review_result.md`를 작성합니다.
결론이 먼저 보이는 역피라미드 구조이며, **판정 한 줄과 요약은 비즈니스·테크 리뷰를 모두 마친 뒤 맨 위에 작성합니다**.
기록 순서는 판정 한 줄 → 최종 의견 접기 → 요약 → 비즈니스 리뷰 → 테크 리뷰입니다.

- **판정 한 줄**: 제목 바로 아래에 `--verdict` 출력을 그대로 한 줄로 적습니다 (산출은 "판정 산출" 참조).
- **최종 의견**: 판정을 뺀 종합 판단·후속 액션은 접기로 내립니다.
- **상태 표기**: 요약의 비즈니스·테크 리뷰 상태 줄, 요약 카테고리 표의 상태 열, 테크 리뷰 카테고리 소절 제목 세 곳에 `--status` 출력을 그대로 씁니다. 요약 표의 건수 열은 텍스트 등급만 씁니다.
- **리뷰 포인트**: 볼드 한 줄 `**<이모지> <등급> <제목>**` 다음에 지적 사항과 권장 조치를 일반체 1~3문장으로 적습니다. 영향·발생확률 축 판정, 근거, 코드 위치, 호출 흐름은 항목 바로 아래 접기에 둡니다 (등급 산출은 "위험도 분류" 참조).
- **항목은 문단으로 둡니다**. 리스트 항목 안에 접기를 넣으면 GitHub·IDE 미리보기에서 렌더링이 깨집니다.
- **카테고리 단위 접기는 두지 않습니다**. 접기는 리뷰 포인트 항목 단위로만 둡니다.
- **비즈니스 리뷰도 같은 리뷰 포인트 형식**을 씁니다.
- 발견 0건 카테고리도 요약 표에는 남기고(검증 수행의 증거), 테크 리뷰 본문의 카테고리별 소절은 발견이 있는 카테고리만 둡니다.

리뷰 결과를 보고하는 대화창 답변도 같은 판정 한 줄로 시작합니다. 그 밖의 대화창 출력 형식은 정하지 않습니다.

## 산출물 접기 기준

산출물의 상세 내용은 `<details>` 접기로 분량을 줄이되, 아래 기준을 따릅니다.

- **접기 가능**: 근거·대안 비교·상세 절차·코드 예시·참고자료
- **접기 금지**: 결정사항·리스크·액션 아이템
- **항목별 접기**: 리뷰 포인트는 항목 단위로 접습니다. 접기 안은 축 판정·근거·코드 위치·호출 흐름, 밖은 제목·지적 사항·권장 조치입니다. 카테고리 단위 접기는 두지 않습니다.
- **최종 의견 접기**: 판정 한 줄을 뺀 종합 판단·후속 액션은 접습니다. 액션 아이템의 실체인 리뷰 포인트 제목이 본문에 그대로 보이므로 "액션 아이템 접기 금지"와 충돌하지 않습니다.

`.ai/10_rules/writing-principles.md`가 있으면 그 원칙을 따르고, repo 고유 확장 `writing-principles-local.md`와 충돌하면 local이 우선합니다. 이 블록은 파일이 없을 때의 기본값입니다.
