description: 이슈 시작 전 플랜·구현·검증 3역할의 모델 조합을 분류·추천하는 경량 스킬입니다. 모델 조합 추천, 모델 선별, 이슈 모델 선택, 플랜/구현/검증 모델 배정 시 사용합니다.
---

## 개요

이슈 내용을 입력받아 **플랜·구현·검증 3역할**에 어떤 모델을 배정하면 좋을지 분류·추천하는 경량 스킬입니다.

- **경량**: 이슈 텍스트와 후보 모델만 입력받아 대화로 추천을 제시합니다. 산출 파일·스크립트가 없습니다.
- **비자동**: 추천은 제안일 뿐이며, 최종 선택은 사용자가 합니다. 조합 확정·이후 워크플로우 실행은 하지 않습니다.

## 관련 skill

- issue-work (권장): `issue-work`의 **"새 이슈 시작 시"** 앞단에서 활용할 수 있습니다 — 이 스킬로 모델 조합을 정한 뒤 이슈 작업을 시작합니다. 절차를 결합하거나 `issue-work`를 자동 호출하지는 않습니다(경계 유지).
- issue-audit (권장): 검증 역할의 **"구현과 다른 벤더 모델"** 제약은 `issue-audit`의 교차모델 감사(계획 마지막 고정 Task N)를 전제로 합니다 — 이 스킬이 검증 모델을 타벤더로 추천하는 근거입니다.

## 참조 문서

- **공통 규칙**: `.ai/10_rules/context-loading.md` — 있으면 따르며, 이미 적재되어 있으면 재로딩하지 않습니다.
- **스킬 고유 추가 참조** (있으면 분류 신호 판단에 활용, 없으면 이슈 텍스트만으로 판단):
  - `.ai/50_adr/index.md` — 이슈가 ADR(아키텍처 결정 기록, Architecture Decision Record)을 건드리는지 대조
  - `.ai/30_contract/index.md` — 이슈가 소프트웨어 계약(인터페이스·스키마·프로토콜)에 영향을 주는지 대조

## 입력

이 스킬은 **이슈 내용**과 **후보 모델**을 입력받습니다. 이슈 내용은 분류 신호(설계 판단 필요 여부)를 판단할 근거이고, 후보 모델은 3역할 배정 후보 풀입니다. 후보 모델은 아래 **인자 입력·프롬프트 입력·미입력 시 질의** 3경로로 받으며, **모델 목록을 하드코딩하지 않고** 모델명에서 벤더를 추정하되 확신이 서지 않으면 사용자에게 확인합니다.

### 이슈 내용

분류 신호를 판단할 이슈 내용을 아래 우선순위로 확보합니다.

1. **프롬프트 본문** — 이슈 요구·배경·완료 조건이 프롬프트에 있으면 그대로 사용합니다.
2. **파일·링크** — 스펙 문서 경로나 GitHub 이슈 URL이 주어지면 그 내용을 읽어 사용합니다.
3. **현재 active 이슈** — `.ai/90_issues/active/`에 진행 중 이슈 spec이 있으면 후보로 삼되, 대상이 맞는지 사용자에게 확인합니다.

어느 경로로도 이슈 내용을 확보하지 못하면 추측하지 않고, 추천 전에 사용자에게 이슈 내용을 질의합니다.

### 인자 입력

호출 인자로 후보 모델을 콤마로 나열합니다.

```
/issue-model-triage fable5, opus4.8, gpt-5.6sol
```

### 프롬프트 입력

프롬프트 본문의 자연어에서 후보 모델을 읽습니다 (예: "후보는 opus 4.8이랑 gpt-5.6, gemini 3 정도야").

### 미입력 시 질의

인자·프롬프트 어디에도 후보가 없으면, 추측하지 않고 사용자에게 후보 모델 목록을 질의합니다.

> 벤더 추정: 모델명에서 벤더를 추정합니다(예: `opus`·`fable`·`claude` → Anthropic, `gpt` → OpenAI, `gemini` → Google). 새·미상 모델이라 벤더나 역량 등급이 불확실하면 사용자에게 확인합니다.

## 판단 로직

### 분류 기준

이슈가 **설계 판단이 필요한지** 여부로 분류합니다. 아래 신호가 하나라도 있으면 **설계 판단 필요**, 없으면 **정형 이슈**입니다.

| 신호 | 설명 |
|------|------|
| 설계 선택지 복수 | 구현 방식이 여러 갈래로 갈리고 하나를 골라야 함 |
| ADR 관련 | 아키텍처 결정 기록(ADR)을 새로 남기거나 기존 결정을 바꿈 |
| 계약 영향 | 소프트웨어 계약(인터페이스·스키마·프로토콜)을 바꿈 |
| 완료 기준 비결정성 | 완료의 정의(DoD)를 결정적 명령으로 환원하기 어려워 의미 판단이 필요함 |

분류 결과별 추천 규칙:

- **설계 판단 필요** → 플랜에 후보 중 **최상위 역량 모델**을 배정하고, 구현은 **플랜과 같은 모델**을 기본으로 둡니다(세션 캐시 이점 + 제약 충족). 같은 모델을 쓰기 어려우면 **같은 벤더의 다른 모델**을 차선으로 두되, 이때는 모델 단위 캐시 이점이 보장되지 않음을 함께 안내합니다.
- **정형 이슈** → 플랜·구현 모두 **하위 역량 모델**로 배정해 상위 모델 한도를 아낍니다.

> 역량 등급("최상위/하위")은 이 스킬을 실행하는 AI가 그 시점 지식으로 후보를 등급화합니다. 확신이 서지 않는 새·미상 모델만 사용자에게 확인하며, 등급표를 이 문서에 하드코딩하지 않습니다.

### 제약 검증

추천 조합은 아래 제약을 모두 만족해야 합니다.

- **플랜·구현**: **같은 모델을 기본**으로 합니다(프롬프트 캐시가 모델 단위라 세션 중 전환은 손해). 같은 모델이 어려우면 **같은 벤더의 다른 모델**까지 허용하되, 이때는 캐시 이점이 보장되지 않는 차선임을 밝힙니다 — 세션 단위로 벤더를 섞지 않습니다.
- **검증**: 구현과 **다른 모델 + 다른 벤더** (교차모델 audit 전제, `issue-audit` 근거)
- **만족 불가 시**: 후보만으로 제약을 채울 수 없으면 조합을 억지로 추천하지 않고, **그 사실과 부족한 조건**(예: "검증용 타벤더 모델 부재")을 안내합니다.

## 출력

추천은 아래 3요소로 제시합니다.

1. **추천 조합 표**

   | 역할 | 모델 | 벤더 | 선정 사유 |
   |------|------|------|-----------|
   | 플랜 | … | … | 한 줄 |
   | 구현 | … | … | 한 줄 |
   | 검증 | … | … | 한 줄 |

2. **분류·근거 요약**: 이 이슈를 어떻게 분류했는지(설계 판단 필요 / 정형 이슈)와 그 근거 신호, 제약 충족 여부를 짧게 요약합니다.
3. **경계 명시**: "이 표는 제안일 뿐이며, 최종 선택은 사용자가 합니다. 이 스킬은 조합을 확정하거나 이후 워크플로우(issue-work 등)를 자동 실행하지 않습니다."

## 예시

> 아래 예시의 역량 등급 배정(어느 후보가 최상위·하위인지)은 **작성 시점의 런타임 지식으로 등급화한 예시**이며 고정 등급표가 아닙니다(위 `분류 기준`의 하드코딩 금지 원칙). 같은 후보라도 실행 시점 지식에 따라 등급이 달라질 수 있으니, 표의 특정 모델 배정이 아니라 **분류 → 등급화 → 제약 검증의 흐름**을 참고하세요.

### 예시 1: 후보 3개 입력 시 추천 표

입력: `/issue-model-triage fable5, opus4.8, gpt-5.6sol`
이슈: 새 캐시 계층을 어디에 둘지 설계 선택지가 갈리고 ADR을 남겨야 하는 이슈.

분류: **설계 판단 필요** (근거: 설계 선택지 복수 + ADR 관련).

| 역할 | 모델 | 벤더 | 선정 사유 |
|------|------|------|-----------|
| 플랜 | Claude Fable 5 | Anthropic | 후보 중 최상위 역량 — 설계 판단 필요 이슈라 플랜을 최상위로 |
| 구현 | Claude Fable 5 | Anthropic | 플랜과 같은 모델 — 세션 캐시 이점, 제약(플랜·구현 같은 모델) 충족 |
| 검증 | GPT-5.6 (sol) | OpenAI | 구현과 다른 벤더·다른 모델 — 교차모델 audit 제약 충족 |

> 미선정: Claude Opus 4.8 (Anthropic) — 이번 조합에 불필요(후보는 풀이며 전부 쓰지 않아도 됨).
> 제약 충족: 플랜·구현 같은 모델(Fable 5), 검증은 타벤더(OpenAI). 이 표는 제안이며 최종 선택은 사용자가 합니다.

### 예시 2: 타벤더 검증 모델 부재 시 실패 안내

입력: `/issue-model-triage fable5, opus4.8`
두 후보 모두 Anthropic이라 검증 역할의 "구현과 다른 벤더" 제약을 만족할 수 없습니다.

> 추천을 제시할 수 없습니다.
> - 부족한 조건: **검증용 타벤더 모델**이 후보에 없습니다(후보가 모두 Anthropic).
> - 필요 조치: 비-Anthropic 모델(예: OpenAI GPT 계열, Google Gemini 계열)을 후보에 최소 1개 추가해 주세요.

### 예시 3: 정형 이슈 추천 표

입력: `/issue-model-triage fable5, opus4.8, gpt-5.6sol`
이슈: 오타·문구 정정처럼 설계 선택지가 없고 완료의 정의(DoD)가 결정적 명령으로 환원되는 정형 이슈.

분류: **정형 이슈** (근거: 4신호 없음 — 설계 선택지 단일, ADR·계약 무관, 완료 기준 결정적).

| 역할 | 모델 | 벤더 | 선정 사유 |
|------|------|------|-----------|
| 플랜 | Claude Opus 4.8 | Anthropic | 정형 이슈 — 후보 중 하위 역량 모델로 최상위 모델 한도 절약 |
| 구현 | Claude Opus 4.8 | Anthropic | 플랜과 같은 모델 — 캐시 이점, 제약(플랜·구현 같은 모델) 충족 |
| 검증 | GPT-5.6 (sol) | OpenAI | 구현과 다른 벤더·다른 모델 — 교차모델 audit 제약 충족 |

> 미선정: Claude Fable 5 (Anthropic) — 정형 이슈라 최상위 역량 모델은 불필요(한도 절약).
> 제약 충족: 플랜·구현 같은 모델(Opus 4.8), 검증은 타벤더(OpenAI). 이 표는 제안이며 최종 선택은 사용자가 합니다.
